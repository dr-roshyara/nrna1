# F3.2 Domain Construction Contract

**Status**: Specification for F3.2-L1 → L2 stabilization  
**Date**: 2026-05-14  
**Purpose**: Define the single construction model for CommitteeAssociation and MembershipLineage

---

## Core Principle

After F3.2-L1, there is ONE way to construct valid episodes and lineages.

No legacy constructors, no implicit defaults, no status injection.

---

## 1. Creation Rules

### CommitteeAssociation::create()

**Purpose**: Bootstrap a new constitutional relationship

**Contract**:
```php
CommitteeAssociation::create(
    MemberId $memberId,
    CommitteeId $committeeId,
    ApplicationReason $associationType,
    DateTimeImmutable $associatedAt,
): CommitteeAssociation
```

**Always produces**: `status: ACTIVE`, no audit fields (`actorId: null`, `transitionReason: null`, `transitionedAt: null`)

**Never**: Do not pass `status` parameter. Do not create SUSPENDED/TERMINATED via `create()`.

**Used by**:
- `MembershipApplication::approve()` → establishes new relationship
- `MembershipLineage::establish()` → creates initial ACTIVE episode
- `MembershipLineage::reapplyInitialEpisode()` → new relationship after termination

---

### CommitteeAssociation::rehydrate()

**Purpose**: Reconstruct an episode from persistence (database roundtrip)

**Contract**:
```php
CommitteeAssociation::rehydrate(
    AssociationId $associationId,
    MemberId $memberId,
    CommitteeId $committeeId,
    ApplicationReason $associationType,
    DateTimeImmutable $associatedAt,
    MembershipStatus $status,
    ?string $actorId = null,
    ?string $transitionReason = null,
    ?DateTimeImmutable $transitionedAt = null,
): CommitteeAssociation
```

**Always**: Applies the same constructor invariants as `new CommitteeAssociation(...)`.

**If database is invalid**: Constructor throws `InvalidMembershipConstructionException` — this is **correct behavior**. DB validation happens at application startup, not silently during loads.

**Used by**:
- `EloquentMembershipLineageRepository::hydrateEpisodes()` → loads from DB

---

### Transition Methods

**Purpose**: Safe state transitions with immutability guarantees

**Contract**:
```php
$episode->suspend(string $actorId, string $reason, DateTimeImmutable $at): CommitteeAssociation
$episode->restore(string $actorId, DateTimeImmutable $at): CommitteeAssociation
$episode->terminate(string $actorId, string $reason, DateTimeImmutable $at): CommitteeAssociation
```

**Always**: Return a new instance, never mutate original.

**Invariants enforced**:
- `suspend()`: requires ACTIVE → produces SUSPENDED with all audit fields
- `restore()`: requires SUSPENDED → produces ACTIVE with actorId (restoration actor is valid ACTIVE state) + transitionedAt
- `terminate()`: requires not-TERMINATED → produces TERMINATED with all audit fields

**Never**: Call constructor directly to create SUSPENDED/TERMINATED. Use these methods.

**Used by**:
- `MembershipLineage::suspend()` → delegates to entity method
- `MembershipLineage::restore()` → delegates to entity method
- `MembershipLineage::terminate()` → delegates to entity method
- Tests to establish non-ACTIVE state for assertions

## 2. Rehydration Rules

### What database is allowed to contain

**ACTIVE episodes**:
- `status = 'active'`
- `actorId` can be null OR a UUID (e.g., restoration actor)
- `transitionReason` must be null
- `transitionedAt` can be null OR a timestamp (for restoration timestamp)

**SUSPENDED episodes**:
- `status = 'suspended'`
- `actorId` MUST be a UUID (who suspended)
- `transitionReason` MUST be a string (why suspended)
- `transitionedAt` MUST be a timestamp

**TERMINATED episodes**:
- `status = 'terminated'`
- `actorId` MUST be a UUID (who terminated)
- `transitionReason` MUST be a string (why terminated)
- `transitionedAt` MUST be a timestamp

### Hydration strictness

**Constructor invariants apply to rehydration**:
- Invalid DB state surfaces at load time (not silently tolerated)
- If DB contains SUSPENDED without actorId, hydration fails (by design)
- If DB contains TERMINATED without reason, hydration fails (by design)

**Rationale**: The constitutional system treats invalid DB as a configuration error that must be caught at startup, not hidden during operation.

**Migration path**: Before deploying F3.2-L1, verify all rows satisfy these invariants. Add a pre-startup validation check if needed.

---

### Constructor vs Rehydration boundary

| Aspect | Constructor | Rehydration |
|--------|-------------|-------------|
| **What it is** | Creating new state | Reconstituting persisted state |
| **Invariants** | Applied (strict) | Applied (strict) |
| **On violation** | Throws exception | Throws exception |
| **When it runs** | During domain logic | During DB load |
| **If it fails** | Business logic error | Configuration/data error |

**Both use the same constructor**, so invariants cannot diverge.

## 3. Transition Rules

### Data ownership per transition

| Data | Lives where | Owned by | Duration |
|------|------------|----------|----------|
| `actorId` (who acted) | Entity state (episodes) + Event | Transition method + Event handler | Permanent |
| `transitionReason` | Entity state (episodes) + Event | Transition method + Event handler | Permanent |
| `transitionedAt` | Entity state (episodes) + Event | Transition method + Event handler | Permanent |
| Event metadata | Domain event only | Event handler | Event lifetime |

### Example: Suspension lifecycle

```php
// 1. Command asks domain to suspend
$suspended = $active->suspend($actorId, $reason, $at);

// 2. Entity creates new SUSPENDED episode with all audit fields
// 3. Aggregate (MembershipLineage) records MembershipSuspended event
$this->recordEvent(new MembershipSuspended(
    lineageId: $this->lineageId,
    memberId: $this->memberId,
    committeeId: $this->committeeId,
    actorId: $actorId,           // duplicated for audit completeness
    reason: $reason,
    suspendedAt: $at,
));

// 4. Repository saves SUSPENDED episode to DB (with audit fields)
// 5. Event handler processes MembershipSuspended event

// Later: Replay
// 6. Event replay reconstructs SUSPENDED from DB via rehydrate()
// 7. Constructor validates all audit fields present
// 8. Event handler re-executes
```

### State vs Event distinction

**Entity episode state**: "What is the member's current/historical status?"
- Contains: status, audit fields, identities
- Persisted: YES (part of episodes array)
- Used for: governance queries, eligibility checks, history reconstruction

**Domain event**: "What institutional action happened?"
- Contains: what happened, who did it, when, why, context
- Persisted: YES (separate event stream, F3.3)
- Used for: audit trail, replay, integration, notifications

**Both exist together** — not either/or.

## 4. Test Construction Patterns

### Pattern 1: Create a new ACTIVE episode (most common)

```php
$episode = CommitteeAssociation::create(
    memberId: $member,
    committeeId: $committee,
    associationType: ApplicationReason::RESIDENCE,
    associatedAt: new \DateTimeImmutable('2026-05-14 10:00:00'),
);
// Result: $episode->status === ACTIVE
```

### Pattern 2: Create a SUSPENDED episode (for test setup)

```php
$active = CommitteeAssociation::create($member, $committee, ApplicationReason::RESIDENCE, $now);
$suspended = $active->suspend('actor-uuid-001', 'Test suspension', $now);
// Result: $suspended->status === SUSPENDED with all audit fields
```

### Pattern 3: Create a TERMINATED episode (for test setup)

```php
$active = CommitteeAssociation::create($member, $committee, ApplicationReason::RESIDENCE, $now);
$terminated = $active->terminate('actor-uuid-001', 'Test termination', $now);
// Result: $terminated->status === TERMINATED with all audit fields
```

### Pattern 4: Establish a lineage (aggregate creation)

```php
$lineage = MembershipLineage::establish(
    lineageId: LineageId::generate(),
    memberId: $memberId,
    committeeId: $committeeId,
    tenantId: TenantId::fromString('test-tenant'),
    reason: ApplicationReason::RESIDENCE,
    at: new \DateTimeImmutable('2026-05-14 10:00:00'),
);
// Result: $lineage->current()->status === ACTIVE
```

### Pattern 5: Reconstitute a lineage (hydration)

```php
$episodes = [
    CommitteeAssociation::rehydrate(
        AssociationId::generate(),
        $memberId,
        $committeeId,
        ApplicationReason::RESIDENCE,
        $now,
        MembershipStatus::ACTIVE,
    ),
];
$lineage = MembershipLineage::reconstitute(
    LineageId::generate(),
    $memberId,
    $committeeId,
    TenantId::fromString('test-tenant'),
    $episodes,
);
// Result: lineage is reconstructed with validation
```

### Pattern 6: Perform transitions within a lineage

```php
$lineage->suspend($actorId, $reason, $at);    // adds SUSPENDED episode
$lineage->restore($actorId, $at);              // adds restored ACTIVE episode
$lineage->terminate($actorId, $reason, $at);   // adds TERMINATED episode
```

## 5. Constructor Invariants (F3.2-L1)

These MUST be enforced at construction time:

### ACTIVE episodes

- No required audit fields
- `actorId` may be null OR a UUID (valid on restore)
- `transitionReason` must be null
- `transitionedAt` can be null OR a timestamp

### SUSPENDED episodes

```
if status = SUSPENDED:
  require actorId != null              // "who suspended?"
  require transitionReason != null     // "why suspended?"
  require transitionedAt != null       // "when suspended?"
```

### TERMINATED episodes

```
if status = TERMINATED:
  require actorId != null              // "who terminated?"
  require transitionReason != null     // "why terminated?"
  require transitionedAt != null       // "when terminated?"
```

### MembershipLineage invariants

```
if episodes is empty:
  throw InvalidArgumentException("Lineage must have at least one episode")

if episodes[0].status != ACTIVE:
  throw InvalidArgumentException("Episode chain must contain valid transitions")
```

## 7. Design Rationale

### Why constructor validation at hydration time?

> "Better to fail loudly at startup than fail silently at query time"

If DB contains invalid data, that is a **configuration error**, not a **runtime error**.

Validating at hydration catches data problems before the app operates on them.

### Why no status flexibility in create()?

> "Factory purity"

`create()` is **definitional**: "I am creating a new relationship."

New relationships are ALWAYS ACTIVE. Status transitions are **behavioral** (via transition methods).

Mixing them violates the boundary between definition and behavior.

### Why explicit rehydrate() factory?

> "Semantic clarity"

Hydration is **semantically different** from creation:
- Creation: "I am making something new"
- Rehydration: "I am reconstituting something that existed"

Explicit factory names the semantic difference clearly.

### Why is actorId valid on ACTIVE (restored)?

> "Audit trail completeness"

When a member is restored from suspension, we want to know WHO restored them.

That information lives in:
1. The `MembershipRestored` event (event stream)
2. The resulting ACTIVE episode (entity state)

This is **defense-in-depth**, not duplication.

## 8. Known limitations (out of scope for F3.2-L1)

This contract does NOT yet define:

- [ ] Full state machine transitions (ACTIVE → SUSPENDED → ACTIVE → SUSPENDED — allowed or not?)
- [ ] Event replay determinism checks
- [ ] Temporal ordering guarantees
- [ ] Hydration from event streams vs database

These are **Layer 2–5 concerns** and will extend this contract.

This contract defines a **single, uniform construction model** for episodes and lineages.

After F3.2-L1 alignment to this contract:

✅ All tests speak the same construction language
