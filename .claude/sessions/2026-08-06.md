## Seventh block (appended): a production page fixed and confirmed live

### Summary

`https://publicdigit.com/organisation-create-tutorial` threw `SyntaxError: Invalid linked format` and rendered nothing. **Fixed, deployed, and confirmed working in a browser by the Product Owner** — the first thing this session verified in production rather than locally.

**Cause:** a translation contained `support@publicdigit.com`, and in vue-i18n `@` starts a linked message (`@:key`), so a literal `@` is a syntax error.

### Completed

| Item | Outcome |
|---|---|
| The reported page | ✅ **Fixed, deployed, confirmed live** |
| The whole `@` class | **30 messages across 9 namespaces** — `0 of 14,341` messages can now throw this error |
| Assets | Rebuilt and committed (`app-Bu_oS0vX.js` → `app-0p9dPQCa.js`) — **this is the step that made the fix real** |
| `PBDIGIT-44` | Records the fix, the still-open `{{ }}` class, and the missing i18n gate |

### Decisions

- **`(at)` for prose, `{'@'}` for placeholders and CSV examples.** One directive, two implementations: `(at)` in an *import example* would produce broken files users actually upload, and in a form placeholder it teaches the wrong email format.
- **Left `mailto:support@publicdigit.com` untouched** — an href is not a message; escaping it would break the link.
- **Did not delete `public/build/`** when asked whether to: it is the tracked deploy artifact, all 386 assets are manifest-referenced, and deleting it would have removed the very assets needing deployment.
- **Did not add the i18n gate** — a new CI gate is a governance decision. Recorded in `PBDIGIT-44` with the working prototype described.

### Problems — all three were mine

1. **My first verification used the wrong tool and reported a false pass.** `baseCompile()` accepted all 14,341 messages including the broken one; I said "0 failures" before catching that only the vue-i18n *runtime* reproduces it. **A gate built that way would pass a broken build.**
2. **I fixed the source and implied the page was fixed.** It was not — `public/build/` is tracked, no CI builds it, and the browser was still served the old bundle. The console output the Product Owner pasted three times **contained the proof in its first line** (`app-Bu_oS0vX.js`); I read it as a repeated complaint rather than as evidence naming the deployed build.
3. **I used `npm run build` when the project also has `npm run prod`** (`vite build && node scripts/fix-build.js`). I checked before claiming it was harmless: `fix-build.js` only normalises Windows backslashes in the manifest, and the manifest has none — a no-op on Linux. Correct by luck, not by reading first.

### The diagnostic worth keeping

```
curl -s <page-url> | grep -o 'app-[A-Za-z0-9_-]*\.js'
```

**If that filename is not the one in the repo, no source change can be live** — and every further edit is wasted motion. Two of the three problems above would have been caught by running it once.

### Rev 2 — the Product Owner supplied the domain model, and rev 1 was wrong without it

**The legacy "Unpublish Results" control meant *hide the public results page during a dispute*, never *undo publication*.** Two business concepts, not one:

* **Election Lifecycle** — *this election reached `results_published`*. A constitutional fact, **immutable once true**.
* **Result Visibility** — *the public results page is reachable*. **Toggleable** during a dispute.

**The conflation is proven mechanically:** `Election::applySideEffectsForPublishResults()` `:1905-1911` sets `results_published` (visibility) and `results_published_at` (the fact) **in one statement** — so nothing ever revealed the seam. The lifecycle reads only the timestamp; the public page reads only the boolean. **The field pair already implements the correct model by accident, and the boolean is misnamed.**

**Two of my rev-1 claims were wrong and are withdrawn in the ticket:**

1. *"the engine and the boolean disagree — a divergence."* **Not a divergence.** *Published* and *hidden* are both true, about different facts.
2. *"one-way door, the election is stuck."* **The lifecycle is correct** — publication should be irreversible and `archive` should be the only exit. The real gap is that **Result Visibility has no capability**, so there is no supported way to show the results again.

**What got sharper instead:** `results_published_at` is **mass-assignable** (`$guarded = []`, 72 fillable), and `updateTimeline()` accepts it as editable input. **A deputy can fabricate the constitutional publication fact at an arbitrary date, with no transition** — worse than rev 1's "sets a boolean". Adjacent, recorded but *not* ticketed (discovery frozen): **`state` and `status` are mass-assignable too.**

**And the irony worth remembering:** the timeline form is currently the *only* working way to restore visibility. **The escalation defect is also the accidental recovery path** — so D-2 must not be fixed alone without D-1's control existing, or the results become unreachable by any supported route.

### Knowledge recorded (extended the existing candidate — ES-005.4, never a copy)

Two corollaries added to `docs/pks/2026-08-06-legacy-consumer-migration-pattern-candidate.md`:

1. **New functionality gets built against the deprecated representation.** Coexistence is the intended transitional state; the defect is that the deprecated representation stays *writable and welcoming*. **A migration that does not close it to new writers is not converging.**
2. **A migration can inherit a conflation.** Before deciding where a legacy field's authority moved, establish **how many business concepts it encodes** — otherwise both migrate to one authority and the second becomes unimplementable. **Diagnostic: if a capability can only be expressed by writing the legacy field, the field carried more than one concept.**

### Rev 3 — four refinements from the Product Owner, and one of them was reachable in production

**The diagnosis is now the PO's sentence, which is more precise than mine:** *Result Visibility never became a first-class capability during the constitutional migration.* Publication migrated into the lifecycle; visibility did not get a capability; **so the legacy boolean continued as a surrogate for the missing one.** Mine described the symptom ("modelled as a lifecycle action"); this names the cause. File renamed to match.

**Language rule adopted:** *publication* = the constitutional fact only (`results_published_at`, the `publish_results` transition). The control is **`hide results` / `show results`** — never "unpublish", never "hide publication". Remaining uses of "unpublish" in the ticket are quoted legacy labels or code identifiers, which the rule permits.

**The authorization question was reclassified, not answered.** *Who may hide/show results* is an **authorization policy** (A-1), not a domain-model question — the domain already knows what happens. Same for whether hiding carries a reason (A-2). **No open domain questions remain**, and neither item blocks D-2.

#### The refinement that turned into a finding

The PO asked for the dependency to be documented — *visibility exists only once publication has happened*, so `draft + visible results` is impossible. **Checking whether it was enforced showed it is not, and that the invalid state is reachable:**

* `ResultController:23` gates on `if (! $election->results_published)` — **the boolean alone, no lifecycle check.**
* `validatePhaseUpdatePermissions()` `:1478-1503` guards the `administration`, `nomination` and `voting` date groups — **there is no guard for `results_published_at`.**

**So a deputy filling `results_published_at` on a `draft` election renders a public results page for an election that never published — and on a `voting_active` election it exposes results while voting is open.** Recorded as **invariant V-1** with a test that must set the boolean on a draft *and* a voting election. **This is the strongest reason D-2 is a defect rather than an untidiness.**

#### Knowledge addition

Corollary 2 gained the sharper consequence: **splitting a conflation without stating the dependency converts a hidden conflation into a reachable invalid state** — worse than the conflation, because a single field at least made the two concepts move together.

#### Judgement to remember

**The PO's "document the dependency" was worth more than a documentation task.** Writing an invariant down forces the question *is it enforced?* — and here the answer was no, with a live path. **An invariant that is merely stated is a comment; the value came from testing it against the code.**

## PBDIGIT-58B implemented — Election Entry Resolution migrated to the lifecycle

**Approved by the Product Owner with one architectural condition:** consumers must ask a business question, not compare lifecycle enum values. **The condition was satisfied by discovery, not design** — `ElectionLifecycle::of($e)->canVote()` already exists, is already the house idiom (`ElectionController.php:46`), and the facade declares itself "the sole consumption point… Controllers, repositories, and queries MUST NOT bypass this to access legacy fields directly."

### What `canVote()` is (the evidence the PO required before login could depend on it)

```
canVote()  Facades/ElectionLifecycle.php:115
  → snapshot->canVote → derivePermissions()  EngineImpl:245-251  (VotingActive ⇒ true)
    → getState()  EngineImpl:64-120
```

The last hop *is* `state === VotingActive` — but that state is the output of the constitutional computation, which already accounts for **suspension** (`:69`, checked first), **archived** (`:74`), **results published** (`:79`), **counting incl. setup completion** (`:85-89`) and **the voting window itself** (`:100`). So `canVote()` is a *named projection*; `getState()` is the computation. A future `voting_paused` changes `derivePermissions()`, not this consumer.

**Boundary recorded, at the PO's insistence: `canVote()` is election-level, not voter-level.** It answers *"is this election accepting votes?"* — never *"may this voter enter?"* Voter eligibility stays with `VoterEligibilityService`/`EligibilityEvaluator` (MB-5, unresolved, untouched).
