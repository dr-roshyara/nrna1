## Mission

Investigate the following customer/business journey in PublicDigit:

> "A person wants to create an organisation in PublicDigit and then visit the organisation's homepage."

This is an ARCHITECTURAL / PRODUCT-DISCOVERY investigation.

The objective is NOT to make tests green.
The objective is NOT to repair code.
The objective is to establish, from evidence, whether the system provides the intended business capability, how that capability is currently represented across the architecture, and whether the existing verification actually verifies the business outcome.

Produce:
1. one evidence-based discovery/review report;
2. one backlog ticket capturing the verified problem/opportunity and the next authorised work;
3. update the backlog index only if that is required by the repository convention.

NO production-code changes.
NO test changes.
NO fixture changes.
NO migrations.
NO refactoring.
NO implementation of proposed solutions.

---

# 1. Governing architectural principle

Business value is the highest-level concern.

Analyse in this order:

business outcome
→ business capability
→ domain meaning / business invariants
→ authoritative business decision ownership
→ application capability / use case
→ authorization
→ interface / HTTP / navigation
→ persistence
→ test / verification

Do not invert this order.

Do not begin from:
- a PHPUnit failure,
- a controller,
- a route,
- a model,
- a database column,
- or an existing test.

Those are implementation evidence, not the business definition.

---

# 2. DDD separation of concerns

For every significant decision encountered, distinguish explicitly between:

### Domain
What business fact, invariant, lifecycle rule, or organisation concept exists?

### Application
What business capability/use case orchestrates the operation?

### Authorization
Who is permitted to perform the operation?

### Infrastructure
How is the business operation technically persisted, delivered, cached, mailed, etc.?

### Interface / Projection
How does the user reach the capability and how is the resulting organisation represented?

### Verification
What business invariant or customer outcome does each test actually verify?

Do not infer business ownership from:
- namespace,
- directory,
- controller location,
- test location,
- class name,
- database table,
- or framework convention.

Determine ownership from behaviour and evidence.

---

# 3. First establish the business journey

Define the journey independently of implementation.

At minimum identify:

1. Actor
2. Business intent
3. Business outcome
4. Preconditions
5. Organisation creation capability
6. Resulting organisation identity
7. Organisation homepage capability
8. Authorization expectations
9. Tenant/organisation context expectations
10. Expected navigation after successful creation
11. What must be true for the journey to be considered successful

Do not invent missing business rules.

If a requirement is not established in the repository, record:

> BUSINESS DECISION REQUIRED

rather than guessing.

→ route
→ request validation
→ application/controller entry point
→ domain/application behaviour
→ organisation persistence
→ membership/ownership relationship
→ tenant/current-organisation context
→ redirect/navigation
→ homepage route
→ middleware/authorization
→ homepage controller/use case
→ homepage projection
→ dependent data

For every transition record exact evidence.

Use file + line references wherever possible.

Do not describe something as "working" merely because the code appears connected.

Use precise classifications:

- OBSERVED IN CODE
- OBSERVED AT RUNTIME
- TESTED
- INFERRED
- NOT VERIFIED
- BUSINESS DECISION REQUIRED
- MECHANISM NOT ESTABLISHED

# 5. Runtime versus static evidence

This distinction is mandatory.

If runtime verification is unavailable, do NOT write:

> "The journey works."

Instead write:

> "The journey is statically wired end-to-end, but runtime execution has not been established."

Similarly:

> "No statically detectable blocker was found"

is acceptable.

But do not convert that into:

> "The happy path is complete."

unless an actual runtime execution proves it.

A successful test is also not automatically runtime proof of the customer journey if the test exercises a different contract or mechanism.

---

# 6. Test-evidence audit

Treat existing tests as evidence to classify, not as truth.

For every relevant test ask:

1. What business outcome is the test intended to protect?
2. What business invariant does it assert?
3. What capability does it exercise?
4. What interface does it enter through?
5. What authoritative decision source does the behaviour use?
6. Is the fixture establishing the actual required business state?
7. Is the test exercising the current product contract?
8. Is it testing the correct layer?
9. Is it asserting business behaviour or implementation mechanics?
10. Does the assertion still correspond to the current business journey?

Classify discrepancies without immediately fixing them.

Use:

- TEST CURRENTLY VALID
- TEST OBSOLETE
- TEST CONTRACT DRIFT
- TEST FIXTURE DRIFT
- TEST WRONG LAYER
- TEST IMPLEMENTATION-COUPLED
- TEST COVERAGE GAP
- UNDETERMINED

Do not assume that every failing or outdated test should be repaired.

---

# 7. Business Decision Ownership

For important decisions record:

`Domain`
`Application`
`Policy/Authorization`
`Infrastructure`
`Interface/Projection`
`Unknown`

Examples:

- "Who may create an organisation?" → authorization/business policy question.
- "What constitutes a valid organisation?" → domain/business rule.
- "How creation is orchestrated?" → application.
- "Where organisation data is stored?" → infrastructure/persistence.
- "What the homepage displays?" → interface/projection unless it represents a business decision.

Do not confuse a technical mechanism with the owner of the business decision.

---

# 8. Legacy and contract drift

Explicitly investigate whether current tests, routes, controllers and frontend code describe different versions of the product.

For every discrepancy distinguish:

1. Old contract exists
2. New contract exists
3. Business requirement is known
4. Business requirement is unknown

Do NOT decide which contract is correct from code alone.

If the business source of truth is absent:

> BUSINESS DECISION REQUIRED

---

# 9. Security and privacy

Because organisation creation is a security-sensitive capability, explicitly inspect:

- authentication requirement;
- email verification requirement;
- authorization;
- organisation membership;
- tenant isolation;
- creator/owner provenance;
- cross-organisation access;
- CSRF protection;
- sensitive information written to logs;
- redirect target;
- whether the newly-created organisation becomes the user's active organisation.

Do not call something a security defect merely because it differs from another route.

Establish the actual business/security invariant first.

For example:

> "Other organisation routes require verified users"

does NOT automatically establish:

> "Organisation creation must require verified users."

That is a business/security policy decision unless already established elsewhere.
