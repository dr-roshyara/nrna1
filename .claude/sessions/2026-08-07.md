## PBDIGIT-61 — newsletter suite repaired (authorized: this ticket only)

**Baseline first**, per the PO's added step: 6/6 reproduced on a clean tree at `45df1dc5`, every failing assertion recorded before diagnosis.

### The root cause was a feature defect, and the evidence named which side

The route prefix is **`organisations/{organisation:slug}`** — explicit model binding. Every method of `OrganisationNewsletterController` declared **`string $slug`** and then re-queried by it, so the lookup ran against a value that was no longer the slug → `404` before any controller logic (which is why a non-admin saw `404`, not `403`).

**Proof chain, measured not inferred:**
1. A diagnostic probe showed the org resolves by slug, the user is verified and holds the `admin` role, and the URL is correct — yet the request 404s.
2. `withoutExceptionHandling()` surfaced `ModelNotFoundException` thrown at **the controller's own `firstOrFail`**, not in binding.
3. `bindingFields` = `{"organisation":"slug"}` — the route binds a model.
4. **Calling the controller directly with the slug string succeeded** while the routed call failed → parameter passing, not data.
5. **Decisive:** sibling controllers in the *same route group* (`ParticipantInvitationController`, `OrganisationRoleController`) already take `Organisation $organisation`. This controller was the only one written against a contract that does not exist.

**Fix:** 13 methods now take `Organisation $organisation`; redundant lookups removed; 5 redirects switched from `$slug` to the model.

### Two genuine test defects behind it

* three `store` posts omitted **`audience_type`** (controller requires it) — validation failed, so the redirect happened but no row was created;
* `preview recipient count` used **`status: 'inactive'`**, rejected by `members_status_check` (`active|expired|suspended|ended`) → `'expired'`, preserving the 3-of-5 intent.

**Neither weakens an assertion** — both supply input the feature legitimately requires.

**Result: `NewsletterCreationTest` 6/6 green.** Then step 7: the deferred `PBDIGIT-48` predicate removal re-applied and suites re-run — still green. **`PBDIGIT-48` Bucket 1 now has zero deferrals.**

**HEAD verification first** (PO's instruction — narrative is not evidence): the `status != 'deleted'` predicate is **physically absent** at HEAD; the only `'deleted'` occurrences are the two explanatory comments, and `git show 1fd746a3` contains `- ->where('status', '!=', 'deleted')` twice. **Then the residual, investigated exactly as instructed — assert the audience query first, change nothing.** That exonerated both suspects in one run:

| Measurement | Result |
|---|---|
| `queryAllMembers` vs the fixture | **1** — the audience query is **correct** |
| `audience_type` in the **DB** | `'all_members'` (column is `NOT NULL DEFAULT`) |
| the earlier `NULL` | an **unhydrated in-memory model** — which is why the speculative fixture edit changed nothing, and why reverting it was right |
| `send` | **500**, `QueryException 25P02` *"transaction is aborted"* |

**`25P02` was a decoy.** `dispatch()` wraps its insert in `retry(2, …)`: the *first* insert failed and aborted the transaction; the retry could then only report the abort. **The retry masked a total feature outage.**

**The real error, proven by direct insert:**

```
SQLSTATE[22P02]: invalid input syntax for type bigint: "d2556557-…"
```

`NewsletterService::dispatch()` inserted `'id' => Str::uuid()` into `newsletter_recipients.id`, which is **`bigint DEFAULT nextval(...)`**. `NewsletterRecipient` is a plain `Model` — no `HasUuids`, no `$keyType`. **Schema and model agreed; only `dispatch()` disagreed.** So **no newsletter could ever be sent, in production either** — the two "pre-existing failing tests" had been reporting a real outage all along.

**Fix:** drop the `'id'` key; the sequence assigns it. **All five newsletter suites green: 25 passed, 45 assertions.**

**Regression check across everything touched today:** 26 passed, 2 failed — the same two `DashboardResolverElectionPriorityTest` failures that pre-date all of this work and belong to `PBDIGIT-59`'s semantics.

### Judgement worth keeping

**Two "obvious" hypotheses were wrong, and both were killed by measurement rather than argument:** the `NULL` audience_type (an ORM artifact, not data) and the fixture (correct all along). **The instruction to assert the query directly before touching either side is what made that cheap** — a fixture edit would have "fixed" nothing while hiding a production outage.

### Recorded, not fixed

`retry()` around a statement inside `DB::transaction()` can only ever surface `25P02` once the first attempt fails — it converts a precise error into an opaque one. Worth auditing wherever else that pattern appears.

### PBDIGIT-62 — the exclusion that fails open

```php
Election::withoutGlobalScopes()                       // Election's scopes removed
    ->whereDoesntHave('voterSlugs', fn ($q) => …)     // subquery on VoterSlug — tenant scope STILL applied
```

`VoterSlug` and `ElectionMembership` both carry `tenant`. `BelongsToTenant` **does not no-op without context** — it falls back to the *platform* org id, so the subquery matches nothing, `whereDoesntHave` is trivially true, and **the already-voted exclusion never fires at login**. Both entry-resolution consumers have the hole.

**The code comments prove the author knew the hazard** — *"bypasses BelongsToTenant which requires session context — not set yet when DashboardResolver runs at login time"* — and defeated it **only on the outer query**.

**Consequence: a voter who has already voted is routed back to the ballot after login.**

**Generalisation recorded in the ticket:** `withoutGlobalScopes()` does not reach relationship subqueries, and a scoped-to-nothing `whereDoesntHave` **fails open** — the guard silently permits. Worth auditing every `withoutGlobalScopes()` + `whereHas`/`whereDoesntHave` pair over a tenant-scoped model.

## PBDIGIT-62 repaired (authorised, bounded)

**Reproduced in the generated SQL first:** with no tenant context the subquery carried `and "election_memberships"."organisation_id" is null`, so `not exists (…)` was always true — **the guard failed open**.

**Fix — two closures in `User.php`:** `$query->withoutGlobalScope('tenant')`. **Deliberately narrower than the authorisation's sketch**, which used `withoutGlobalScopes()`: the blanket form also drops `SoftDeletingScope`, which would make a **soft-deleted slug count as a vote**. Only `tenant` is lifted, and only inside these two subqueries.

**Why that is not a hole:** login-time resolution is *intentionally* cross-tenant — the outer query already declares it. **An exclusion must be evaluated in the same span as the set it excludes from.**

**Tests:** new `test_already_voted_is_excluded_when_no_tenant_context_is_set` pins the login-time condition, records the vote on **both** representations, and asserts a **positive control first** so it cannot pass for the wrong reason. **Proven RED against pre-fix code**, GREEN after.

## Eligibility failure investigation (read-only) — cluster cleared, and my own count corrected

**First, a correction to my own assessment: it is 8 tests, not 16.** The 16 were exception *mentions* — PHPUnit prints each failure twice (the `FAILED` header and the `➜ throw` line). **8 FAILED lines, 8 throw lines, one test class, one throw site.** I had escalated this as the estate's highest risk partly on an inflated number; the estate assessment has been corrected in place.

**Conclusion: fixture failures, not a production defect — the opposite of `PBDIGIT-62`, and established by tracing rather than assumed.**

Call path: `AssignVoterHandler:58` → `VoterEligibilityPolicy` (Domain interface) → `EloquentVoterEligibilityQueryService` (bound `AppServiceProvider:141`) → `FullMembershipPolicy::decideForContext()`, which requires:

```php
$context->isActive && !$context->isDeleted
    && membershipStatus === 'active'
    && feesStatus ∈ ['paid','exempt']
```

The org factory defaults `uses_full_membership => true`, so full-membership mode applies — and the fixture creates an `OrganisationUser` but **no `members` row at all**. Both required attributes are null, so eligibility is **correctly refused**. The production rule is right.

**Trap recorded for whoever repairs it:** other fixtures in this repo create members with `fees_status => 'unpaid'`, which is *also* ineligible under this rule — copying an existing member fixture would fail for a second, different reason.

**Authority: partially resolved.** Assignment-time eligibility has one coherent authority (interface in Domain, Eloquent adapter, two policies chosen by `VoterSourceStrategy`). Whether *voting-time* eligibility shares it remains the open `PBDIGIT-49`/MB-5 question — **untouched, and not mine to settle** (`R-34`).

**Business rule worth PO awareness (not a defect):** fees status gates voter assignment — a member in arrears cannot be assigned as a voter.

## Eligibility fixture repair — one line, and the fixture told us which line

**Authorised as a fixture-only step.** Before editing, checked the intended `VoterSourceStrategy` per test rather than assuming the factory default — and the fixture answered the question itself.

**The setUp comment reads: `// For election-only mode tests, also add to organisation_users`.** The author intended **election-only** and built exactly the right fixture for it (an active `organisation_users` row, no member records — which is precisely what `ElectionOnlyPolicy` requires: `isImportedVoterRegistry && isActive && !isDeleted`). The bulk tests do the same for their extra users. **The fixture was internally consistent and complete for the mode it meant.**

What broke it: `Organisation::factory()` defaults `uses_full_membership => true`, so `VoterSourceStrategy::fromOrganisation()` returned `MembershipRegistry`, and eligibility correctly demanded an active member with paid/exempt fees. **The intent and the mode disagreed — the fixture was never wrong for its own scenario.**

**Repair:** state the mode explicitly instead of inheriting a factory default —

```php
Organisation::factory()->create(['uses_full_membership' => false]);
```

**This is why the trap mattered:** adding `Member` rows (the other repair) would have *also* gone green while silently converting eight election-only persistence tests into full-membership tests, coupling them to fees governance they were never about.
