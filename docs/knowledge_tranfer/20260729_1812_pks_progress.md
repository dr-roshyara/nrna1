# The PKS — Final Documentation (Updated)

## Executive Summary

The Product Knowledge System (PKS) is a knowledge system that models engineering knowledge, governance, evidence, and their relationships. One of its primary capabilities is providing AI with deterministic guidance about which engineering artifacts to produce, when to produce them, where to store them, how to structure them, and how to verify them.

This document presents the **complete, governed, evidence-based** understanding of the PKS based on the completed:

- **Phase I — Strategic Discovery** (2026-07-27)
- **Phase II.A — Strategic Modeling** (M0-M8, complete)
- **Phase II.B — Architecture Definition** (AD-1, complete)
- **Phase II.C — C4 Views** (C4-1/C4-2, complete)

The architectural interpretation is **evidence-backed, governed, and certified** under the PKS methodology.

## 1. What the PKS Is

### 1.1 Core Definition

> **The PKS is a knowledge system that models engineering knowledge, governance, evidence, and their relationships. One of its primary capabilities is providing AI with deterministic guidance about which engineering artifacts to produce, when to produce them, where to store them, how to structure them, and how to verify them.**

### 1.2 What the PKS Is NOT

| Misconception | Correction |
|---------------|------------|
| The PKS is a documentation system | ❌ No — documentation is one capability |
| The PKS is software | ❌ No — it is knowledge specifications (YAML + Markdown) |
| The PKS is an instruction manual for AI | ❌ No — AI guidance is one application |
| The PKS is only about documentation | ❌ No — it models knowledge, governance, evidence, and more |

### 1.3 Why This Distinction Matters

If the PKS were defined only as a documentation instruction system, it would be too narrow to support the broader needs of engineering knowledge management. The completed work indicates a more fundamental architecture:

| Aspect | Documentation-Focused View | Knowledge System View |
|--------|---------------------------|----------------------|
| Primary concern | What documents to produce | What knowledge exists and how it relates |
| Core concepts | ADR, Guide, Log, Report | Decision, Rule, Finding, Observation, Verdict |
| Relationships | Document dependencies | Concept relationships (supersedes, drives, traces) |
| Lifecycle | Document states | Concept lifecycle states |
| Governance | Document approval | Knowledge governance |
| AI guidance | What to write | How to understand and act |

## 2. The PKS Architecture (Complete)

### 2.1 The Three Layers

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    PKS — Three Layers                                       │
│                                                                              │
│  Layer 1: Knowledge Model (The Semantics)                                   │
│  └── Concepts: Decision, Rule, Finding, Observation, Verdict, etc.         │
│  └── Relationships: supersedes, drives, traces, justifies, etc.            │
│  └── Lifecycle: 3-class structure (pre-authority → authoritative → terminal)│
│  └── Evidence: Citations, provenance, epistemic classes                    │
│                                                                              │
│  Layer 2: Representation (How It Is Stored)                                 │
│  └── Internal model: concepts.yaml, relationships.yaml, lifecycles.yaml    │
│  └── Machine-readable: YAML/JSON                                           │
│  └── Human-readable: Markdown                                              │
│                                                                              │
│  Layer 3: Presentation (How It Is Exposed)                                  │
│  └── ADR (Decision → Markdown)                                              │
│  └── Guide (Knowledge → Markdown)                                           │
│  └── Session Log (Observations → Markdown)                                 │
│  └── Verification Report (Verdicts → Markdown)                             │
│  └── YAML → AI tools (Claude Code, etc.)                                   │
└─────────────────────────────────────────────────────────────────────────────┘
```

**The primary modeling concern is the knowledge represented by the documents. The documents remain important governed artifacts through which that knowledge is recorded, reviewed, and communicated.**

## 7. Key Architectural Principles

### 7.1 Knowledge Before Documentation

> **The primary modeling concern is the knowledge represented by the documents. The documents remain important governed artifacts through which that knowledge is recorded, reviewed, and communicated.**

### 7.2 Evidence Before Architecture

> **No concept is promoted without operational evidence. All decisions are evidence-backed.**

### 7.3 Governance Before Implementation

> **No decision is final without human approval. AI surfaces governance questions; it does not resolve them.**

### 7.4 Reversibility

> **Every modeling decision should be explainable months later. Rejected concepts remain part of project memory with rejection rationale.**

### 7.5 Separation of Concerns

> **Knowledge is not the same as documentation. Domain is not the same as capability. Analysis is not the same as design.**

### 7.6 Visual Precision ≤ Architectural Precision

> **Representations never exceed the precision of the architecture they render. Silence is an architectural decision.**
