## 0. The collision — the folder's own event model is the anti-pattern

The input warns:

> *"Do not use one vague event such as `KnowledgeUpdated` for all of these."*

Measured in the folder, `20260815_1615_target_architecture.md` §10 *Event-driven evolution*:

```
DecisionApproved  →  KnowledgeUpdated  →  ProjectionGenerated  →  AIContextRefreshed
```

**`KnowledgeUpdated` is verbatim the vague event the input names.** The folder proposed it as its event model; the input, arriving independently, identifies that exact shape as the failure mode.

Why it matters beyond style: `KnowledgeUpdated` carries no aggregate identity, no version, and no domain fact. Every handler subscribing to it must re-derive what actually happened — which means each handler embeds its own interpretation of a change it cannot see. That is `P-7` violated by construction: **many independent interpretations of one event.** The corpus already knows this failure (`how_to_work_with_sessions` §11: *"there must not be two independent interpretations of the same authoritative workflow record"*).

**Ruling: the folder's four-event chain is superseded.** Events are named for the domain fact that occurred:

```
RuleActivated · ConflictAnalysisRequested · ConflictAnalysisCompleted · ConflictDetected
```

And the input's accompanying rule is adopted: **an event must not imply that downstream analysis is complete.** `RuleActivated` says a rule activated. It does not say the system is consistent.

## 1. Placement

Adopted:

```
Application service          loads · invokes · commits
        │
   Aggregate                 raises the event — it knows the domain fact
        │
   after commit
        ▼
   Dispatcher → handlers     reactions · analysis · audit · projections
```

Two constraints, both already corpus rules reached independently:

- **The aggregate raises; it does not publish.** No Kafka, no projection call, no audit write, no knowledge of handlers. This is `ALLOC-1`'s coordination boundary — now stated a seventh time.
- **Publication follows commit.** An event announcing a state change that did not commit is a false record — `INV-A1`, *a report of an act is not the act*, in its sharpest form.

---

## 2. The binding rule — an event may not enforce an invariant

The input's most valuable single ruling:

> *"Do not use an event to enforce a local invariant… Events represent facts after valid state transitions. They are not deferred validation hooks for conditions that must hold atomically."*

**Adopted as binding, because it directly protects the matrix.**

`..._1023` classifies 32 invariants by `atomicity`. An `ATOMICALLY_REQUIRED` condition checked in an event handler has been moved **outside the atomic boundary** — the state committed, the event fired, and the handler discovers the violation afterwards. The row still says `ATOMICALLY_REQUIRED`; the implementation is eventually consistent. Nothing in the matrix would detect the drift.

> **`EVT-1`** — No handler may evaluate an invariant whose `atomicity` is `ATOMICALLY_REQUIRED` or `SAME_CONTEXT_TRANSACTION`. Handlers act on facts; they do not validate them.

The corollary is the useful half: **`EVT-1` makes the matrix's `atomicity` column mechanically meaningful.** A row's classification now determines where its check may legally live.

---

## 3. Four categories — the elaboration `..._0922` §11 asked for

| Category | Purpose | Contract |
|---|---|---|
| **Domain event** | An internal fact in the ubiquitous language | Internal; may carry rich domain references |
| **Domain-event notification** | In-process dispatch mechanism | Implementation detail; **not** a public contract |
| **Integration event** | Crosses a context or system boundary | **Published language** — versioned, deliberately smaller |
| **Audit event** | Accountability record | Actor · policy version · request id · provenance · integrity |

`..._0922` §11 listed *"domain state · domain events · audit events · provenance records · projection build records"* as five things to keep apart, without saying how they differ. This supplies it, and adds the notification/integration split the corpus lacked.

**The audit distinction is the one that matters most here**, and the input states it correctly:

> *"An audit event may be generated from a domain event but is not identical to it."*

This is `INV-A1` at the event layer, and it closes the loop with `..._0922` §9: an audit event *records that something happened*; it does not own the transition. A system that treats its domain event stream as its audit trail has made the report into the act.

**Integration events must not leak the internal model.** `EngineeringRuleActivatedV1` is a published-language contract; `RuleActivated` is not. This is `AD-1`'s `AP-8` — *the outbound surface is narrower than the internal vocabulary* — reappearing at the event boundary, independently.

## 4. Payload — the version fields are the pin

The proposed payload carries `aggregate_version`, `rule_version: "R-001@7"`, `causation_id` and `correlation_id`.

**`rule_version` is `reconstructable_as_of` in event form.** `..._1023` §4 found nine matrix invariants that cannot be transactionally enforced and must pin a referent version; `..._1034` §2 extended pinning to `policy_version`. The input arrives at the same notation from the event side. **Third independent arrival at pinning.**

**`causation_id` and `correlation_id` are new**, and they supply exactly what `..._0922` §11 required of an audit stream — *"events remain **ordered, correlated**, integrity-protected, and linked to source state"* — a requirement stated with no mechanism until now.

Adopted, with the corpus's own addition: **`authored_by` travels on the event** (v3 §5.3). An event that loses provenance hands every downstream handler material it cannot classify.

And the input's structural rule is adopted: *"prefer references and version identifiers over embedding the entire aggregate"* — which is `..._0922` §1's reference-by-identity rule, restated at the event boundary.

## 5. The activation flow — and the first input to get this structurally right

Every prior input ended its activation flow at *allow / block / review*, and `..._1023` §6.3, `..._1029` §6 and `..._1034` §4 each corrected it: **a mechanism that emits *allowed* has granted authority.**

This input reaches the same terminal phrasing — *"application service decides: allow / block / review"* — **but its code does not.** It writes:

```python
rule.activate(command.approval_reference)
```

and its event table places `RuleApproved` as *"raised by Approval / governance process."*

**That is correct, and it is the first input to model it correctly.** The handler is not approving. It is *executing against an already-recorded human approval*, and `approval_reference` is the record of that act. Approval and activation are two operations by two actors — precisely v3 §10's *"creation and authority are different operations."*

**Refined ruling, replacing the flat correction:**

> An application service may **refuse**, and may **execute an approval already recorded**. It may not **approve**. The presence of `approval_reference` as a required parameter of `activate()` is what makes the call legitimate — and `INV-RULE-002` (*no active rule without an authority reference*) is exactly this invariant seen from the aggregate.

The prose should follow the code: *allow* → **`PROCEED_ON_RECORDED_APPROVAL`**.

**And the input frames `OQ-24` better than the register did:**

```
HARD      analysis runs before RuleActivated  — a pre-commit gate
ADVISORY  RuleActivated fires, then ConflictDetected arrives asynchronously
```

The event model makes the choice concrete: it is not a policy preference, it is **whether `ConflictDetected` can arrive after a rule is already active.** That is a business question with a visible consequence, which is what `OQ-24` needed.

## 11. Bottom line

Three findings, in order of weight:

**The folder's own event model was the anti-pattern.** `KnowledgeUpdated` forces every handler to re-derive what happened, which is many independent interpretations of one fact — the failure `how_to_work_with_sessions` §11 named as the reason `AST-016` delegates rather than reproduces. Superseded.

**`EVT-1` makes the matrix's `atomicity` column enforceable.** An `ATOMICALLY_REQUIRED` invariant checked in a handler has silently become eventually consistent, and nothing in the matrix would catch it. The classification now determines where a check may live.

**The activation correction is refined rather than repeated.** Four inputs ended at *allow*; this one's **code** is right where its prose is not. `rule.activate(approval_reference)` executes a human act already recorded — it does not grant one. That is the shape the corpus has been looking for since v3 §9, and it arrived as a function signature rather than an argument.

## 12. Addendum — Transactional Outbox (input, 2026-08-16 10:50)

Filed here rather than as a tenth document: delivery is the continuation of the event layer, and the material is heavily blocked (§12.0), so a separate artifact would be disproportionate. External citations (`axonops.com`, `zylos.ai`, `nilus.be`) recorded as unverified input.

### 12.0 Scope — this is the most `OQ-1`-dependent input received

Measured by content: `CREATE TABLE outbox_messages`, `TIMESTAMPTZ`, `JSONB`, `FOR UPDATE SKIP LOCKED`, a polling relay, an inbox table, four background workers, broker topics, dead-letter queues, and *"one PostgreSQL transaction"* as the V1 recommendation.

**Roughly nine-tenths of this input presupposes that the answer to `OQ-1` is "software with a relational database."** It is not rejected; it is **unadjudicable until a human decides**, exactly as `..._0922` §13 Part B and `..._1029` §11.6 already are.

What follows is only what survives either answer.

### 12.1 Under specifications, the commit log *is* the outbox

The pattern's purpose is stated precisely and is technology-independent:

> *"This avoids the dual-write failure where the database succeeds but the broker publish fails, or vice versa."*

**The problem is real in both worlds. The solution is already present in one of them.**

`..._0922` §3 established that if the PKS remains specifications, the atomic change unit is the **git commit** — and a commit is atomic across *all files simultaneously*. Therefore:

| Outbox mechanism | Equivalent under specifications |
|---|---|
| aggregate row + outbox row in one transaction | rule file + pending-notification file in **one commit** |
| `occurred_at` ordering | commit order |
| `aggregate_version` | commit SHA |
| `UNIQUE(aggregate_type, aggregate_id, aggregate_version, event_type)` | a commit touching one path once |
| durable-before-published | committed-before-consumed |

> **`EVT-2`** — Under a specifications representation there is no dual write, because there is no second store: **the commit log is the outbox.** The dual-write problem returns only when an external broker or database is introduced.

This is the third finding of this shape — after content hashing (`..._0922` §3) and analysis snapshots (`..._1029` §11.1) — and it strengthens the same conclusion each time: **the machinery `OQ-1`'s "software" answer would require is largely free under its "specifications" answer.** That is now a substantial argument, arrived at three times independently.

### 12.2 At-least-once and idempotency — adopted, technology-independent

> *"It does **not** guarantee exactly-once delivery… Therefore every consumer must be idempotent."*

**Adopted as a domain rule, not an implementation note.** Any asynchronous delivery may duplicate; the requirement on consumers follows from that alone and holds under git polling as much as under Kafka.

> **`EVT-3`** — Every event consumer is idempotent. Reprocessing a delivered event produces no additional effect.

It composes with two existing rows: `INV-ANL-010` (identical inputs yield an identical result) and `INV-PRJ-001` (a projection identifies its source snapshot). **A projection rebuilt from a pinned snapshot is idempotent by construction** — which is the cheapest possible satisfaction of `EVT-3`, and another consequence of the pinning discipline.

### 12.3 Before-commit vs after-commit — reconciled with `EVT-1`

The input permits synchronous before-commit handlers *"when the reaction is part of the same business transaction"*, with the caution that *"handling other aggregates in the same transaction can enlarge the effective consistency boundary."*

**This needs reconciling with `EVT-1` (§2), and the reconciliation is a sharpening:**

> A before-commit handler may **react** within the same consistency boundary. It may never **validate** an `ATOMICALLY_REQUIRED` invariant — that check belongs to the aggregate, before the event exists at all.

The distinction is the same one §2 draws: an event is a fact *after* a valid transition. A before-commit handler that validates has turned the event into a deferred validation hook; one that reacts has not.

The after-commit list is adopted unchanged and matches the corpus row for row — graph projection, search index, AI context, audit enrichment, conflict re-analysis. All are `EVENTUALLY_CONSISTENT` or `ANALYTICAL` in the matrix; none is `ATOMICALLY_REQUIRED`. **The matrix's `atomicity` column already predicts this split**, which is a useful independent check on both.

### 12.4 The mapper rule — adopted

`RuleActivated` → `EngineeringRuleActivatedV1`, via an explicit translation that *"removes internal implementation details, adds schema version, selects the integration contract, attaches provenance references."*

**Adopted as the mechanism for §3's category boundary.** It is `AP-8` — *the outbound surface is narrower than the internal vocabulary* — implemented. The instruction *"do not persist a raw in-memory domain object blindly"* is the operative half: without a mapper the internal model leaks into a published contract and can no longer change.

### 12.5 A regression — and it is precisely locatable

`..._1044` §5 credited the previous input for being the first to model activation correctly:

```python
rule.activate(command.approval_reference)      # events input — from the COMMAND
```

This input writes:

```python
authority = self.authority.evaluate(actor=command.actor, rule=rule)
if not authority.allowed: raise RuleActivationDenied(authority.reasons)
rule.activate(approval_reference=authority.approval_reference)   # from the POLICY
```

**The approval reference has moved from the command to the policy's return value.** That is not a refactor. In the previous input the handler *executed an approval already recorded and supplied by the caller*; here the policy **mints** the approval reference during evaluation.

> A mechanism that produces the approval reference has granted the authority that reference is supposed to record. `INV-A1` — *a report of an act is not the act* — and v3 §9: the mechanism records authority, it never grants it.

`INV-RULE-002` (*no active rule without an authority reference*) is satisfied in both versions — which is exactly why this matters: **the invariant cannot detect the difference.** A reference exists either way. Only its *provenance* distinguishes a recorded human approval from one manufactured by the evaluator, and no row in the matrix currently checks provenance of an approval reference.

**New matrix row required** — recorded as `OQ-33`:

> `INV-RULE-011` — a rule's `approval_reference` resolves to a **recorded** approval act, not to a value produced during the activating transaction.

And `if not authority.allowed` is the **fifth** occurrence of `ALLOW`/`DENY`; the `..._1034` §4 vocabulary correction stands unchanged.

### 12.6 Negative rulings — adopted, third in the family

> *"Do not introduce Kafka, event sourcing, or distributed transactions merely to publish domain events."*

Joins `..._0922` §13 (*no microservices, event sourcing, or mandatory graph DB for V1*) and §6 above (*event sourcing not required*). **Three subtractive rulings, all consistent**, and all survive `OQ-1` in either direction — a "no" needs no technology to be true.

### 12.7 Blocked inventory

`outbox_messages` schema · `inbox_messages` · `audit_events` table · polling relay · CDC · row leasing (`SKIP LOCKED`) · backoff · dead-letter queues · the four background workers · *"one PostgreSQL transaction"*. **All `OQ-1`.**

Two rows of the failure table are domain-level and adopted: *authority denied → no activation event*, and *projection update fails → core knowledge remains committed; projection is stale and rebuildable* (which is `INV-PRJ-002` restated).

## 13. Addendum — Idempotent Consumers / Inbox (input, 2026-08-16 10:55)

External citations (`vabs.github.io`, `andrewaltimit.github.io`) recorded as unverified input. Filed here to keep the event layer — semantics, delivery, consumption — in one canonical place.

### 13.0 Scope, and a measurement worth stating plainly

This is the **third consecutive input on one layer**: events (§1–§11) → outbox (§12) → inbox (§13). All three are predominantly implementation, and all three sit inside `OQ-1`.

Measured across today's ten documents: **`OQ-1` is now referenced 49 times, and five documents carry an explicitly blocked section.**

`..._1040` §2 recorded `OQ-1` as **decidable today** — it needs no evidence, no analysis, and no further input; the corpus has simply never been asked whether the PKS is software. Every input since has deepened the design that depends on the answer without moving the answer.

That is not a criticism of the inputs, which are good. It is the register's finding restated with a larger number: **design is accumulating faster than the decision it rests on.**

### 13.1 The unsafe pattern — adopted, and it generalizes

```python
if not inbox.exists(message_id):     # two workers both see "not present"
    apply_effect()
    inbox.insert(message_id)
```

> **`EVT-4`** — Deduplication state and the business effect commit together. A check performed *before* an effect is not deduplication; it is a race.

This is technology-independent and it is the same defect shape as `..._1023` §4's cross-aggregate problem: **a condition read at one instant and acted on at another, with no guarantee it still holds.** The corpus has now met it twice, in unrelated layers.

### 13.2 The idempotency key is the pin — fourth arrival

The proposed hierarchy:

```
message_id  ·  operation_id  ·  aggregate_id + aggregate_version  ·  business key
```

with the governing rule:

> *"The key must be produced from the event or business operation, not generated when the consumer receives it."*

**Adopted.** And the worked keys are pins: `rule_id + rule_version` · `projection_type + source_snapshot_id` · `rule_set_snapshot + analyzer_version + applicability_context_hash`.

That last one is `AnalysisRun`'s identity from `..._1023` §4.3, reconstructed independently as a deduplication key. **Pinning has now arrived from four directions** — invariant checking, policy versioning, event payloads, and idempotency keys. Each time the same conclusion: *identity must include the version of what was read.*

### 13.3 Version-aware consumers implement `INV-PRJ-001`

```
current 7, incoming 6 → stale, ignore
current 7, incoming 7 → duplicate, ignore
current 7, incoming 8 → apply
```

**Adopted.** This is `INV-PRJ-001` (*a published projection identifies the source snapshot it was built from*) made operational: the recorded `source_version` is what makes both duplicate and out-of-order delivery detectable with one comparison.

And the accompanying caution is adopted as a rule: **do not assume ordering unless the contract guarantees it.** Under `INV-A3`, an unordered stream is not a defect to be assumed away — it is a fact consumers must handle.

### 13.4 Naturally idempotent effects — free under specifications

> *"A consumer is safer when it uses state replacement or upsert rather than additive updates."*

**Adopted as the preferred design**, and it composes with `EVT-2` (§12.1): if the PKS remains specifications, **a projection rebuilt from a pinned snapshot is naturally idempotent** — rebuilding twice from commit `abc123` yields the identical artifact. There is nothing to deduplicate.

**Consequence worth stating:** under the specifications answer to `OQ-1`, the inbox table is largely unnecessary, because the effects are replacement rather than accumulation. Under the database answer it is required. **This is the fourth finding of that shape**, after content hashing, analysis snapshots, and the outbox — and the pattern is now consistent enough to be a genuine input to `OQ-1` rather than an aside.

### 13.5 The strongest convergence in this input

> *"Never assume that a timeout means the operation did not happen."*

**This is `INV-A3` — *absence is never permission* — in the delivery domain.** The corpus derived that invariant from authority: no assignment, no grant, no START, no readable record ⇒ **STOP · REPORT · ESCALATE**, never proceed. The input derives the identical rule from distributed systems: absence of a success response is not evidence of non-occurrence.

Two unrelated domains, one epistemic rule: **absence of a record is not a fact about the world.** Reconciliation — query the provider before retrying — is the delivery-layer form of *resolve the record, do not infer from silence*.

### 13.6 Retention is an authority concern, not an operational one

The input recommends permanent records for `RuleActivated` · `ExceptionGranted` · `ConflictResolved` · `EvidenceVerified` · `DecisionApproved`, and consumer-specific retention rather than one global TTL.

**Adopted — and the corpus supplies an invariant behind it that the input does not state.**

`INV-EXC-003` requires that an exception's validity not exceed its approver's authority, and `..._1023` §4 showed that this is checkable later **only if the approving grant's version was pinned**. If the record carrying that pin is aged out by a TTL, the question *"was this exception validly approved?"* becomes permanently unanswerable.

> **`EVT-5`** — Retention for governance-critical events is bounded by **reconstructability**, not by operational convenience. A record whose deletion would make a recorded authority act unverifiable is permanent.

That converts retention from an ops policy into a governance one for exactly the five event types the input names — which is the right list, reached from the wrong reason.

### 13.7 Blocked, and not adopted

**`OQ-1`:** `inbox_messages` DDL · `PRIMARY KEY (consumer_name, message_id)` · `ON CONFLICT DO NOTHING` · leases and `locked_until` · the six inbox states · dead-letter queues · the four-table PostgreSQL layout · the observability metric set.

**Illustrative only:** the `payment_provider.charge` example — different domain, recorded so it is not mistaken for EKS vocabulary, as with the shipment and patient examples in `..._1034` §9.

**Confirmatory:** `QUARANTINED` matches the matrix's `failure_behavior: QUARANTINE`; the inbox/outbox pairing matches §12.
