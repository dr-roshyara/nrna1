# The PKS: A Knowledge System for Engineering

---

## Executive Summary

The Product Knowledge System (PKS) is a knowledge system that models engineering knowledge, governance, evidence, and their relationships. One of its primary capabilities is providing AI with deterministic guidance about which engineering artifacts to produce, when to produce them, where to store them, how to structure them, and how to verify them.

This document presents the current understanding of the PKS based on the completed Strategic Discovery (Phase I) and the Strategic Modeling work in progress (Phase II.A). The architectural interpretation is evidence-based and subject to refinement as Strategic Modeling progresses.

---

## 1. What the PKS Is

### 1.1 Core Definition

> **The PKS is a knowledge system that models engineering knowledge, governance, evidence, and their relationships. One of its primary capabilities is providing AI with deterministic guidance about which engineering artifacts to produce, when to produce them, where to store them, how to structure them, and how to verify them.**

### 1.2 What the PKS Is NOT

| Misconception | Correction |
|---------------|------------|
| The PKS is a documentation system | ❌ No — documentation is one capability |
| The PKS is software | ❌ No — it is knowledge specifications (YAML + Markdown) |
| The PKS is an instruction manual for AI | ❌ No — AI guidance is one application |
| The PKS is only about documentation | ❌ No — it models knowledge, governance, evidence, and more |

### 1.3 Why This Distinction Matters

If the PKS were defined only as a documentation instruction system, it would be too narrow to support the broader needs of engineering knowledge management. The current Strategic Modeling work indicates a more fundamental architecture:

| Aspect | Documentation-Focused View | Knowledge System View |
|--------|---------------------------|----------------------|
| Primary concern | What documents to produce | What knowledge exists and how it relates |
| Core concepts | ADR, Guide, Log, Report | Decision, Rule, Finding, Observation, Verdict |
| Relationships | Document dependencies | Concept relationships (supersedes, drives, traces) |
| Lifecycle | Document states | Concept lifecycle states |
| Governance | Document approval | Knowledge governance |
| AI guidance | What to write | How to understand and act |

## 2. The PKS Architecture (Current Understanding)

Based on the current Strategic Modeling work, one plausible architectural interpretation is a layered structure:

### 2.1 The Three Layers

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    PKS — Three Layers                                       │
│                                                                              │
│  Layer 1: Knowledge Model (The Semantics)                                   │
│  └── Concepts: Decision, Rule, Finding, Observation, Verdict, etc.         │
│  └── Relationships: supersedes, drives, traces, justifies, etc.            │
│  └── Lifecycle: Draft → Proposed → Approved → Deprecated → Archived        │
│  └── Evidence: Citations, provenance                                       │
│                                                                              │
│  Layer 2: Representation (How It Is Stored)                                 │
│  └── Internal model: concepts.yaml, relationships.yaml, lifecycles.yaml    │
│  └── Machine-readable: YAML/JSON                                           │
│  └── Human-readable: Markdown                                              │
│                                                                              │
│  Layer 3: Presentation (How It Is Exposed)                                  │
│  └── ADR (Decision → Markdown)                                              │
│  └── Guide (Knowledge → Markdown)                                           │
│  └── Session Log (Observations → Markdown)                                 │
│  └── Verification Report (Verdicts → Markdown)                             │
│  └── YAML → AI tools (Claude Code, etc.)                                   │
└─────────────────────────────────────────────────────────────────────────────┘
```

**The primary modeling concern is the knowledge represented by the documents. The documents remain important governed artifacts through which that knowledge is recorded, reviewed, and communicated.**

### 2.2 The PKS Models

Based on the current evidence, the PKS appears to include the following models:

| Model | What It Models | Status |
|-------|----------------|--------|
| **Knowledge Model** | Concepts, relationships, lifecycles | In progress (M0-M4) |
| **Governance Model** | Approvals, boundaries, authority | In progress (OQ routing) |
| **Evidence Model** | Citations, provenance, confidence | In progress (M1) |
| **Artifact Model** | Documents as governed artifacts | Future |
| **Process Model** | Workflows, gates, reviews | Future |
| **AI Guidance Services** | What, when, where, how, verify | Derived from above |

If the PKS evolves as the current strategic model suggests, the Artifact Model and AI Guidance Services naturally become projections of the underlying knowledge model.

## 3. The Knowledge Concepts

### 3.1 Concepts Identified (17 Operating Concepts)

The evidence discovery identified 17 operating concepts in the repository:

| # | Concept | Definition |
|---|---------|------------|
| G-1 | **Decision** | A selection among alternatives under explicit trade-offs |
| G-2 | **Rule** | A binding behavioral norm with a single canonical home |
| G-3 | **Invariant** | A condition that must always hold; violation is a defect |
| G-4 | **Ruling** | A recorded governance act by an authority |
| G-5 | **Finding** | An evidenced defect/observation raised by a review or audit |
| G-6 | **Question** | An owned, routed unknown whose lifecycle outlives its carrier |
| G-7 | **Term** | A ubiquitous-language entry; changes are first-class governed events |
| G-8 | **Contract** | A versioned specification of expectations at a boundary |
| G-9 | **Model Element** | A named element of a governed model |
| G-10 | **Observation** | A factually captured evidence entry |
| G-11 | **Risk** | An identified potential harm with a register lifecycle |
| G-12 | **Candidate** | A knowledge item holding probationary status |
| G-13 | **Work Item** | A unit of work with lifecycle ≠ progress |
| G-14 | **Guide Step** | A teaching unit, one step per file, ordered |
| G-15 | **Verdict** | The outcome of evaluating evidence against a criterion |
| G-16 | **Exception Record** | A recorded, approved deviation |
| G-17 | **Charter Grant** | An authorization permitting a named next activity |

### 3.2 What These Concepts Represent

These concepts represent the **knowledge** — the semantics of the domain. They are independent of any particular document that records them.

**The document is not the primary thing. The knowledge is.**

### 3.3 Relationship Between Knowledge and Documents

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Knowledge → Documents                                    │
│                                                                              │
│  Knowledge (Semantics)     →    Document (Projection)                       │
│  ───────────────────────        ─────────────────────                       │
│  Decision                      →    ADR                                     │
│  Observation                   →    Session Log                             │
│  Verdict                       →    Verification Report                     │
│  Knowledge                     →    Guide                                   │
│  Finding + Risk                →    Retrospective                           │
│  Term                          →    Glossary                                │
│  Rule                          →    Policy Document                         │
│  Contract                      →    API Specification                       │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 5. What the PKS Is Not (Reinforced)

### 5.1 The PKS Is Not Software

The PKS is knowledge specifications (YAML + Markdown). It does not require PHP, Python, or any other programming language. AI tools consume the specifications directly.

### 5.2 The PKS Is Not Just Documentation Instructions

Documentation guidance is one capability of the PKS, not the PKS itself. The broader PKS models knowledge, governance, evidence, and their relationships.

### 5.3 The PKS Is Not a Finished Product

Strategic Modeling is still in progress. The architectural interpretation presented here is based on current evidence and subject to refinement as later work (M2-M8) introduces new concepts or relationships.

## 7. Key Architectural Principles

### 7.1 Knowledge Before Documentation

> **The primary modeling concern is the knowledge represented by the documents. The documents remain important governed artifacts through which that knowledge is recorded, reviewed, and communicated.**

### 7.2 Evidence Before Architecture

> **No concept is promoted without operational evidence. All decisions are evidence-backed.**

### 7.3 Governance Before Implementation

> **No decision is final without human approval. AI surfaces governance questions; it does not resolve them.**

### 7.4 Reversibility

> **Every modeling decision should be explainable months later. Rejected concepts remain part of project memory with rejection rationale.**

### 7.5 Separation of Concerns

> **Knowledge is not the same as documentation. Domain is not the same as capability. Analysis is not the same as design.**
