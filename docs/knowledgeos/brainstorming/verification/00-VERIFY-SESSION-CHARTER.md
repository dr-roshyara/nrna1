## 1. Mandate

> *"You are not the author of the KnowledgeOS theory. You are its adversary. Your success criterion is finding errors, missing assumptions, invalid derivations, counterexamples and statistical weaknesses — not confirming the theory."*

The verification target is the **Candidate KnowledgeOS Theory (CKT)** — wherever it exists in the corpus (book + mathematical documents + research artifacts + architecture artifacts + executable witnesses). The book (Edition 2) is **one representation** of the theory, not the truth source.

### What this session does NOT do

- Does not edit Edition 2 or any theory/architecture artifact (findings only; amendment is a separate human-authorized act).
- Does not "repair" the theory while verifying it (no hindsight contamination).
- Does not reason backward from implementation to theory ("the software does X, therefore the theory says X" is forbidden).
- Does not adjudicate. Findings → human disposition → research → authorized amendment.
- Does not claim authority: *"Theory authority = none until ratified."*

## 2. Verification levels (fixed hierarchy)

| Level | Question | Verdict vocabulary |
|---|---|---|
| **1 — Semantic/theoretical validity** | Does the theory make mathematical & statistical sense? | VALID / CONDITIONALLY VALID / INCONSISTENT / UNDER-SPECIFIED / OPEN / REFUTED |
| **2 — Computational validity** | Can the theory actually be computed? | (entered only after Level 1 sufficiently resolved) |
| **3 — Efficiency & accuracy** | Can it be improved *without changing semantics*? | (optimization must not alter semantics) |
| **4 — Architectural realization** | Does the architecture faithfully implement the verified theory? | ARCHITECTURALLY CONFORMANT (or not) |

Direction of verification: **Theory → Architecture → Implementation** — never the reverse.

## 3. Proposition status vocabulary (from mandate §9)

| Status | Meaning |
|---|---|
| **RECONSTRUCTED** | What the historical/material record supports |
| **THEORETICALLY SOUND** | Level-1 mathematical audit passed |
| **COMPUTATIONALLY SOUND** | Level-2 computational audit passed |
| **OPTIMIZED / VERIFIED** | Level-3 refinement survived without semantic degradation |
| **ARCHITECTURALLY CONFORMANT** | Architecture status (separate axis) |

Guard: *"It is implemented, therefore it is mathematically true"* is an invalid inference and will itself be reported as a finding wherever the corpus commits it.

## 4. Evidence layers

```text
BOOK (exposition, derived representation)

ARCHITECTURE / IMPLEMENTATION (evidence of realization, never mathematical authority)

```

Historical truth and mathematical truth are kept rigorously separate.

## 5. Finding discipline (Master Mandate §11–§13)

- Finding IDs: **TV-F-nnn**. Each finding carries: claim under examination (quoted/precisely located) · source artifact · verification level (L1 Math / L1 Stat / L2 Comp / L3 Eff / L3 Acc / L4 Arch) · test performed · result (**PROVEN / DISPROVEN / CONDITIONALLY PROVEN / COMPUTATIONALLY SUPPORTED / UNDER-SPECIFIED / UNPROVEN / OPEN**) · severity (**BLOCKING / MAJOR / MINOR / OBSERVATION**) · counterexample where applicable · required disposition (never auto-repaired).
- **No silent repair (absolute):** false implication → record failure, don't substitute; undefined symbol → don't invent a definition; inconsistent invariant → don't weaken it; architecture/theory mismatch → don't alter architecture.
- **Evidence hierarchy:** A mathematical proof · B formal/model evidence · C computational evidence · D historical evidence · E interpretation. Never upgrade D→A or C→A without independent proof. Implementation is a *witness*, not a proof.
- **Falsifiability test (§14):** for every major proposition, formulate *what would make it false*; if that cannot be formulated, investigate whether the proposition is falsifiable at all.
- The strongest statement made must never exceed the strength of the available evidence. Do not seek confirmation; a negative result is a successful outcome.
