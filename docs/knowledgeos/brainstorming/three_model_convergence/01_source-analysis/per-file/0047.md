## What Is This Document About?
Distinguishes a **role model** (who may act) from a **workflow state machine** (what happens, in what
order), diagrams a full lifecycle from Governance → Architecture → Independent Verification →
Governance Routing → (repair or accept) → Human Acceptance → Implementation Authorization →
Implementation → Independent Verification → final Acceptance. Each of five responsibilities is given
a short operating contract (Governance: authority+lifecycle, not domain design or code;
Architecture: proposes, does not accept its own work; Implementation: cannot quietly redesign
architecture; Independent Verification: can say a model is unsupported/wrong/insufficient but "does
not supply the replacement architecture"; Governance Communication: a cross-cutting coordination
capability, explicitly *not* another architecture role, answering "who acts now / what is blocked /
what exact instruction goes next"). A separate, more mechanical workflow state machine is sketched
(CREATED → REGISTERED → HANDOFF → START → ACTIVE → {HANDOFF|STOP} → terminal
COMPLETE/CANCEL/SUPERSEDED), with the explicit rule drawn from operational history: **"a deliverable
being produced is not the same thing as its lifecycle being closed."**

The document proposes a four-layer reorganization (Authority → Governance → Workflow →
{Architecture, Implementation} → Verification → Human Acceptance), with Knowledge/Evidence and
Communication/Context named as cross-cutting concerns rather than layers. It closes with a five-item
gap list (role identity/provenance; knowledge evidence provenance/reproducibility; a communication

defects."
