## Why This Classification?
Designs a language-neutral architecture for computing the LCOM4 code-cohesion metric across
PHP/Java/Python source, separating language-specific extraction (bindings) from a common Fact

## What Is This Document About?
"Language-specific understanding, language-neutral calculation" — each language needs its own
parser/binding into a common L3 Fact Model, but only one LCOM4 calculation engine is needed. Recent
evidence is cited: a Python scanner failed trying to directly parse PHP syntax (heredoc, attributes,
interpolation, anonymous classes, etc.) — "the problem was not the LCOM4 formula; the problem was
that Python was trying to understand PHP," motivating the binding/engine separation. A staged
migration is recorded as a formal "future architectural direction" (not current scope): keep the PHP
calculator temporarily as a conformance reference, verify a future common engine's equivalence
against the conformance specification (not against the PHP calculator's output — "a future engine
that merely reproduces the PHP calculator's results would not satisfy this condition"), only then
retire it. The recorded direction deliberately generalizes away from naming Python as "the" future
engine, keeping the architectural commitment (one engine) separate from an unevaluated technology
choice.
