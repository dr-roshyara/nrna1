## What Is This Document About?

about documents *of* domain objects, not the objects themselves.

§2 classifies **three ontology layers**, explicitly declining a reviewer-proposed fourth: **L-A
Documentation** (exists, executable, lint-enforced — 31 types × 8 statuses × 5 authorities × 9

Product** (partially exists — `bounded-contexts.yaml` plus four unindexed catalogs). The declined
fourth layer is refused precisely: `knowledge-types.yaml` already covers engineering-knowledge
document kinds, so a separate "Engineering Knowledge Ontology" layer would name a distinction the

§3 delivers the document's sharpest result: **three independent proofs that D-1..D-7 cannot be
placed in the existing schemas**, one of them mechanically decisive rather than argued —
`bounded-contexts.yaml` **already contains a `governance` key**, defined as a *product* context
("Authority models, approval workflows, committee hierarchy," `code_path: app/Contexts/Governance").
Adding D-1 "Engineering Governance" as a platform-side concept would **collide with an existing key
in an enum `knowledge-lint` mechanically enforces** — a genuine, checkable, tool-verifiable
contradiction, not a modelling preference. Two further proofs (vocabulary insufficiency — no edge
type expresses `governs`/`produces`/`consumes`/`observes`; subject mismatch — `Engineering Method`
has no reviewer or code refs and cannot carry a knowledge card) corroborate but do not by themselves

§4 sharpens the PKS-as-projection question further than 0020/0036 left it: supporting evidence is
substantial and pre-existing (`authorities.yaml`'s `derived` rank; a typed `derived_from` edge;
