**TRIGGERED — DDD architectural boundary resolved.** Answers "should parsing belong inside KnowledgeOS?":
**yes, but** KnowledgeOS owns the **Semantic Reconstruction** capability while concrete parsing technologies
(C-type, Sanskrit-type) remain **replaceable implementation adapters**. Justification:
KnowledgeOS⊃SemanticReconstruction⊃Parsing — if parsing were external, an unowned gap would open exactly
where KnowledgeOS must understand intent. Rejects making "the parser" a domain object; places parser
implementations *under* an Inquiry/Semantic Reconstruction capability (Structural/Semantic-Role/Reference-
Resolution/Modality/Context) alongside a separate Knowledge Model. States the DDD rule explicitly: **"the
domain capability owns the contract; parsing technologies implement the contract."**

Explicitly uses this boundary to **protect the Sanskrit-lens research discipline** (continuing 0457's
self-correction): never "our parser is Sanskrit grammar," always "Sanskrit grammar provides one lens from
which we derive and test required capabilities." Boundary: KnowledgeOS owns Intent→SemanticRepresentation→
DimensionCandidates→Inquiry; parsers merely provide NaturalLanguage→Structural/SemanticRepresentation as
"replaceable analytical providers." Deeper justification: since Parsing≠DimensionDiscovery, the
orchestration (relevance reasoning, Zero gap-detection, Sārathi next-action decision) "cannot sensibly
belong to an external parser — it is the epistemic responsibility of KnowledgeOS." Formalizes:
**KnowledgeOS = SemanticReconstruction + DimensionDiscovery + EpistemicOperations + KnowledgeModel**, with
**Parser ∈ Implementation of SemanticReconstruction**. Explicitly defers the separate infrastructure
question (in-process/separate-service/external-model deployment) as subordinate to this ownership decision.
