## What Is This Document About?
Track 2 is characterized as deliberately outside the governed architecture lane — it "governs
nothing" until the current architecture baseline is reconstructed, verified and accepted, and Track
2's findings become architectural input only through ARB adoption. Its method is a **semantic chain**,
each step exposing what the next needed: **Rule → Authority → Scope → Applicability**.

**Step 1 (Rule)** distinguishes Rule from Decision, Recommendation, and Permission, and defines it
precisely: *"a standing, authoritative obligation governing behaviour within a defined scope and
period; a deviation is non-conformance unless an authorized exception permits it."* No Rule class is
built — the definition is explicitly semantic, not implementation.

**Step 2 (Authority)** finds, from 20 live grants, that every one traces to a human act, and states
the governing principle precisely: **"the mechanism records authority; it does not create
authority."** Five gaps are found and left open rather than resolved: authority has no temporal
ending; delegation is observed but not represented; ownership and authority are different; provenance
needs stronger immutable addressing; rule changes need to connect to the authority mechanism.

**Step 3 (Scope/Applicability)** is the document's sharpest content. Three distinct senses of "scope"
are separated — **subject scope** (what a Rule applies to), **authority scope** (what a person may
authorize), **evaluation scope** (what a checker actually inspected) — with an explicit prohibition
against conflating them. A ruling (SC-2) states: *"missing scope must not silently broaden a Rule,"*
and a candidate invariant is recorded verbatim: **`UNKNOWN ≠ DOES NOT APPLY` · `UNKNOWN ≠ EMPTY
SCOPE`.** A three-valued applicability model is given: `Specified → know it`, `Unspecified → cannot
determine`, `Not applicable → this dimension doesn't make sense for this subject`. A separate ruling
(SC-1) establishes four scope dimensions (System location, Environment, Artifact kind, Lifecycle
phase), with **Audience explicitly excluded** from applicability.

The document closes by naming what Track 2 deliberately does **not** decide (language, database,
aggregates, events, service decomposition, C4 Level 4, microservices — a long explicit exclusion
list) and by placing itself precisely in a governance diagram: Track 2 provides *candidate* semantic
input; the ARB adopts or rejects it; only then does it become a formal architecture work item.

## TIER 2 — DEEP ANALYSIS
**Trigger status: TRIGGERED** — states a **three-valued applicability logic** with a candidate
invariant that anticipates §19's Zero-Model discipline more precisely than anything read so far, and
supplies a **governance philosophy principle** (mechanism records, does not create, authority)

### Mathematical derivation
None formally, but the applicability construction deserves precise logical treatment:
```
applicability(rule, dimension) ∈ {SPECIFIED(value), UNSPECIFIED, NOT_APPLICABLE}

SPECIFIED(v)    — the dimension is known to have value v for this subject
UNSPECIFIED     — the dimension's value for this subject is not known
                  (NOT collapsible to "does not apply" or "empty scope")
NOT_APPLICABLE  — the dimension itself has no meaning for this subject
                  (a category-level fact, not a missing-data fact)
```
This is a genuine **three-valued classification**, and the document's explicit ruling —
*"unknown applicability must never be treated as non-applicability"* — states a **non-collapse
axiom** between two of the three values. This is structurally identical in *shape* to what §19 will
require: distinguishing unknown/unobserved from missing/impossible from absence-of-evidence. It is
**not proved as a formal system** here (no closure properties, no combination rules for multiple
dimensions), but it is the most precisely stated multi-valued epistemic-status construction in the
corpus to date.
