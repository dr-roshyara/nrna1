## 12 · Implementation relevance

### Kernel test
*Remove the separation rule.* Nothing breaks in software — **because it is not a capability.** It is a **decision rule about what to build**, and its entire value is exercised before anything is implemented.

### Decision
**PRESERVE AS KNOWLEDGE ONLY** — and this is the clearest case in the register where that verdict is the *strong* result rather than a consolation.

### Engineering consequence
None directly, and a large one indirectly: this rule is the instrument that disposes of `S1-F006`'s entire measurement stack (`S2-F021` → `DO NOT IMPLEMENT`), and it would dispose of any future entropy/metric/embedding proposal the same way. **Its function is to prevent implementation, not to require it.** A rule that reliably produces `DO NOT IMPLEMENT` verdicts is doing more engineering work than most features.

### What would be lost by not implementing
Nothing buildable. What would be lost by **not preserving** it is concrete: the corpus's standing defence against mathematically elegant proposals arriving as architecture — the `§14` failure mode, already observed once in this corpus (the complex-numbers proposal C responds to).

### Existing protection
⟨r4⟩ and the §16 altitudes cover specific instances. The **general rule** is not stated in law as a rule, and per §23 that is not an argument for adding it — it is an argument for keeping it as guidance.
