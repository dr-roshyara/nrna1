# EKS-39 — A central research object silently changed from a *test* into a *list*, and the programme's current blocker is the direct consequence

**Status:** **BACKLOG · SEMANTIC-DRIFT EXPOSURE** — registered from `P-91` (`docs/knowledgeos/theory-extraction/112-P91-…`). ⛔ **Not commissioned; activation requires a Human/PO-ARB authorization act.**
**Class:** operating-model problem — how a concept's *type* is allowed to change.
**Registered by:** Lane T (theory extraction), 2026-09-09.

> ### ⛔ **This item records a problem and a candidate requirement. It commissions nothing, criticises no author, and proposes no repair to the object.**

---

## 1 · The problem in plain terms

One concept sits under most of the programme's remaining work: **the distinctions the system is
required to preserve.** It has kept the same name throughout.

⭐⭐⭐ **It has not kept the same kind of thing.**

| when | what it was |
|---|---|
| at the start | ⭐ **a TEST** — *"remove this piece; does any required operation now give a different answer?"* |
| three days later | ⭐ **a LIST** — a tiered inventory of named items, each with values and priorities |

$$\boxed{\begin{array}{c}\textbf{⭐⭐ A test needs no acceptance criteria. It compares two outputs.}\\ \textbf{A list of requirements does — each item must say } \mathbf{what\ would\ count\ as\ meeting\ it.}\end{array}}$$

⛔ **Nobody wrote those acceptance criteria, because nobody recorded that the object had changed kind
and now needed them.**

## 2 · Why this is the current blocker, not a historical curiosity

The programme is presently stuck on a precise question: *what does it mean for a requirement to be
satisfied?* Several efforts have looked for the missing connection between the governing contract and
a requirement's acceptance conditions, and each concluded it is absent.

⭐⭐⭐ **The archaeology shows the connection was never lost. It was never needed, and then never built.**
While the object was a test, the question could not arise; once it became a list, the question arose
and nothing answered it.

⭐ **That reframes the blocker from *"a missing piece of theory"* to *"an unrecorded change of kind"***
— which matters, because the two call for different work.

## 3 · Why it is a business problem

**a. Every step was locally reasonable.** Widening the scope, giving items names, adding priorities —
each is an ordinary improvement, and none is wrong on its own. ⛔ **The damage is cumulative and
belongs to no single step**, which is exactly why no reviewer caught it.

**b. Earlier results are silently inherited by a different object.** Work done when the concept was a
test — its criterion, its derivations, its four-state result — is cited by documents that treat it as a
list. ⭐⭐ **Whether those results transfer is a real question that nobody has asked**, because the name
never changed.

**c. It defeats the programme's own strongest discipline.** This estate is unusually careful about
marking what is derived, stipulated, proposed or open. ⭐ **All of that machinery tracks a claim's
STATUS. None of it tracks a concept's TYPE.** ⛔ **So a change of kind passes every check.**

**d. It has already produced a false search.** Effort has gone into looking for a missing bridge in the
corpus. ⭐⭐ **The bridge is not missing from the record — it was never owed by the earlier object.**
Searching harder could not have found it.

**e. It is very unlikely to be the only case.** ⭐ At least three other central objects in this
programme have moved between being a criterion, a structure and an inventory. **This one was found
only because someone traced it to its origin.**

## 4 · What is *not* the problem

⛔ **No individual document is wrong.** Each formulation is defensible where it stands.

⛔ **This is not about the concept's content.** Whether the current list is right, complete, or well
chosen is outside this record.

⛔ **This is not a naming collision.** The programme already tracks cases where one symbol carries two
meanings at the same time. ⭐⭐ **This is the opposite: one meaning at a time, changing across time,
under a stable name — and the earlier sense is not contradicted, it is quietly superseded.**

⛔ **No repair, migration or renaming is proposed here.**

## 5 · Candidate requirement (a direction, not a design)

> ⭐ **When a concept changes kind — from a test to a set, from a criterion to an inventory, from a
> predicate to an object — that change should be recorded as an event, with what the new kind now
> requires that the old one did not.**

⭐⭐ Two properties matter more than the format:
1. **Type is not status.** ⛔ *"Proposed"*, *"derived"* and *"open"* describe how well a claim is
   supported. ⭐ **They say nothing about what kind of thing it is**, and the existing vocabulary
   therefore cannot express this event at all.
2. ⭐ **The useful part of the record is the *consequence*, not the label.** *"This is now a list, so
   each entry needs acceptance criteria"* is the sentence that would have prevented the current
   blocker.

## 7 · Urgency

⚠️ **High, because the blocker it explains is the current one.** ⭐ Effort is being spent looking for a
connection that was never owed. ⛔ **Until the change of kind is on the record, that search can be
repeated indefinitely** — and each repetition will correctly conclude that the connection is absent.

⭐ **And the diagnostic work is already done**; what is missing is a place to write it down.
