THREE DESIGN DECISIONS THE TESTS PIN

K1 asserts NON-NULLABLE constructor parameters by reflection. Three of the four source accessors
on AdjudicationProcessState are nullable and the type system does not know concludeFailureDeclared()
sets them together. The invariant is the AGGREGATE's; the event only CARRIES it. So the null case
is made unrepresentable in the event and the construction SITE fails closed -- responsibilities
stay split instead of the event defending an invariant it does not own.

K3 is deliberately TWO failures, not one: an unsupported schema version and an incomplete payload
are different defects with different causes, and a single "invalid input" test would let either
regress unnoticed.

K4 extends the EXISTING EventHydratorRegistryWiringTest rather than adding a second file. The
registry's wiring has one home; a second file asserting the same contract would drift from it.

O-1 -- AN AMBIGUITY RETURNED, NOT ABSORBED

OutboxEventAdapter exposes ONE public method, enqueue(), and dispatches to PRIVATE per-event
writers -- writeAdjudicationExpired() and writeDeterminationIssued(). A new event needs a new
private writer for its payload to exist at all.

So the payload shape is a contract between two halves -- writer and hydrator -- and only the
hydrator is in the authorized scope. K2/K3 assert a v1 shape I DEFINED. Until a writer produces
it, that shape is an engineering proposal, not a verified contract: a hydrator that agrees only
with itself proves nothing about what will be in the outbox.

Does writeAdjudicationFailureDeclared() belong to D2 (the registration pair) or D4 (publication,
HELD)? If D2, the shape becomes verifiable here and K2/K3 gain real force. If D4, the hydrator
ships against an unverified shape and THAT LIMITATION MUST APPEAR IN THE ACCEPTANCE EVIDENCE
rather than being discovered when D4 lands and the shapes disagree.

Not written, not chosen. Not a stop condition for D1/D2 either -- both remain executable; only
the strength of K2/K3's evidence depends on the answer.

RECORDED, NOT A DEFECT CLAIM: WP-6's AdjudicationExpiredHydrator has no dedicated unit test and
no registry-wiring assertion. This batch therefore establishes coverage the accepted precedent
lacks, which is a reason not to describe WP-4C-1's evidence as parity with it.

Priority-2 engineering quality work, inside existing authority. No behaviour changed, no
governance touched.

THE GAP, AND WHY IT SAT OPEN

AdjudicationExpiredHydrator shipped with WP-6, is registered at AdjudicationServiceProvider
line 81, and had NO unit test and NO registry-wiring assertion. I found it while writing
WP-4C-1's equivalents, recorded it as a coverage observation about accepted work, and then left
it -- because I had started treating "no governance event" as "no engineering work". That was
wrong: the event model controls AUTHORITY TRANSITIONS, not engineering productivity.

WHAT WAS ADDED

  8 unit tests   event type - v1 reconstruction - VO type fidelity - the v1-only window
                 (unsupported version rejected, ABSENT version accepted by design) - missing
                 required field rejected, one case per field
  1 wiring test  the registry resolves 'AdjudicationExpired' after the provider boots

Two assertions are worth more than the rest:

THE ABSENT-VERSION TOLERANCE IS NOW PINNED. The shipped hydrator reads
$payload['schema_version'] ?? 1, so a payload with no version is accepted as v1. That is a
deliberate tolerance, not an oversight, and it was undocumented and untested -- a future change
could have narrowed the window silently and broken older rows.

THE ABSENCE OF A VERDICT IS ASSERTED STRUCTURALLY. Constitutional Policy 4: a timer concludes
nothing. The test reflects over AdjudicationExpired's properties and asserts they are exactly
[challengeRef, expiredAt], with outcome, legitimacy, reason and concludedByAuthority explicitly
absent. Expiry announcing a verdict would be a constitutional defect, and now a payload addition
cannot slip in unnoticed.

RESULT: NO DEFECT FOUND

All 12 pass. The hydrator behaves as documented. So this bought coverage rather than a fix --
which is the honest outcome to report, and was not knowable in advance. Had any assertion failed
it would have been implementation evidence about accepted work, reported and not silently
repaired.

  static analysis  [OK] No errors
  merge gate       PASS -- 304 tests, 790 assertions (was 295 / 773)
  risky            111 -> 112. Consistent with ENG-012, cause still unestablished

A COMMAND-CHAINING DEFECT WORTH RECORDING

My first verification used `grep -c ... && grep ...`. grep -c returned 0 matches, exited 1, and
silently killed the rest of the chain -- so the provider check never ran and I nearly reported an
unverified state as verified. Zero matches is a RESULT, not an error; chaining verification steps
with && makes an expected-empty result indistinguishable from a broken command.
