# F-SERIES v1.3 — DESIGN FOR REVIEW (not implemented)

**Status: DESIGN ONLY — for human/architect review before any code is written (F-LOG-0010).** v1.2 stays frozen and not
approved. F3082 stays at READ-COMPLETE. HDR-1…HDR-5 stay open.
**Inputs:**
- the independent re-audit `audits/20260925_1540_F-SERIES-v1.2-INDEPENDENT-REAUDIT.md` (F-LOG-0009);
- two senior reviews of it (2026-09-25), which agree on "v1.3 first" and on YES to a dedicated human decision and YES
  to a mechanical git boundary, and which ask for the v1.3 design to be reviewed before implementation.

**Organizing principle (from the review):**

```
DETECTION  ≠  VALIDATION  ≠  AUTHORIZATION  ≠  EVIDENCE
(candidates)  (independent review)  (a human decision)  (an immutable, hash-identified object)
```

v1.2 failed where it modelled one of these as another: an authorization as log text mentioning an F-ID, validation as
agreement with an unconstrained auditor, evidence as a mutable file with a hash in a forgeable ledger, and detection as
a gate. v1.3 models each as its own domain object with its own invariant.

## 1. Where I agree and where I disagree with the reviews

**Agree (and adopted as requirements below):**
- v1.3 comes before any D1.
- N-01, N-02, N-03, N-04 and N-06 are the core.
- N-04 is a hard blocker before RECONSTRUCTED.
- N-09: the math detector is a *candidate detector* with measured recall on an explicit test set; it never makes a
  completeness claim.
- The 0.8 Jaccard threshold is a design choice, not a finding; containment is reported alongside it.
- Families for multiplicity must be defined mechanically, and HDR-3 is not implemented as text.
- HDR-1…HDR-5 stay unresolved, and HDR-4 waits until the authorization semantics are repaired.
- The v1.3 re-audit must be adversarial.
- Lexical guards become warnings, not gates.
- The v1.2 overstatements (F-21, C15 §6) are corrected.

**Disagree — three points, all about what this environment can actually guarantee:**

**D-1. The machine cannot establish `decision.actor = human` from anything in the repository as it is set up today.**
The review asks for a decision record whose `actor` the machine can establish. In this checkout every commit the AI
makes is authored as the human (`Dr. Nab Raj Roshyara`), no signing key is configured, and the AI can write any line in
any file, push to the remote (`origin`), and run `git commit`. Therefore no string, record schema, git author field or
commit history *inside this environment* can distinguish a human decision from an AI-written one. A `HumanDecision`
record with an `actor` field would be the same "approval-shaped text" N-05 criticised, only better formatted. The only
mechanical actor binding available is **a secret the AI cannot use**:
- **Option A (recommended):** the human signs decision records with a key the agent has no access to, and the gate
  verifies the signature against a public key pinned in the approved index.
  - An SSH signing key or a GPG key, held in a passphrase-protected agent or on a hardware key that is not unlocked for
    this session.
  - The records are verified with `git verify-commit` on a decision commit, or with `ssh-keygen -Y verify` /
    `gpg --verify` on a detached signature file.
  - This is the only option that makes N-01 and N-05 mechanical.
- **Option B:** the human makes the decision out of band (e.g. through the claude.ai UI, answering the session), and
  the AI records it. The actor binding is then *procedural*, and the record says so.

Either way, the semantic object is the decision record the review describes. Only its *authenticity* differs between
A and B, and the protocol must name which one is in force. **This is a human decision (new HDR-6).**

**D-2. A git-prefix check guarantees consistency with committed history, not authenticity of that history.** I agree
the check should replace the hand-rolled chain: it defends against truncation and recomputation in the working tree
(N-02). But the AI also makes the commits, and it could in principle commit a forged state, or rewrite local history.
The real external witness is:
- (i) human-signed decision commits (D-1, Option A), which the pipeline requires as ancestors of HEAD; and/or
- (ii) the pushed remote as a second copy.

v1.3 will state exactly this: git-bound transition integrity = no uncommitted or truncated state is ever acted on.
Authenticity = signed human decisions. They are two different guarantees.

**D-3. An auditor-completeness floor reduces independence, and the design should say so.** If the auditor must satisfy
the same coverage rules as the extractor (N-03), the two processes share their method, and agreement becomes partly a
property of the shared rules. I still recommend the floor, since an unconstrained auditor is worse. The v1.3 audit record
will report the auditor's own completeness separately from agreement, and it will not call agreement "independent
validation" without that qualification.

## 2. Domain model (DDD + formal state)

| Concept | Kind | Identity | Invariant |
|---|---|---|---|
| **EvidenceObject** | aggregate root (per F-ID, per L1 version) | `ev:<F-ID>:L1:v<k>` + the **evidence hash** = sha256 over the canonical manifest of its artifacts (UNITS, INVENTORY, DISPOSITIONS, CATEGORY-CHECK, ATTESTATION, PROMPT) | once sealed (CONTENT-EXTRACTED), its artifacts never change; a later L1 is a new version `v<k+1>` with `supersedes: v<k>` and the old version kept byte-for-byte |
| **HumanDecision** | aggregate root | `hd:<n>` + record hash | `{action ∈ closed set, target F-ID, target evidence hash, run, reason, utc, authenticity: SIGNED(key id) \| PROCEDURAL}`; valid only if its authenticity is the one the protocol requires (HDR-6); binds to exactly one evidence hash |
| **AuditRecord** (independent L1) | entity of an EvidenceObject | the audited evidence hash + the auditor's evidence hash | the auditor inventory satisfies the completeness floor; the comparison is recomputed; the verdict is accepted only through a HumanDecision `ACCEPT-L1` naming that evidence hash |
| **Transition** | domain event | `(F-ID, seq)` | legal (state table); its preconditions are verified against **committed** state; the transition commit contains exactly the event + the stage's artifacts |
| **Consumption** | value object | `(consumer F-ID, source F-ID, source evidence hash)` | every cross-file quote, checkpoint population and hypothesis evidence names the **evidence hash** it consumed, and that hash must be an ACCEPTED, sealed EvidenceObject |
| **Detection signal** | value object | detector id + version + unit | never a gate on its own; it only produces review obligations (§4 P1-2) |

**Action vocabulary for HumanDecision (closed):**
- `APPROVE-PROTOCOL`: targets the hashes of the governing documents **and of the enforcing scripts**;
- `ACCEPT-L1`: targets an evidence hash;
- `REJECT-L1`;
- `AUTHORIZE-REEXTRACTION`: targets the superseded evidence hash, with a reason;
- `ACCEPT-EXCEPTION-<STATE>`: targets an F-ID + run;
- `GO-D1`: targets an F-ID;
- `DECIDE-HDR-<n>`: carries the decided value, e.g. the temporal semantics.

## 3. P0 requirements (blocking before F3082 D1)

**P0-1 · Human authorization semantics (N-01, N-05; D-1).**
- `human_ref_ok(ref, fid)` and the approval-line parser are replaced by `decisions(target)`. It reads decision records
  from one place, `decisions/HD-<n>.json` (one file per decision, never edited), plus the signature file when Option A
  is chosen.
- A record counts only if:
  - it matches the action and the target hash;
  - its authenticity meets the protocol's requirement;
  - no later record revokes it.
- Governance-log prose never counts again, which removes the N-01 and N-05 parser class of bugs entirely.
- The AI may *draft* a decision file for the human to sign (Option A). It never produces the signature.

**P0-2 · Immutable evidence boundary (F-01, N-04, N-06).**
- CONTENT-EXTRACTED seals EvidenceObject `v<k>`: it computes the evidence hash and records it in the transition.
- Artifacts are written into `ledger/F####/L1-v<k>/` and never rewritten.
- A re-extraction creates `v<k+1>` and requires `AUTHORIZE-REEXTRACTION` targeting `v<k>`'s hash (this closes N-04 in
  every path, not only CONTENT-EXTRACTED→CONTENT-EXTRACTED).
- Once any L2/L3 exists for `v<k>`, the new version's lineage records that fact, and the audit diffs `v<k>` against
  `v<k+1>`.

**P0-3 · Git-bound transition integrity (N-02; D-2).** Every gate checks four things before it evaluates evidence:
1. the working `F-SERIES-STATE.jsonl` equals `HEAD:F-SERIES-STATE.jsonl`;
2. every sealed artifact equals its committed blob;
3. the working tree has no uncommitted change under `ledger/`, `decisions/` or the state files;
4. every HumanDecision the gate relies on is in a commit that is an ancestor of HEAD.

After a successful transition the gate *itself* commits exactly the event + the stage's artifacts, with a fixed message
format, and the next gate re-verifies. **The hand-rolled `prev_hash`/`hash` chain and the anchor are retired.** Git
provides this property natively. The pre-v1.2 prefix is already committed history, so the anchor is kept only as a
historical record.

**P0-4 · Auditor completeness (N-03; D-3).**
- The AUDITOR-INVENTORY must pass the same coverage rules as an extractor inventory:
  - every non-markup unit is covered;
  - cue units are bound to DEFINITION/TERM, math units to FORMULA/NOTATION/THEOREM, code units to the code categories;
  - the same anti-catch-all bounds apply.
- The comparison is extended per unit: category divergence (not only group absence), the extractor's releases and
  NO-SUBSTANTIVE dispositions listed for review, and items per unit on both sides.
- The AuditRecord reports the auditor's completeness and the agreement separately.

**P0-5 · AUDITED evidence immutability for consumers (N-06).**
- `cross_file_candidates`, `recorded_quotes`, `check_research` and the checkpoint snapshot resolve every other F-ID
  through `(F-ID, evidence hash)`, verify that the sealed artifacts still hash to it, and verify that an `ACCEPT-L1`
  exists for it.
- A consumption record stores the hash.
- The checkpoint snapshot refuses if any hypothesis or evidence is mutable.

**P0-6 · Re-entry model (N-04, F-17).**
- The state machine separates *re-entry into analysis* (RECONSTRUCTED, ANALYZED, RESEARCHED under the same evidence
  hash; allowed after AUDIT-FAILED) from *new evidence* (a new L1 version; always `AUTHORIZE-REEXTRACTION`).
- READING under a fresh run after L2 exists is treated as new evidence (same rule).

## 4. P1 requirements (in v1.3, not blocking the design review)

**P1-1 · Pin the enforcing implementation (N-05).** `APPROVE-PROTOCOL` targets the protocol, the runbook, the contracts
index, **every script under `scripts/`**, and the v1.1 base contracts. A change to any of them revokes execution.

**P1-2 · Detection as signals (N-08, N-09, F-04, F-05, F-09, F-10, F-12, F-14).**
- The math, definition, prescription, S-identifier and temporal detectors produce **review obligations**, not
  pass/fail gates.
- Each flagged unit or record must carry a reviewer disposition, and the independent auditor reviews a stated sample
  plus all releases.
- **Exception — the three rules that are structural, not lexical, stay hard:** the outcome field is a closed
  *whitelist* schema per record kind (N-08); a release is never allowed on MATH/CODE kinds (N-09); and every string
  field gets a case-insensitive S-identifier check with path normalisation (N-08, A13).
- The math detector is extended with arrows and Greek letters next to operators, and its **recall is measured on a
  written, versioned notation test set** (synthetic, not F-content) and reported as a number, never as completeness.

**P1-3 · Isolation (F-02, C15).**
- Attestation paths are normalised (`os.path.normpath`) with an explicit deny regex.
- The reader calls the git-bound check.
- The extractor's and auditor's **exact prompt** becomes a sealed artifact of the EvidenceObject (`PROMPT.md`, hashed
  in the attestation), so a human can inspect it for contamination. It must contain no content description of the
  F-file.
- C15 §6 is rewritten so that nothing is called "mechanical" that is not.

**P1-4 · Statistics (RN-08, N-10, F-15, F-16).**
- Near-duplicates report Jaccard **and** containment, and publish the distribution; 0.8 is labelled a design choice.
- A multiplicity family is defined mechanically as *all confirmatory comparisons scheduled at the same checkpoint*,
  and cannot be self-declared per hypothesis.
- De-facto hypotheses filed as SUGGESTION-RESEARCH are flagged for review.
- A checkpoint counts as opened only with a valid STATE record whose snapshot hashes verify (N-07).
- HDR-2 must not rely on `file_mtime`, because a git checkout sets it to checkout time.

**P1-5 · Documentation.** The v1.2 matrix rows F-21 and F-16 ("clusters"), C02 §5 ("the audit reviews every
release"), the C13 §2 check order and the C15 §6 "Mechanical" row are corrected in v1.3 files. The frozen v1.2 files
stay unchanged.

**Proportionality (the re-audit's §8, adopted):** retire the hand-rolled chain and the anchor mechanism (P0-3); demote
the lexical guards (P1-2); keep the CATEGORY-CHECK only as the auditor's review input; defer the checkpoint population
machinery until close to CP-01, keeping only the READING block.

## 5. How v1.3 will be judged

1. The adversarial suite covers every v1.2 re-audit attack A01…A21 as a regression test, plus the review's list:
   - forge human approval;
   - forge state;
   - truncate state;
   - recompute hashes;
   - reduce the auditor inventory;
   - modify audited evidence;
   - re-enter after L3;
   - bypass the approval parser;
   - bypass the provenance guards;
   - consume modified prior evidence.
2. A **fresh** independent adversarial re-audit (a new agent, its own scratch location, the persisted reports as its
   only prior conclusions).
3. Success requires both. Passing tests alone is conformance, not validity.
