## Rationale
- [S0897] (EXAMPLE, ARGUMENT): A constitution-derived requirement (architecture-assurance) is 'not an opinion' but a normative consequence of the constitution, illustrating Constitution -> Requirement derivation.
- [S0897] (EXAMPLE, EXPLANATION): A risk-model-derived requirement path: RISK:DataLoss -> Control:VerifiedRestore -> RollbackVerified, showing requirements can emerge from Goal+Risk rather than only from architecture rules.
- [S0897] (FORMALIZATION, EXPLANATION): Describes the LLM's role as proposing candidate requirements from unstructured sources (e.g. reading a 300-page policy), which KnowledgeOS records as CandidateRequirement; only after a deterministic/governed check (SourceExists?, SourceApplicable?, AuthorityValid?, RuleSatisfied?) does CandidateRequirement -> ContractRequirement.
- [S0897] (ANALYSIS, OPEN-QUESTION, RESTATEMENT): Because the requirement taxonomy now spans Knowledge+Evidence+Validation+Authorization+State rather than only 'what must be known,' proposes the more precise terms 'Epistemic-Governance Contract' or 'AssuranceContract,' but explicitly declines to rename yet since 'Epistemic Contract' retains conceptual value — records the naming issue rather than resolving it.
- [S0897] (EXPLANATION, EXAMPLE): Describes contract normalization: an LLM can help normalize vague natural-language sources ('Make sure the migration is safe') into canonical, structured, executable requirements while the natural language remains provenance.
- [S0897] (CONCEPT, EXPLANATION): Argues a Ubiquitous Language is needed for requirements, listing ten candidate DDD domain-object terms (Requirement, AssuranceRequirement, KnowledgeRequirement, ValidationRequirement, GovernanceRequirement, BlockingRequirement, SatisfactionRule, RequirementDependency, RequirementSource, RequirementVersion), explicitly framing them as domain objects rather than merely database fields.
