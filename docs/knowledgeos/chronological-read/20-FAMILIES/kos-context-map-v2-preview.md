## Rationale
Justifies each context-map edge: Governance->Knowledge (governance establishes what is organizationally binding, e.g. Architecture Decision->Authoritative Knowledge, Governance Policy->Applicable Constraint, Approved Exception->Effective Expected State; governance must not depend on an agent's interpretation to become authoritative); Knowledge->Assurance (knowledge translates governance into reusable engineering meaning, e.g. Decision D42 establishing 'Service X must use pattern P' becomes an assurance expectation, so assurance consumes the authoritative expectation rather than inventing it); Assurance->EngineeringState (assurance observes/evaluates engineering reality but does not own it); Engineering->Evidence (Runtime->Observation->Evidence, e.g. Git commit/CI result/deployed image/Kubernetes state/monitoring/security scan, with KnowledgeOS preserving references/interpretation without becoming the source system); Evidence->Knowledge (Evidence->Claim is valid, but Evidence ↛ Authority automatically — 'one of the central boundaries'), closing the semantic feedback loop Governance->Knowledge->Assurance->Engineering->Evidence->Knowledge [S1028].
