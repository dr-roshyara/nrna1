### Theme 1 — Framing: does architecture survive contact with the running system? (106.1-106.2)
`[S1005]` — 3 rows condensed into this theme. Frames Step 106's central test as whether the architecture survives contact with the running system, via a chain A_I (intended) → A_C (implementation) → A_D (deployed) → A_R (runtime), requiring approximate conformance A_R≈A_I subject to documented differences; states the governing principle Documentation ≠ RuntimeEvidence (runtime is the final authority for runtime facts); and defines the four representations (Architecture/Source/Deployment/Runtime models) with the explicit goal Conformance(A_I,A_C,A_D,A_R), not literal equality.

### Theme 2 — Deployment, configuration, environment and instance identity (106.3-106.10, Experiments 1-5)
`[S1005]` — 8 rows condensed into this theme. Runs Experiment 1 (a deployed version 2.0 lagging the declared 2.1 is DeploymentDrift, must be reported, PASS) and Experiment 2 (runtime behavior must be evaluated against actual production configuration, not the repository default, PASS); states configuration is part of architecture (A_R=Code+Configuration+Infrastructure+Dependencies+RuntimeState); runs Experiment 3 (environment-specific infrastructure, e.g. dev PostgreSQL vs prod ManagedDatabase, is not automatically a violation if declared EnvironmentAware, PASS); defines the runtime topology model Component→Instance→Environment→Host/Platform; runs Experiment 4 (multiple runtime instances must map to the same logical component, PASS); states LogicalComponent ≠ RuntimeInstance; and runs Experiment 5 (scaling a service from 2 to 8 instances does not create eight logical components, PASS).

### Theme 3 — Runtime dependency graph, drift definition, and dynamic-vs-static dimensions (106.11-106.19, Experiments 6-9)
`[S1005]` — 9 rows condensed into this theme. Lists runtime dependency-discovery evidence sources (network connections, service discovery, traces, logs, configuration, deployment manifests); runs Experiment 6 (an observed dependency violating an architecture-forbidden edge is RuntimeArchitectureViolation, PASS); defines the runtime architecture graph G_R(t)=(V_R,E_R) compared against the intended graph G_I; defines Drift(t)=Difference(G_I,G_R(t)), called one of the most valuable KnowledgeOS capabilities; runs Experiment 7 (an undocumented new external API in production is a DriftCandidate, PASS); states Drift ≠ Violation (a runtime difference may be an ApprovedException or ExpectedDynamicBehavior); runs Experiment 8 (temporary scaling instances not enumerated in architecture is not itself a violation, PASS); requires KnowledgeOS to model which architectural dimensions are intentionally dynamic (Instances(t), Load(t), Connections(t), ResourceAllocation(t)) versus static; and runs Experiment 9 (architecturally-permitted auto-scaling 2→20 is not drift, PASS).

### Theme 4 — Governance policy enforcement via direct runtime observation (106.20-106.21, Experiment 10)
`[S1005]` — 2 rows condensed into this theme. Notes runtime network observation can directly test governance rules such as Agent ↛ ProductionDB, and runs Experiment 10 (an observed Agent→ProductionDB connection is a Security/GovernanceViolation, stronger evidence than mere configuration inspection, PASS).

### Theme 5 — Evidence freshness, desired-vs-actual state, reconciliation, and technical-vs-operational success (106.22-106.33, Experiments 11-15)
`[S1005]` — 12 rows condensed into this theme. Defines required runtime evidence fields (Timestamp, Source, Environment, Component, ObservationType, TraceID); runs Experiment 11 (an undated observation is weak evidence, PASS); states a past observation does not automatically establish current state; runs Experiment 12 (a stale health observation cannot alone establish current health, PASS); distinguishes ObservedHealthy(t_1) from CurrentlyHealthy (the latter requiring fresh evidence); distinguishes DesiredState from ActualState (e.g. DesiredReplicas=4 vs ActualReplicas=3); runs Experiment 13 (three actual workers against four desired is RuntimeDrift, PASS); defines reconciliation as identifying the Gap between DesiredState and ActualState; runs Experiment 14 (a deviation caused by an approved maintenance window is KnownDeviation, not necessarily Violation, PASS); defines the runtime verification pipeline Deployment→Verification→RuntimeObservation; runs Experiment 15 (a technically-successful deployment with a failing health check is DeploymentTechnicalSuccess=True/RuntimeConformance=False, PASS); and restates TechnicalSuccess ≠ OperationalSuccess as a distinction KnowledgeOS must represent.

### Theme 6 — Incident analysis, architecture-aware observability, DDD mapping, and the governance/knowledge/code feedback loops (106.34-106.47, Experiments 16-22)
`[S1005]` — 14 rows condensed into this theme. Defines the incident-analysis chain Failure→RuntimeObservation→Evidence→AffectedComponent→Architecture; runs Experiment 16 (a production outage with no mapping from the failed runtime component to the architecture model is poor architectural observability — result explicitly FAIL, the only recorded failure among the 33 experiments); defines the desired architecture-aware observability chain Trace→Component→BoundedContext→BusinessCapability; runs Experiment 17 (mapping a traced component to its bounded context enables domain-level incident interpretation, PASS); states runtime architecture must connect RuntimeComponent→BoundedContext, making DDD operational for incident response; runs Experiment 18 (a database failure affecting three bounded contexts must be fully identified, PASS); defines the runtime-to-governance escalation chain RuntimeDrift→ArchitectureFinding→GovernanceDecision; runs Experiment 19 (an undocumented dependency creates an assignable ArchitectureFinding, PASS); restates the bottom-up chain Runtime→Observation→Evidence→Knowledge; runs Experiment 20 (a runtime-discovered dependency becomes provenance-bearing ObservedFact, not immediately ApprovedArchitecture, PASS); defines the architecture-promotion pipeline Observed→Investigated→Accepted/Rejected→ArchitectureKnowledge (preventing runtime reality from silently rewriting governance); runs Experiment 21 (a validated undocumented component correctly flows Observation→ArchitectureUpdate, PASS); defines the runtime-to-code feedback loop RuntimeEvidence→Bug→CodeChange→Verification; and runs Experiment 22 (a forbidden-dependency finding correctly flows Finding→Remediation→Test→Deployment→Observation, PASS).
