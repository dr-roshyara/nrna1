## Rationale

Defines per-component reconstruction targets and their critical tests: repository topology (do application/domain/infrastructure/governance/knowledge/evidence/assurance/agents directories exist — must not be assumed); package boundary tests (Domain->Infrastructure=FAIL if direct/inappropriate; Agent->Domain potentially valid through application contracts; Agent->Database needs scrutiny; Governance->Agent implementation generally suspicious; Assurance->External systems expected through ports/adapters); .claude/ and .codex/ each tested by 'does it own knowledge, or point to knowledge?' with the desired symmetry (.claude/ and .codex/ hold agent behavior/integration, KnowledgeOS holds governed engineering knowledge); AGENTS.md tested against AGENTS.md=Pointer+OperatingContract (not =EnterpriseKnowledgeBase); .claude/memory/ tested by 'what epistemic status does memory have?' (potentially valid: session hints/workflow state/preferences/temporary context/pointers; potentially problematic: authoritative architecture/binding governance decisions/enterprise policies/unverified claims) [S1031]. Additionally, Defines the registry reconstruction target (what exactly is registered — repositories/agents/knowledge objects/architecture artifacts/services/policies/tools/checks — determining whether it is a TechnicalRegistry, KnowledgeRegistry, or broader) and the hook reconstruction target (each hook classified by Trigger->Action->Evidence, e.g. Git event->Hook->Validation->Evidence vs. Agent event->Hook->Session logging; a blocking hook is not automatically governance — Hook->Policy traceability is required to know which policy authorizes the block) [S1031]. Further, Defines the deterministic-assurance reconstruction target via eight questions (what is checked, where rules are defined, who owns them, how results are recorded, whether versioned, whether evidence preserved, reproducibility, connection to governance), distinguishing CollectionOfChecks from AssuranceSystem; provisionally classifies current assurance maturity as AssuranceCapability=Existing/Partial rather than CompleteAssuranceContext, with semantic integration as the missing question; requires the full chain Rule->Checker->Execution->Result->Evidence->Finding as strong evidence of an assurance architecture (a bare 'a checker exists' is weak evidence) [S1031]. Relatedly, Current-state observation 1: the agent integration layer is already repository-local, which is desirable for reproducibility; the architectural question is what those artifacts are allowed to own, not whether they exist [S1043]. In the same vein, Current-state observation 2: Claude (.claude/) and Codex (.codex/) are evolving toward symmetry, technically different but consuming the same KnowledgeOS authority [S1043]. Current-state observation 3: AGENTS.md functions as an important agent entry/pointer mechanism with high architectural value, provided it points to rather than replaces KnowledgeOS [S1043]. Additionally, Current-state observation 4: .claude/memory/ gives agents cross-session persistence, but its semantic status must remain Agent Contextual Memory absent explicit governed promotion [S1043]. Further, Current-state observation 5, called 'one of the most significant findings': the platform already contains deterministic assurance mechanisms, a strong foundation for the target Assurance Context [S1043]. Relatedly, Current-state observation 6: the remaining question is whether existing records have sufficient semantic identity and provenance [S1043]. In the same vein, Current-state observation 7: the registry provides structured identification/discovery but should not be prematurely equated with the Assurance Graph [S1043]. Current-state observation 8: KnowledgeOS already contains governance-oriented artifacts (constitution, conventions, standards, landscape, decisions, review/verdict artifacts), significantly document-oriented — not inherently a weakness, but raising the machine-addressability question [S1043]. Additionally, Current-state observation 9: eight distinct knowledge-bearing surfaces exist, creating a central architectural risk of knowledge fragmentation [S1043]. Further, Clarifies fragmentation does not automatically mean duplication — two artifacts mentioning the same rules can have distinct responsibilities; the problem occurs only when both become competing authorities, posing the current authority question 'which source wins when two knowledge-bearing artifacts disagree?' — absent a machine-enforceable answer, this is AuthorityAmbiguity, a current-state finding unless governance evidence proves otherwise [S1043].
