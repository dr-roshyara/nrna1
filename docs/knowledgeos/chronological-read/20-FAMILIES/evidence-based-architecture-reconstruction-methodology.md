## All rows (source_id order)

All 84 rows come from a single source file, S1008 (Step 109), read here in its own document order and grouped into 11 themes that follow the document's own section structure (34 numbered "Experiments" run through the whole file as worked PASS/FAIL tests of each principle). Full text of every row is in `03-CONTRIBUTIONS.jsonl`.

**Theme 1 — Governing principle, epistemic status, and `K_actual` vs `K_intended`** (3 rows). States "no architectural assertion without evidence" as Step 109's governing shift from target-architecture definition to actual-system reconstruction; introduces the five-way epistemic status Observed/Inferred/Specified/Claimed/Not-yet-evidenced; reframes the guiding question as `K_actual = Artifacts+Code+Configuration+Workflows+RuntimeBehavior`, compared against `K_intended`.

**Theme 2 — Evidence sourcing and the E0–E5 classification (Experiments 1–5)** (7 rows). Lists ten evidence sources of increasing behavioral strength (no single category sufficient alone); defines the six-level evidence classification E0 (name only) through E5 (governance evidence); Experiments 1–5 each test one level (bare directory → E0/E1; named classes → E2; CI-executed tests → E3; production records → E4; explicit governance identification → E5), completing the chain Structure→Implementation→Verification→Runtime→Governance.

**Theme 3 — `ActualComponentInventory` schema and component categories** (3 rows). Defines the `ActualComponentInventory` schema (13 attributes per component); defines ten semantic component categories (Knowledge, Ingestion, Semantic processing, Governance, Agent integration, Assurance, Storage, Runtime infrastructure, Interface, …); states components may hold multiple roles simultaneously (e.g. `AgentGateway = AgentIntegration+SecurityBoundary+API`), forbidding forced single-category classification.

**Theme 4 — Repository and system boundary reconstruction (Experiments 6–9)** (9 rows). States repository topology and boundaries must be derived from evidence, never assumed; Experiment 6: documented vs. actual repository structure diverge, actual wins for implementation topology; Experiment 7: separately-repositoried components may still form one logical ecosystem, distinguishing `RepositoryBoundary` from `SystemBoundary`; defines `KnowledgeOS_SystemBoundary` as the evidenced union of demonstrably-related components; Experiment 8: a generic CI tool remains external unless explicitly internalized; states `Uses(X,Y)` does not imply membership `Y∈KnowledgeOS` (`InternalComponent` vs `ExternalDependency`); states ownership defaults to Unknown unless evidenced; Experiment 9: a `governance/` directory alone does not prove Architecture-Board ownership.

**Theme 5 — Interface archaeology (Experiment 10)** (3 rows). Lists ten possible interface types (REST, GraphQL, CLI, message bus, database, filesystem, Git, event, webhook, agent protocol); Experiment 10: a client with no network evidence should not be assumed a remote call, possibly an in-process abstraction; distinguishes `InterfaceDeclared`, `InterfaceUsed`, `InterfaceObserved` as three separate evidence levels.

**Theme 6 — Data store reconstruction (Experiments 11–12)** (5 rows). Defines the `Store=(Type,Purpose,Owner,DataClass,Authority,Retention)` tuple; Experiment 11: an existing vector database does not automatically constitute the semantic knowledge store; states `VectorStore≠KnowledgeModel` (similarity retrieval is distinct from meaning/support/ownership/authority); states database schema often outweighs documentation as evidence of what the system actually believes exists; Experiment 12: a documented provenance claim contradicted by a schema lacking any provenance relationship is a potential implementation gap.

**Theme 7 — API, state-machine, business-rule, and test archaeology (Experiments 13–17)** (10 rows). Defines API archaeology as tracing `Endpoint→UseCase→DomainModel→Persistence`; Experiment 13: a minimal POST endpoint does not demonstrate provenance/authority/temporal-validity/semantic-type support; states explicit implementation state-machine transitions are strong lifecycle evidence; Experiment 14: unenforced status transitions despite documented semantics is a gap; lists seven layers where business rules may be enforced; Experiment 15: a nullable `authority` field despite a non-null architecture rule is an enforcement gap; states tests reveal developer-believed invariants (Unit/Integration/Contract/Architecture/Security/EndToEnd/Runtime); Experiment 16: an architecture rule enforced by an architecture test is strong evidence; states `TestExists` is weaker than `TestExecuted` (CI execution required for governance strength); Experiment 17: a test excluded from CI is a `VerificationGap`.

**Theme 8 — Agent-harness, scripts, hooks, and configuration archaeology (Experiments 18–23)** (12 rows). States agent-harness reconstruction (AGENTS.md, `.claude/`, `.codex/`) establishes actual responsibility, not quality; Experiment 18: each `.claude/` subdirectory must be classified individually, a "memory" directory name does not itself imply authority; defines the pointer-layer test (does the harness point at shared knowledge or duplicate it); Experiment 19: both harnesses referencing the same architecture source is strong pointer-layer evidence; Experiment 20: Claude's local architecture document diverging from the authoritative repository document is classified `AgentKnowledgeDrift`/DRIFT; states scripts must not be ignored (a small script can implement a major architectural rule); Experiment 21: a destructive-command-blocking shell script counts as an actual enforcement mechanism even absent a formal service; defines hooks as `AgentEvent→Control` mechanisms; Experiment 22: a session-change logger is evidence for `AgentActionProvenance` but leaves completeness/reliability/retention questions open; states configuration archaeology reveals integration points but warns against exposing credentials; Experiment 23: a URL configuration reference is E2 evidence of an integration point, not proof of successful runtime communication.

**Theme 9 — Actual-vs-intended pipeline, `ComponentActual`, semantic boundaries, and the dependency graph (Experiments 24–26)** (8 rows). Defines the promotion path `Configuration→SuccessfulCall→RuntimeObservation` reaching E4; presents the actual-vs-intended pipeline `Intended→Architecture→{Implementation,Governance}→{Deployment,Authority}→Runtime→Evidence→Conformance`; defines the `ComponentActual=(ObservedRole,Dependencies,Interfaces,Data,Controls,Tests,Runtime,Owner)` tuple; Experiment 24: three overlapping actual services against one architected service is potential `BoundaryDrift` (classified OBS, not yet a violation); defines semantic boundary reconstruction as tracing `Responsibility→Data→Behavior→Invariant` (DDD-style archaeology); Experiment 25: two services mutating the same decision state is a potential aggregate/boundary violation (OBS); defines the actual dependency graph `G_actual=(V,E)`; states every edge requires provenance, with inferred dependencies weaker than observed runtime ones; Experiment 26: a source-level import can coexist with an unobserved runtime dependency (`StaticDependency=True`/`RuntimeDependency=NotObserved`).

**Theme 10 — Data flow, control flow, evidence-chain completeness, and the confidence formula (Experiments 27–30)** (9 rows). Defines actual data-flow reconstruction `Input→Processing→Storage→Output`; Experiment 27: a stored claim lacking any evidence relationship shows incomplete knowledge semantics despite an existing API; defines actual control-flow reconstruction `Request→Authorization→BusinessRule→Action→Audit`, warning post-action authorization is a serious control defect; Experiment 28: authorization following (not preceding) a protected action is classified VIOLATION; defines evidence-chain reconstruction `Claim→Artifact→Code→Test→Runtime` (`Chain=Incomplete` when any link is missing); Experiment 29: code+test evidence without runtime evidence yields `ImplementedAndVerified` but `RuntimeProven=Unknown`; defines `Confidence=f(EvidenceDepth,EvidenceIndependence,EvidenceFreshness)`, explicitly not a function of LLM confidence; states independent multi-source evidence outweighs duplicated single-source evidence; Experiment 30: two documentation sources both claiming something unimplemented remain Specified/Claimed, never Verified.

**Theme 11 — Output artifacts, the Evidence Ledger, negative evidence, hypothesis testing, and final verdict (Experiments 31–34)** (15 rows). Specifies five Step 109 output artifacts (ActualComponentInventory, ActualDependencyGraph, ActualDataFlow, ActualControlFlow, EvidenceLedger); defines the Evidence Ledger schema (ID/Claim/Evidence/Type/Strength/Status); states `NotFound≠DoesNotExist` — absence of found evidence is `NegativeSearchEvidence`, not proof of non-existence, unless the search is demonstrably exhaustive; Experiment 31: absence of a literal `Decision` class does not license concluding `DecisionCapability=False` (decisions may be represented elsewhere); prescribes a semantic-search (concept/behavior) strategy for reconstruction; states prior architectural hypotheses `H_1..H_n` must be tested against actual artifacts via `Search(H)→Evidence` yielding Confirmed/PartiallyConfirmed/Contradicted/NotEstablished; Experiment 32: a registry directory containing only agent configuration does not automatically confirm a prior "there is a registry" claim; warns against "architectural mythology" (the loose claim "we already have this" spanning designed/partially-implemented/prototyped/once-implemented/intended/manually-performed); defines an eight-value implementation status vocabulary (Designed, Prototype, Partial, Implemented, Verified, Operational, Governed, Deprecated); Experiment 33: a prototype-branch-only feature is classified Prototype, not Operational; distinguishes Deprecated (unused legacy) from Active; Experiment 34: an unused old script is a potential `LegacyArtifact`, not a current component; states the reconstruction quality criterion (evidence across eight dimensions: Components, Interfaces, Data, Rules, Agents, Tests, Runtime, Governance); records the Step 109 verdict PASS scoped to the methodology itself, with the honest implementation verdict `KnowledgeOS_actual=NotYetFullyMapped`; previews Step 110 (classifying actual artifacts into Core/Supporting/External/Agent-specific/Legacy/Unknown).
