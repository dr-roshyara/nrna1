## All rows (source_id order)

All 72 rows come from a single source file, S1001 (Step 102), in document order, grouped into 11 themes by section; 29 numbered "Experiments" run through the file testing each principle. Full text of every row is in `03-CONTRIBUTIONS.jsonl`.

**Theme 1 — Framing and the first empirical rule** (2 rows). Frames Step 102 as answering the narrower prerequisite question "what actually exists" before conformance judgment; states the first empirical rule — every architectural element must carry `EvidenceStatus`, never an assumed "Known".

**Theme 2 — Inventory layers and repository identity (Experiments 1–3)** (7 rows). Defines 14 inventory layers spanning repositories through human governance interfaces; Experiment 1: every discovered repository must receive a known identity/purpose; defines the repository identity tuple `Repo=(Name,Purpose,Owner,Lifecycle,Technology,Dependencies,Environment)`; Experiment 2: unclear purpose/owner yields `InventoryStatus=Incomplete`, never an assumed default owner; links unowned artifacts to GovernanceRisk (Step 97); states a repository may contain multiple distinct application types; Experiment 3: a multi-purpose repository must not be classified as one monolithic application.

**Theme 3 — Component identity, bounded contexts, and shared vocabulary (Experiments 4–5)** (5 rows). Defines `ComponentID` as required identity for every meaningful executable unit; defines the bounded-context inventory tuple `BC=(Purpose,Language,Entities,Commands,Events,Dependencies,Owner)`; Experiment 4: two modules sharing the term "Knowledge" with different meanings must not be merged; proposes a Term→Definition→Context vocabulary inventory; Experiment 5: three distinct occurrences of "Memory" must be investigated separately, not assumed identical.

**Theme 4 — Agent, registry, and hook inventory (Experiments 6–8)** (8 rows). Defines agent inventory categories (Agents, AgentHarnesses, AgentConfiguration, AgentSkills, AgentTools, …); restates the Claude≈Codex operating-contract principle; Experiment 6: engineering knowledge duplicated into `.claude/` from KnowledgeOS is a potential boundary violation; restates the pointer-layer principle `AgentConfiguration→KnowledgeOS` (never `=`); defines a five-state registry-existence classification (Exists/Partial/Specified/Unknown/Absent); Experiment 7: a described-but-unimplemented `PolicyRegistry` is `SpecifiedButMissing`; defines the hook inventory model `Hook→Trigger→Action→Invariant`; Experiment 8: an existing hook with no documented invariant needs semantic-role investigation.

**Theme 5 — Data ownership separation and schema inventory (Experiments 9–10)** (4 rows). Requires semantic (not necessarily physical) separation of OperationalData/KnowledgeData/EvidenceData/GovernanceData; Experiment 9: a single table mixing user state/knowledge/audit/AI-output is a potential aggregate/boundary problem; defines the schema inventory chain `Schema→Owner→Version→Consumers→MigrationPath`; Experiment 10: an unversioned schema is a `VersioningGap`.

**Theme 6 — Governance-artifact and CI/CD inventory (Experiments 11–13)** (6 rows). Requires locating actual instances of ADR/ArchitecturePrinciple/ArchitectureRule/VerificationRecord/Decision; Experiment 11: a Markdown-only ADR with no machine-readable link to implementation has incomplete automated traceability; defines CI/CD inventory categories (Build, Test, StaticAnalysis, SecurityScan, ArtifactGeneration, Deployment); Experiment 12: functional CI tests without architecture conformance checks show functional-but-not-architectural verification; defines the deployment inventory chain `Component→Image/Artifact→Environment→Version→Configuration`; Experiment 13: a version mismatch (repo 5.0 vs. production 4.7) is deployment drift.

**Theme 7 — Infrastructure, external dependencies, network boundaries, and secrets (Experiments 14–16)** (7 rows). Defines infrastructure inventory categories linked to prior Nexus-work infrastructure-discovery; defines the external-dependency tuple `Dependency=(Purpose,Protocol,Owner,Version,Criticality,FailureMode)`; Experiment 14: an unowned external dependency is a `DependencyGovernanceGap`; defines the network-boundary inventory `Component→NetworkZone→AllowedCommunication`; Experiment 15: network config allowing an architecturally-forbidden `Agent→ProductionDatabase` path is an architecture violation; defines the secrets inventory chain (`Secrets→Storage→Consumer→RotationPolicy`), constrained to never copy secret values; Experiment 16: a credential must be recorded as `SecretExists` without reproducing the value.

**Theme 8 — Observability and the machine-readable inventory requirement (Experiments 17–18)** (4 rows). Extends Step 99's observability model (Logs/Metrics/Traces/Alerts/RuntimeChecks) into the inventory; Experiment 17: a critical service with only logs (no metrics/trace correlation) has partial observability; states the inventory itself must be a versioned, provenance-bearing, confidence-scored, freshness-tracked machine-readable artifact; Experiment 18: an undated `ComponentExists=True` claim has weak freshness semantics.

**Theme 9 — Automated discovery, machine-discovery-is-not-classification, and the evidence-confidence hierarchy (Experiments 19–23)** (11 rows). Lists automated discovery mechanisms (RepositoryScanner, DependencyScanner, DeploymentScanner, RuntimeDiscovery); Experiment 19: a newly-discovered component not reflected in the inventory is `InventoryDrift`; states automated discovery (`Component=X`) is not the same as classification (`BoundedContext=X`, business capability, etc.); Experiment 20: a scanner identifying `policy-engine/` cannot automatically establish its organizational authority; defines the hybrid inventory formula `Inventory=MachineDiscovery+HumanKnowledge+AIAnalysis+Governance`; illustrates evidence-confidence scoring (direct repository evidence 0.99 vs. code-inferred business purpose, lower); Experiment 21: authority inferred only from naming convention is low-confidence, not authoritative fact; warns folder/repository names (`governance/`, `approved/`) never establish actual authority; Experiment 22: a file named `approved-architecture.md` does not gain authority from its filename; defines an evidence-strength hierarchy (`DirectRuntimeEvidence > DocumentationClaim` for runtime facts, etc.); Experiment 23: current runtime evidence overrides stale documentation for current state, while documentation remains evidence of original intent.

**Theme 10 — Snapshotting, diffing, and impact analysis (Experiments 24–26)** (6 rows). Defines `InventorySnapshot(t)` as a historical architectural state artifact; Experiment 24: an old snapshot remains reconstructable after later changes; defines the inventory diff operation `Diff(Inventory_t1,Inventory_t2)`; Experiment 25: a removed service between releases is reported as `Removed(ServiceB)`; extends diffing into impact analysis `Change→AffectedArtifacts→AffectedInvariants`; Experiment 26: a schema change traced to 14 consumers via the inventory graph generates potential verification obligations.

**Theme 11 — The typed inventory graph, the v1 deliverable, conflict handling, self-consistency invariants, and final verdict (Experiments 27–29)** (12 rows). Formalizes the architecture inventory as a typed graph `G_architecture=(V,E)` with typed nodes (Repository/Component/…); Experiment 27: a critical component with no `governedBy` edge is a governance gap; distinguishes KnowledgeOS's inventory (semantic and governance relationships between artifacts) from a conventional CMDB; names the target deliverable "KnowledgeOS Architecture Inventory v1" (a 15-part checklist); defines a six-value inventory Status enum (Confirmed/Probable/Inferred/Unknown/Missing/Conflicting), avoiding forced single-value resolution; Experiment 28: two documents disagreeing on ownership yields `Status=Conflicting`, not a latest-document-wins resolution; defines the conflict-resolution loop `Conflict→Investigation→Resolution→Decision→UpdatedKnowledge`; states four inventory self-consistency invariants (every critical component needs an owner, every production component needs an owner, …); Experiment 29: an ownerless production component is an `InventoryInvariantViolation`; restates KnowledgeOS's recursive self-analysis (`KnowledgeOS→Analyze(KnowledgeOS)→KnowledgeOfKnowledgeOS`); records the Step 102 verdict PASS with a different meaning than Steps 91–100 (only the inventory methodology, not the inventory's completeness, is verified); previews Step 103 (testing whether the real data model implements the Evidence→Knowledge chain).
