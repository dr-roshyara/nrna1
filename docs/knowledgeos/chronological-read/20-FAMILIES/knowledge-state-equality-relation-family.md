## Rationale
- [S1640] (ARGUMENT/RESTATEMENT) Preserved historical result: identity is not equality — two evidence objects e1,e2 can both support the same proposition p (Supports(e1,p) and Supports(e2,p)) without e1=e2; this affects provenance, deduplication, replay, validation, audit and merge, and is attributed to an earlier corpus reconstruction rather than newly derived here.
- [S1640] (EXPERIMENT/ARGUMENT) Operation test — Merge: Merge(K1,K2) cannot be specified using structural equality alone, since a1=(p,e1) and a2=(p,e2) sharing proposition p could legitimately merge to {a1,a2} (kept separate) or to a single combined-evidence assertion depending on ontology; Merge equality is semantic+identity+provenance dependent, with exact final semantics unresolved.
- [S1640] (EXPERIMENT/ARGUMENT) Operation test — Supersede: if Meaning(x1)=Meaning(x2) but Identity(x1)!=Identity(x2) and x2 supersedes x1, collapsing x1,x2 under semantic equality would destroy the supersession relation x2 succ x1 itself; supersession therefore requires an identity/version distinction, strongly suggesting semantic equality alone cannot serve as the sole equality relation.
- [S1640] (EXPERIMENT/ARGUMENT) Operation test — Replay: two distinct histories H1,H2 (H1 !=_H H2) can replay to the same current state K (Replay(H1)=Replay(H2)=K); Replay is treated by the corpus as a history/audit operation rather than another state transformation, and requires historical identity/equality independent of current-state equality.
- [S1640] (FORMALIZATION/ANALYSIS) The full operation/equality matrix across Merge, Supersede, Replay, Remove, Revise, Deduplicate, Validate rates each of structural/semantic/identity/historical/provenance equality as insufficient, required, relevant, potentially-required, or context-dependent per operation, with every row's overall status UNRESOLVED, NORMATIVE/DOMAIN-DEPENDENT (Deduplicate), or 'Assessment relation' (Validate); Remove requires identity for correct object targeting (must not remove a2 when removing a1 despite structural identity), Revise cannot use semantic equality as its sole target selector (must not implicitly revise x2 when revising x1 despite x1 equiv_sem x2), Deduplicate cannot be specified until its preservation policy is known (structural/semantic/identity/provenance criteria can each give different results), and Validate shows semantic state equality does not imply identical validation results because validation is a relation over (K,E) pairs, not K alone — reinforcing that not every operation is a state transformation T:K->K.
- [S1640] (ANALYSIS/WARNING) DDD interpretation: rather than one generic 'Equality' concept used everywhere, different bounded contexts legitimately require different named relations (same assertion, same evidence, same domain identity, same version, same semantic meaning, same observable state); a database PRIMARY KEY must not automatically be interpreted as SemanticIdentity, and a content hash must not automatically become DomainIdentity.
- [S1661] (ARGUMENT) Major architectural result: preserving provenance does not imply that semantic equality must be provenance-sensitive (K1 equiv K2 can hold under semantic equality with different Pi, while K1 cong_Pi K2 differs) — the two equality notions from Step 261 must not be conflated; validation only needs K to store sufficient provenance identity for deterministic resolution (the external service can hold the larger graph); and explanation of 'why does KnowledgeOS believe this' requires both Pi and History(T) together, reinforcing Provenance != History as two complementary rather than substitutable paths.
- [S1673] (VALIDATION/ANALYSIS) ARC E (State vs History, called 'the deepest and most honest arc') is independently checked and found genuinely sound where claimed: semantic minimality is correctly distinguished from mere syntactic compactness; the requirement that the equivalence relation be a congruence (not merely an equivalence) for the transformation set is correctly derived; the reflexivity/symmetry/transitivity proofs are verified correct but trivial (holding for any observational equivalence, establishing nothing KnowledgeOS-specific) — and importantly, the corpus itself does not overclaim them; hash identity is correctly kept distinct from semantic identity.
