## Rationale
Chooses Nexus as the vertical-slice subject because existing KnowledgeOS work already covers infrastructure discovery, version info, repository/blob-store info, runtime info, network info, migration requirements, governance questions, and architecture/change-management concerns — spanning Business/Architecture/Infrastructure/Security/Operations/Governance knowledge; but requires starting with Read->Analyze->Verify, not Agent->Production->Modify Nexus, to prove the semantic/assurance architecture without unnecessary operational risk [S1045]. Presents the workstream dependency graph and justifies the ordering: Agent Integration is not first because 'if the semantic foundation is unstable, the agents simply automate ambiguity' (do not scale agent access before authority is defined); the Graph is not first because a graph of poorly defined semantics produces 'fast confusion,' needing stable identities/ownership/relationships first; Governance is early because it defines ExpectedState (without which assurance has nothing authoritative to compare against, Governance->Assurance); Evidence is early because without it Verification becomes a bare assertion (Verdict->Evidence required) [S1045].
