## All rows (source_id order)

All 65 rows come from a single source file, S0995 (Step 96), in document order, grouped into 8 themes by section. Full text of every row is in `03-CONTRIBUTIONS.jsonl`.

**Theme 1 — `Evolution ⇏ Semantic Corruption`, historical immutability, and versioned knowledge (Experiments 1–5)** (11 rows). States the governing requirement of Step 96: KnowledgeOS must learn/evolve without silently corrupting meaning; formalizes learning as an explicit transition `K_{t+1}=Update(K_t,E_{t+1})`; Experiment 1: updating knowledge after a policy revocation must not rewrite the historical fact that the policy once held; states `CurrentKnowledge ≠ HistoricalKnowledge`; Experiment 2: both `P(t1)=True` and `P(t2)=False` must be retained, not overwritten; distinguishes five non-collapsible categories of knowledge change (Revision, Correction, Contradiction, Refinement, …); Experiment 3: new conditional evidence refines rather than contradicts an old unconditional statement; states knowledge evolution must be versioned (`K^(1)`, `K^(2)`, …) rather than one mutable blob; Experiment 4: a 2025 decision referencing `KnowledgeVersion=7` stays linked to version 7 regardless of the current version; states a model-generated prediction under `M_1` must not be silently reattributed to a later model `M_2`; Experiment 5 confirms `Model(Y_1)=M_1` is retained regardless of current model version.

**Theme 2 — Model provenance, performance evidence, and the learning loop (Experiments 6, 9, 11, 13)** (8 rows). Extends Step 92's decision-snapshot tuple to model-generated `Result=(InputVersion,ModelVersion,Configuration,…)`; Experiment 6: an AI compliance claim without traceable model/policy/evidence/context has weak reproducibility; states a trained model is itself a derived artifact requiring training-data provenance `M←trainedOn—D`; Experiment 9: a model deployed without training-data provenance cannot support strong data-coverage/quality claims; defines model-performance evidence via `Error=Loss(prediction,ObservedOutcome)`; Experiment 11: a prediction-outcome mismatch becomes evidence for further evaluation; defines the learning loop `Prediction→Action→Outcome→Observation→ModelEvaluation→ModelRevision`; Experiment 13: an unsupported counterfactual claim remains an inference, not an established fact.

**Theme 3 — Model-change impact classification and migration integrity (Experiments 14–17)** (8 rows). States a model update can affect decisions/workflows/risk/compliance/authorization/outputs, making model evolution itself a governance event; Experiment 14: a model update substantially changing `ApprovalRisk` must not be treated as an ordinary software patch; defines `Impact(M_1,M_2)` and `GovernancePath=f(Impact)`, scaling required assurance to impact; Experiment 15: a logging-format-only change has low semantic impact vs. a change modifying `AuthorizationDecision` logic; raises the schema-migration question (migrating old `Evidence(source)` records to a new schema); Experiment 16: assigning `provenanceLevel=Verified` to old records lacking that field, without evidence, is a fabrication; states migration must preserve epistemic status — it must not transform Unknown into Verified; Experiment 17: migrating `confidence=NULL` into `confidence=1.0` is semantic fabrication.

**Theme 4 — Backward/forward compatibility, unknown-must-remain-unknown, and multi-dimensional versioning (Experiments 18–22)** (10 rows). Defines backward compatibility (`Reader_new(Artifact_old)` must preserve the old artifact's original meaning); Experiment 18: a new version reading an old decision must reconstruct its original semantics or explicitly decline; defines forward compatibility (`Reader_old(Artifact_new)` must avoid silently misinterpreting unrecognized new fields); Experiment 19: an old component misinterpreting a `NewPolicyType` as `OldPolicyType` is potential semantic corruption; restates unknown-must-remain-unknown for forward compatibility (unrecognized X must stay Unknown, not be coerced to a known value); Experiment 20: an old component must not silently interpret an unrecognized `Collective` authority mode as `Single`; extends versioning beyond code to Schema/Model/Policy/Ontology/Workflow/AgentCapability/EvidenceConfidence; Experiment 21: independent software and policy version changes show one software version number is insufficient; defines the multi-dimensional version tuple `V=(V_software,V_schema,V_model,V_policy,V_ontology,V_workflow)`; Experiment 22: a decision recording only `softwareVersion=5.2` is insufficient to fully reproduce decision semantics.

**Theme 5 — Invariant regression, continuous-verification governance, and specification evolution (Experiments 25, 27–29)** (8 rows). States regression testing must check `InvariantRegression` (semantic invariants), not merely functional regression; Experiment 25: a new version passing all functional tests while allowing unauthorized execution (violating `I_A`) is an invariant regression; defines the continuous-verification governance loop `Change→ImpactAnalysis→Verification→Approval→Deployment→Observation`; Experiment 27: a model change with no impact analysis leaves the system unable to determine which invariants might break; defines the change-impact dependency graph `Change→AffectedModel→AffectedPolicy→AffectedComponent→AffectedInvariant`; Experiment 28: a schema-field change traced through the dependency graph reaches 37 affected components and 12 affected invariants; extends Step 91's `Implementation⊨Specification` to track evolution (`I_1⊨S_1` to `I_2⊨S_2`), requiring explicit traceability; Experiment 29: an implementation-only change needs only normal refinement verification, while a specification change needs a stronger check.

**Theme 6 — Historical-meaning preservation and ontology/concept evolution (Experiments 30–31)** (4 rows). States a new implementation must not retroactively change `Meaning(D_old)` for historical decisions; Experiment 30: automatically reinterpreting 2025 records under a new ontology's redefinition of "Approved" is a violation; defines ontology/concept evolution as requiring preservation of the old meaning, the new meaning, and an explicit mapping between them; Experiment 31: splitting a concept (`Application` into `Application`+`Service`) must not silently reclassify historical records.

**Theme 7 — `Learning ⇏ PolicyChange`, `Learning→Proposal ≠ Authority`, and `AdaptationBoundary` (Experiments 32–35)** (9 rows). States one of the step's strongest principles, `Learning ⇏ PolicyChange` — an AI's discovered patterns must not automatically become policy; Experiment 32: an AI's discovered better rule must become a `PolicyProposal`, not directly `PolicyEffective`; states `Learning→Proposal` does not imply `Learning→Authority` (governance stays separate from learning); defines the human-in-the-loop pipeline `AIProposal→HumanReview→Authorization→EffectivePolicy` for high-impact changes; Experiment 33: an unreviewed AI-proposed security-policy change must not automatically become authoritative; states autonomous low-risk adaptation is possible only if `AuthorizationToAdapt` is itself explicitly granted; Experiment 34: an AI's CacheTTL adjustment (60s→30s) is allowed since it falls within an explicitly authorized boundary; defines `AdaptationBoundary(A)` — changes within it may be autonomous, changes outside require human/governance review; Experiment 35: an AI attempting to change `ProductionAuthorizationPolicy`, when its adaptation boundary only permits low-risk changes, is out of bounds.

**Theme 8 — Final governed loop, the twelve invariants, and the versioned transition-system formalization** (7 rows). States the final governed learning loop `Observe→Learn→Propose→Evaluate→Authorize→Deploy→Observe`, explicitly re-entrant; states twelve new invariants including `I_HistoricalSemantics` (evolution must not silently change the meaning of historical records); records the Step 96 verdict PASS, closing the loop Knowledge→Learning→Evolution→Verification while forbidding Learning from acquiring unauthorized Authority; presents the self-evolving KnowledgeOS lifecycle as `Feedback→ModelEvolution→Verification→…`; formalizes KnowledgeOS as a versioned, distributed, governed transition system `K_t=(S_t,A_t,T_t,I_t,V_t,P_t,E_t)`; summarizes Steps 91–96 in a table (all PASS: refinement, concurrency, failure/recovery, security, privacy, learning); previews Step 97 (modeling real human+AI organizations jointly producing knowledge/decisions while keeping responsibility traceable).
