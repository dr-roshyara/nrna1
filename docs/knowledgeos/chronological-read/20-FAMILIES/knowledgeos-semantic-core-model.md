## All rows (62 rows, grouped by theme; source_id order within each theme)

### Theme 1 — Framing: the irreducible semantic core question and its falsification test
`[S1012]` — 4 rows condensed into this theme. States the central question of what is the irreducible semantic core of KnowledgeOS, distinguishing "many knowledge-ish objects" from what is actually load-bearing; restates the semantic-core hypothesis Evidence→Claim→Decision→Authority→Action→Observation with cross-cutting concerns; defines a ten-question falsification principle for admitting a candidate concept into the actual semantic core; and defines the minimal Evidence tuple (Identity, Source, Content/Observation, Timestamp, Provenance, Context[, Verification]).

### Theme 2 — Artifact vs. Evidence, and Observation as a pre-interpretation state (Experiments 1-3)
`[S1012]` — 7 rows condensed into this theme. Runs Experiment 1 (a file is an artifact, not automatically Evidence, until the system establishes an evidentiary relationship, PASS); states Artifact→Evidence is a semantic transformation, not identity (illustrated by Git commit→Observed change); runs Experiment 2 (a Git commit message interpreted by a verification process confirms Artifact≠Evidence but Artifact-can-become-Evidence, PASS); presents three competing evidence-ownership architectures (EvidenceAuthority/EvidenceAggregator/EvidenceProcessor-style designs) as an unresolved alternative; defines Observation as something observed with no interpretation yet applied, which may later become evidence; runs Experiment 3 (an uninterpreted runtime event is an Observation, not a Claim, PASS); and states Observation-supports→Claim while the observation itself remains distinct, valued for auditability.

### Theme 3 — Claim, Decision, and the Decision≠Recommendation boundary (Experiments 4-6)
`[S1012]` — 7 rows condensed into this theme. Defines Claim as a proposition asserted true within a context, distinct from and weaker than a Decision; runs Experiment 4 (an LLM-generated compliance assessment is an AI-generated claim, not automatically authoritative, PASS); defines a five-state claim lifecycle (Proposed/Supported/Accepted/Disputed/Superseded), conditional on implementation; defines the Decision=(Subject,Choice,Authority,Rationale,Evidence,EffectiveDate) tuple as stronger than a Claim; runs Experiment 5 (a documented recommendation is Recommendation, not Decision, PASS); states Decision≠Recommendation requires an identifiable Authority(Decision) per the governance model; and runs Experiment 6 (an agent recommending board approval has not thereby created the board's decision, classified Recommendation, PASS).

### Theme 4 — Authority and Action as explicit, non-reducible tuples (Experiments 7-9)
`[S1012]` — 7 rows condensed into this theme. Defines Authority=(Actor,Role,Scope,Rule,Validity), explicitly not reducible to a mere user ID; runs Experiment 7 (an "admin" user identity does not automatically equal ArchitectureAuthority, PASS); presents a worked four-row authority matrix requiring actual ownership to be established, not assumed; defines Action=(Actor,Intent,Target,Change,Time,Authorization), important because KnowledgeOS itself participates in the system it observes; runs Experiment 8 (an agent file edit can be reconstructed as AgentAction but is not necessarily a complete audit record, PASS); defines action provenance requirements Action→Actor/Intent/Evidence, with Actor=AgentIdentity for AI actions; and runs Experiment 9 (logged file changes without recorded agent identity constitute incomplete action provenance, PASS).

### Theme 5 — Verification, Finding, and Rule as distinct governance objects (Experiments 10-12)
`[S1012]` — 6 rows condensed into this theme. Defines Verification=(Rule,Input,Method,Result,Evidence,Timestamp) as distinct from Evidence; runs Experiment 10 (a passing test yields TestResult as evidence of verification, but Test≠Verification absent an explicit rule binding, PASS); defines Finding as a detected Expected≠Observed condition requiring attention; runs Experiment 11 (not every test failure is automatically a governance finding — may be infrastructure/flaky/development noise, PASS with an explicit warning); defines Rule as an Allowed/Forbidden/Required behavioral constraint connecting architecture to deterministic enforcement; and runs Experiment 12 (a documented rule sentence is a potential rule specification with enforcement status unknown until implemented, PASS).

### Theme 6 — Architecture-as-knowledge and the cross-cutting concerns of provenance and temporal validity (Experiment 13-14)
`[S1012]` — 5 rows condensed into this theme. Defines Architecture=(Components,Relationships,Constraints,Decisions,Views,Validity) explicitly as knowledge rather than a design artifact only; states provenance is a cross-cutting concern applying to Evidence/Claim/Decision/Action/Observation alike; runs Experiment 13 (identical-text knowledge objects from ArchitectureBoard versus an LLM cannot be treated as semantically equivalent, PASS); states ValidFrom/ValidUntil as a cross-cutting temporal-validity concern; and runs Experiment 14 (an agent retrieving a rule superseded yesterday must not treat it as current authoritative knowledge, PASS).

### Theme 7 — The candidate semantic-core graph, its decisive implementation test, and the minimality principle (Experiments 15-16)
`[S1012]` — 7 rows condensed into this theme. Presents the candidate semantic core as a graph (Authority-authorizes→Decision→{Evidence,Action→Observation}, etc.); states the decisive test is whether the implementation actually contains this candidate graph, warning against declaring SemanticCore_actual by assumption; defines three possible outcomes for actual semantic-core representation (Explicit/Strong, Distributed/Partial, Absent); runs Experiment 15 (absence of a distinct Claim entity alongside implied claim-like usage elsewhere is possible emergent-but-unformalized claim semantics, PASS with a warning); defines the semantic-core-minimality principle Core_minimal=argmin(Model) subject to Model⊢ObservedBehavior; runs Experiment 16 (if Artifact+Observation+Decision+Evidence already explain all behavior, a separate Claim entity may not be minimally necessary, PASS); and distinguishes the semantic core from a feature catalog (search/ingestion/embeddings/governance/audit), asking which concepts are load-bearing versus merely useful capabilities.

### Theme 8 — Capabilities as operations on the object model, and ablation experiments identifying the true invariant core (Experiments 17-20)
`[S1012]` — 6 rows condensed into this theme. Illustrates capabilities (Retrieve/Similarity/Authorize/Prove) as operations over the underlying object model rather than separate primitives; runs Experiment 17 (removing vector search leaves identity/provenance intact — the semantic core survives, PASS); runs Experiment 18 (removing provenance destroys traceability, significantly degrading semantic integrity, PASS); runs Experiment 19 (removing authority semantics collapses the recommendation-vs-decision distinction, PASS); runs Experiment 20 (removing temporal validity makes superseded rules indistinguishable from current ones, PASS); and proposes six candidate semantic-core invariants S1-S6 based on this ablation series, explicitly framed as hypotheses pending implementation confirmation.

### Theme 9 — The semantic truth hierarchy as a graph, and the per-edge machine-readability test (Experiments 21-22)
`[S1012]` — 7 rows condensed into this theme. Defines the semantic truth hierarchy RawData→Observation→Evidence→Claim→Decision as progressively stronger semantic status; cautions the hierarchy is a graph, not a linear pipeline (a Decision can become Evidence for a later decision); presents the full candidate semantic graph diagram, explicitly labeled a target model, not a claim about current implementation; defines the decisive per-edge reconstruction test — whether each semantic-graph relationship is machine-readably represented in the implementation; runs Experiment 21 (a specified Decision-supportedBy→Evidence relationship with no implementation counterpart is a documentation-only relationship, PASS/gap identified); runs Experiment 22 (a Markdown-only relationship is DocumentedRelationship, not MachineReadableSemanticRelationship, PASS); and illustrates candidate machine-readable decision fields (supporting_evidence[]/authority/effective_from/superseded_by).
