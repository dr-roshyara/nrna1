## Rationale
Lord proposes a CandidateAction; a governed execution layer separately checks Authorized?/Safe?/ContractSatisfied?/Allowed?; therefore 'Lord selects; Governance authorizes; Executor executes,' explicitly contrasted as much safer than a direct LLM -> Shell architecture. [S0899] Rejects a naive first formulation a*=argmax_a VOI(a) as insufficient because VOI captures only information/decision value and ignores authorization, safety, cost, urgency, dependencies, and reversibility. [S0899] Where probabilities are unavailable, proposes a qualitative ordering (HighValue > MediumValue > LowValue) or a partial preference relation q1 ⪰ q2, motivated by the principle that 'KnowledgeOS should not manufacture probabilities.'. [S0899] Worked example showing a qualitative preference (q1 directly unblocks the goal, q2 does not, so q1 ≻ q2) can be established without any numerical score — 'preferable when quantitative utility is unavailable.'. [S0899] Gives a concrete nine-step deterministic Lord algorithm (remove unauthorized; remove unsafe; remove dependency-violating; remove expired; rank by decision-critical gap reduction; apply cost/risk preferences; apply deadline; select if unique winner; escalate or tie-break if multiple), called 'ordinary computation,' answering 'can Lord itself be deterministic? Yes, if the action space and preference model are sufficiently defined.'. [S0899] Draws an analogy between the earlier inference architecture Inference(K,M) (M selects reasoning method) and SelectAction(K,P) (P selects decision preference), concluding 'Model and Policy are explicit,' preventing hidden reasoning. [S0899] Extends the Step 25F computability analysis specifically to Lord: core operations (graph traversal, candidate generation, constraint filtering, dependency analysis, rule evaluation, preference comparison, scheduling, state transitions) are normal computational workloads — 'a basic Lord without an LLM could run comfortably on an ordinary PC.'. [S0899]
