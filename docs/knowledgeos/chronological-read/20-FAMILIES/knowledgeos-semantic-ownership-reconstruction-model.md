## Rationale
This object addresses whether KnowledgeOS's proposed concepts (Evidence, Claim, Decision, Authority, and the rest) are genuine, software-enforced domain objects or merely names reused loosely across modules — a shift the document frames explicitly as moving "from component to semantic architecture" via the chain Data→Meaning→Invariant→Owner→BoundedContext [S1011]. The rationale is built by first establishing that raw data is not automatically knowledge: an ADR-approval string only becomes a Decision once subject/authority/timestamp/rationale/status/provenance are all present, and a bare status=APPROVED field is not sufficient semantic evidence of an authorized decision on its own [S1011]. From there the document argues that naming a concept is not the same as implementing it (ConceptMention≠ConceptImplementation) — four classes all naming "Evidence" establish shared terminology only, not proof of a coherent Evidence domain — and that each candidate concept's meaning must therefore be reconstructed from actual implementation semantics rather than assumed from its name [S1011]. This motivates treating "who owns the meaning" as a different question from "who stores the record": a BoundedContext is defined as wherever a coherent semantic model actually owns Concepts+Rules+Invariants+Language (BoundedContext≠Directory), so an `evidence/` directory containing only parsing/OCR/embedding code may be ingestion infrastructure rather than an Evidence bounded context [S1011]. Ownership identification is then grounded in enforcement rather than declaration: Invariant→Owner is named one of the strongest ownership-identification techniques (illustrated by Claim⇒EvidenceRequired), and the component that actually enforces a rule such as Approved⇒AuthorityPresent is argued to be the stronger owner candidate over one that merely manipulates the same data [S1011]. A further argument distinguishes belief from organizational status — True is not Authoritative, so an AI-generated architecture suggestion is a Recommendation, not an ArchitectureDecision, motivating an explicit four-stage authority-transition model Suggestion→Review→Decision→AuthoritativeState [S1011]. The document also argues that several recurring anti-patterns threaten semantic integrity if left undetected: semantic orphans (meaning present, owner unknown), semantic duplicates (two concepts with identical meaning and lifecycle), and — named as potentially the most serious pattern — semantic fragmentation, where one concept (e.g. Decision) is owned independently by multiple services, creating ambiguity about which one is true [S1011]. Fragmentation's proposed resolution is argued not to require physical database consolidation, but rather exactly one authoritative semantic owner with legitimate physical projections elsewhere (API views, search indexes, agent context caches) — none of which compete for authority provided their staleness relative to the authoritative source can be detected [S1011]. This same owner-vs-projection argument is extended to agent memory itself (Agent→AuthoritativeKnowledge: agent memory is a Projection, never an Authority) and to governance rules (Rule→Authority→AuthorityHolder, so a rule with no identifiable authority holder is a GovernanceGap) [S1011]. Finally, the document argues that different concepts legitimately need different lifecycles and invariant sets (DecisionStatus is not FindingStatus) and that an invariant only counts as real once its actual enforcement layer is identified — a README-only invariant is a DocumentedRule, not an EnforcedInvariant — which motivates a reusable semantic-core test: does removing a component destroy meaning (CoreCandidate), or merely reduce a technical capability (SupportingCandidate)? [S1011]

### Theme 2 — Concept identity vs. terminology, and context-relative meaning (6 rows)
Defines the semantic object tuple Concept=(Identity,Meaning,State,Invariants,Relationships,Authority,Provenance) as the basis for identifying genuine domain objects; lists ten candidate semantic concepts and states ConceptMention≠ConceptImplementation, tested by four classes all naming "Evidence" establishing terminology only, not a coherent Evidence domain (Experiment 2, PASS); states each candidate concept's meaning must be reconstructed from actual implementation semantics rather than an assumed definition, tested by Module A treating evidence as a source document versus Module B treating it as a runtime observation being a potential semantic collision (Experiment 3, OBS); and states Evidence_A≠Evidence_B across distinct contexts may be entirely legitimate — the problem arises only when the two are treated as the same concept without an explicit translation.

### Theme 3 — Bounded context and ownership-as-meaning vs. ownership-as-storage (5 rows)

### Theme 4 — Invariant enforcement and identity stability as ownership signals (5 rows)
