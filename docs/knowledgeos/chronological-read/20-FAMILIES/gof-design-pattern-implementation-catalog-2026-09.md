## Rationale
Visitor (double-dispatch operations over a stable object structure, with the explicit new-operation-cheap/new-element-type-expensive trade-off) rated potentially one of the most powerful patterns for KnowledgeOS, given the prediction that new analyses (Provenance/Explanation/Validation/Dependency/ImpactAnalysis/Serialization/Audit) will be added more often than new fundamental epistemic object types -- exactly the situation GoF identifies as suitable for Visitor [S2865]. Argues (drawing on the book's own behavioral-pattern discussion) that patterns are normally combined, not used in isolation, giving three worked combinations, and concludes Architecture != Pattern but rather Architecture = Composition of appropriate patterns [S2865]. Presents the book's Lexi document-editor case study (eight patterns applied to interacting design problems, not isolated textbook examples) as an architectural precedent KnowledgeOS should adopt: design problems and constraints first, pattern selection follows, exemplified by Lexi's choice of Visitor specifically because new analyses were expected more often than new element types [S2865]. Connects the implementation-mechanism decomposition (e.g. Observer, Strategy each decomposing into more primitive mechanisms) to the open K_min (kernel minimality) research question, stating Pattern != Primitive, Pattern != Capability, and Pattern != KernelOperation, and that a pattern implementing a capability never by itself establishes that capability's necessity [S2865].
