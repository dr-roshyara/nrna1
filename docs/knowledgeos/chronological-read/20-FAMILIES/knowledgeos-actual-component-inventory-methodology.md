Given the volume, rows are grouped into ten themes in their original sequence; every row is accounted for exactly once (75 rows condensed into these ten themes; full verbatim text for each remains in `03-CONTRIBUTIONS.jsonl`).

**Theme 1 — Component definition and units of analysis (rows 1-7, 7 rows).** Defines Component=Responsibility+Data+Behavior+Interface+Dependency+Evidence (a component is not merely its directory/class name) and the full reconstruction tuple C=(Identity,Purpose,Responsibilities,Data,Commands,Queries,Dependencies,Interfaces,Invariants,Tests,Runtime,Owner); distinguishes seven frequently-confused units of analysis (Class, Module, Package, Service, Application, DeploymentUnit, BoundedContext); Experiment 1 (PASS): a `KnowledgeService.java` class does not by itself establish a KnowledgeBoundedContext; defines a multi-level reconstruction tree (System->BoundedContext->{Application,Domain,Infrastructure}, Supporting Systems); states component identity must be stable independent of class naming; Experiment 2 (PASS): a renamed class may remain the same logical component.

**Theme 2 — Responsibility and ownership reconstruction (rows 8-20, 13 rows).** States responsibility must be reconstructed from actual Commands+Queries+DataMutations+Dependencies, not README claims; Experiment 3: a KnowledgeManager's actual behavior reveals its real responsibility; states the central rule ObservedBehavior>ComponentName; distinguishes Reads(Data) from Owns(Data); Experiment 4: the component that creates/changes a Decision is the stronger ownership candidate over one that merely reads it; defines the data-ownership graph with separate owns/reads edges; Experiment 5 (OBS, not yet proven): two services mutating the same decision table is potential shared-data coupling; defines the aggregate-ownership model Aggregate→Invariant→Owner; Experiment 6: two independent services both able to set decision.status=APPROVED without a shared invariant boundary is a potential violation; defines command ownership Command→OwningComponent; Experiment 7 (OBS): two services both implementing ApproveDecision is potential duplicate business responsibility; states DuplicateReadModel≠DuplicateDomainOwnership; Experiment 8 (PASS): a UI-projection endpoint alongside an authoritative domain API endpoint is not automatically duplicate domain capability.

**Theme 3 — Interfaces, dependencies, and layering (rows 21-30, 10 rows).** Defines Interfaces(C)=Inbound+Outbound (5 inbound / 6 outbound categories); Experiment 9 (PASS): a component with both API-exposing and API-consuming interfaces records both; classifies communication Sync vs Async; Experiment 10 (DRIFT): documented event-driven architecture contradicted by universal synchronous REST calls; defines a four-way dependency classification (Domain/Application/Infrastructure/External); Experiment 11 (OBS/DRIFT): a domain object importing a PostgreSQL driver is a potential layering violation; defines layer reconstruction Presentation→Application→Domain→Infrastructure, noting intended dependency direction must come from actual architecture rules; Experiment 12: infrastructure calling domain logic may be valid under dependency inversion, requiring semantic interpretation; distinguishes DomainConcept from TechnicalCapability; Experiment 13 (PASS): a component performing only EmbeddingGeneration is technical infrastructure, not domain logic.

**Theme 4 — Ubiquitous language and semantic collisions (rows 31-35, 5 rows).** Prescribes extracting UbiquitousLanguage from classes/APIs/schemas/tests/workflows/documentation and comparing across artifact types; Experiment 14 (OBS): four different terms (Evidence/Document/Artifact/Knowledge Item) used across layers for what may be one concept; defines semantic collisions (SameTerm->DifferentMeaning), warning 'Knowledge' meaning document/embedding/claim/fact/decision/observation across modules is dangerous; Experiment 15 (OBS): two modules using 'Knowledge' with incompatible semantics is a potential bounded-context language collision; defines semantic duplication (DifferentTerms->SameMeaning), illustrated by Evidence/Artifact/SourceRecord potentially indicating accidental duplication.

**Theme 5 — Cohesion, coupling, and bounded-context candidate criteria (rows 36-44, 9 rows).** Defines Cohesion(C) based on relationship among a component's commands/data/invariants/dependencies; Experiment 16: a component spanning six unrelated responsibilities shows very low cohesion; defines Coupling(A,B), noting strong coupling is not automatically bad but unexplained coupling is valuable evidence; Experiment 17 (OBS): a governance component directly accessing six unrelated domain tables is potential excessive coupling; states HighCohesion+HighCoupling clustered around a coherent concept may indicate a bounded-context candidate; Experiment 18 (BOUNDARY CANDIDATE): strongly clustered evidence-related data/commands/rules/APIs/tests; states prior bounded-context candidates (Evidence/Voting/Appointment-Mandate/Contestation/Adjudication) must not be assumed to apply automatically to KnowledgeOS; Experiment 19 (DRIFT): an architecturally-named EvidenceContext implemented across 8 unrelated modules is a potential implementation mismatch; states ComponentInventory≠BoundedContextMap, with the inventory strictly preceding Components->ResponsibilityClusters->BoundedContextCandidates.

**Theme 6 — Runtime identity, lifecycle, ownership, criticality, verification (rows 45-54, 10 rows).** Defines runtime identity LogicalComponent→DeploymentUnit→RuntimeInstance; Experiment 20 (PASS): one logical component deployed as three containers is one logical component with three runtime instances; defines a four-value lifecycle status (Active/Experimental/Deprecated/Retired); Experiment 21 (PASS): a component with disabled deployment is potentially Deprecated/Inactive; defines Owner(C) with five owner categories (team/product/architecture domain/platform/external provider); Experiment 22 (PASS): an unestablishable owner yields Owner=Unknown, itself a governance finding; defines Criticality(C) in {Critical,High,Medium,Low} based on impact not code size; Experiment 23 (PASS): a small 50-line authorization service controlling production changes is potentially Critical despite its size; defines per-component Verification(C) identifying unit/integration/architecture/security/runtime tests; Experiment 24 (PASS): a critical governance component with no automated tests is an AssuranceGap.

**Theme 7 — Component Evidence Card and the relationship graph / architecture smells (rows 55-59, 5 rows).** Specifies the 16-field Component Evidence Card schema as the atomic unit of reconstruction; defines the component relationship graph G_C=(Components,Relationships) with eight relationship types; Experiment 25 (PASS): two components both writing to a shared database surfaces a potential ownership conflict; defines five architecture-smell patterns detectable from the graph (Hub, Circular dependency, Shared-database coupling, Orphan, Duplicate capability), framed as signals not violations; Experiment 26 (PASS): a graph cycle A→B→C→A is flagged CircularDependencyCandidate.

**Theme 8 — Agent-component relationship mapping (rows 60-64, 5 rows).** Defines agent-component relationship mapping: Claude/Codex to KnowledgeOS, Agent to Repository/Verification/Evidence; Experiment 27 (OBS/DRIFT): Claude modifying the repository while bypassing KnowledgeOS governance is a potential agent governance boundary violation; states a shared VerificationEngine between Claude and Codex is useful evidence of a common assurance layer; Experiment 28 (OBS): incompatible per-agent verification mechanisms is potential assurance fragmentation; presents the ideal shared-infrastructure diagram (KnowledgeOS with Common Rules/Evidence/Governance shared by Claude and Codex) contrasted with the undesired per-agent-silo pattern.

**Theme 9 — Inventory status model and confidence scoring (rows 65-68, 4 rows).** Defines a seven-value component inventory status model (Confirmed/Candidate/Legacy/External/Duplicate/Overlapping/Unknown), avoiding premature architecture decisions; Experiment 29 (PASS): two apparently-duplicate components are classified DuplicateCandidate, not immediately marked for deletion; defines Confidence(C)=f(Structure,Source,Tests,Deployment,Runtime) with High/Medium/Low compositions (Source+Tests+Runtime / Source+Tests / DocumentationOnly); presents an illustrative actual component map (KnowledgeOS->Knowledge/Governance/Assurance->nine components C1-C9) with labels required to come from actual repository evidence.

**Theme 10 — CoherentBoundaries diagnostic, outcomes, and anti-premature-redesign discipline (rows 69-75, 7 rows).** States the central discovery criterion CoherentBoundaries: whether Responsibility->Data->Behavior->Ownership align, more important than component count; defines three mutually exclusive architectural outcomes (Coherent, Fragmented, Monolithic) each leading to materially different conclusions; Experiment 30 (potential MonolithicKnowledgeOSCore): evidence/governance/agent-control/runtime-assurance sharing one monolithic service and tables; defines the converse ArchitectureFragmentation outcome, illustrated by Evidence spanning four unrelated implementations and Governance spanning three different mechanisms; states a strict anti-premature-redesign discipline: ObservedArchitecture->TargetArchitecture->Gap->Remediation in that order, never jumping to a redesign conclusion; records the Step 111 methodology pipeline Repository->Component->Responsibility->Data->Interface->Dependency->Verification->Runtime, naming the KnowledgeOS Actual Component Inventory; previews Step 112 (reconstructing Data->Meaning->Invariant->Owner->BoundedContext) to test whether KnowledgeOS has a genuine semantic core or is an aggregation of unrelated tools.
