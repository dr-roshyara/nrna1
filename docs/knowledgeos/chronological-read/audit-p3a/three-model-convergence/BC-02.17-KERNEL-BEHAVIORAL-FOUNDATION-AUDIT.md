## Executive summary

**Central question answer**: the corpus **does** contain a source-grounded behavioral definition of
Kernel — but it is a **historical-primary-corpus design principle that was never executed, was dropped
by the very next research step the same day, and was only rediscovered a full research generation
later**, not a settled mathematical theorem. `ABK-1` — the other candidate the prior audit flagged —
turns out to be **not one object at all**, but a name reused for two incompatible constructions, both
already self-demoted by their own authors from "the Kernel" to "an unratified candidate representation"
within the same two-hour writing session.

**The single most important correction this audit makes to BC-02.15-KERNEL's framing**: Rule 258
(`258.35`/`258.21`) is **not** later mathematical research — its actual source,
`20260830-190941_step_258_identity-equality-and-knowledge-state-equivalence.md`, is dated 2026-08-30,
the same day as Steps 272a/272b/273, and sits squarely inside the historical primary corpus. Neither
Step 272a, 272b, 273, nor `S1792` (Step 276) cites it — confirmed by direct grep, zero hits. **Step
258's own lineage was dropped by the corpus's own subsequent work, and only independently rediscovered
by the much later (2026-08-31 onward) `knowledgeos_kernel/` research programme.** This changes Rule
258's evidentiary weight from "an interesting later research proposal" to "an abandoned historical
design principle the theory's own original authors proposed and then never followed up on" — a more
consequential, and more sobering, finding than either reading alone.

**Bottom-line answer to the final research question (§20)**: the strongest mathematically supported
meaning of "Kernel" the corpus currently permits is **not a single definition** — it is **a historically
sanctioned *criterion* for what a Kernel definition would have to satisfy** (behavioral sufficiency,
per Rule 258.35/258.21), **never itself executed to produce an actual Kernel**, standing alongside **at
least four independently-constructed, mutually `UNWITNESSED` candidate formalizations** (Kernel A–D
below), none of which is shown to satisfy that criterion, and one of which (`ABK-1`) is not even a
single coherent object. **The corpus has supplied a defensible test, not yet a defensible answer.**

## 3. Rule 258.21 formal audit

**Exact statement**: *"For a property `p`, define `Relevant(p)` if there exists a mandatory operation
`T` and states `K_1,K_2` differing only in `p` such that `T(K_1,c)≢_K T(K_2,c)`. Then `p` cannot be
discarded from the semantic state representation unless it is supplied externally to the operation.
This gives us a principled way to discover the minimal kernel."*

| Sub-question | Finding |
|---|---|
| 1. What is `p`? | Any candidate state-component/property, generic and unenumerated |
| 2. What is `T`? | A member of `𝒯`, unenumerated |
| 3. What is `c`? | "An admissible common context" — not formally typed in this file |
| 4. What is `≢`? | Negation of `≡_K` (§258.8) — "distinguishable by ≥1 observation in `𝒪`" |
| 5. "Differ only in `p`"? | **`UNDEFINED IN SOURCE`** — used informally, presupposing a decomposable representation. **A self-tension the source itself does not resolve**: this presupposes separable "properties," sitting oddly next to `258.35`'s own anti-compositional conclusion |
| 6. Mandatory-operation universe? | `𝒯`, explicitly open/unenumerated |
| 7. Does "relevant" mean "necessary"? | **No** — `Relevant(p)` triggers a *three-way disjunctive* consequence (§258.31: enrich `K`; supply `p` as explicit context; or remove the operation from the semantic core) — not a direct "`p`∈`K`" conclusion |
| 8. Relevance ⟹ necessity? | **No, not deterministically** — only one of three resolutions actually adds `p` to `K` |
| 9. Necessity ⟹ minimality? | Not addressed — minimality is a *global* closure condition; `258.21` only tests one property at a time, never states the converse |
| 10. Unique kernel identified? | **Not claimed** — gate table marks "Minimal `K`" 🔴 |
| 11. Inclusion- or cardinality-minimal? | `UNDEFINED IN SOURCE` in this exact vocabulary — phrasing reads closer to inclusion/behavioral-minimality, but the terms are never used |
| 12. Depends on chosen operation set? | **Yes, explicitly** — existentially quantified over `T∈𝒯`, and `𝒯`'s own membership is itself negotiable per §258.31's third resolution |
| 13. Depends on chosen context/task? | Implicitly yes (context is an explicit argument to `T`); no worked counterexample for this specific dependency |
| 14. Depends on chosen equivalence relation? | **Yes, explicitly** — `≢` is defined via `≡_K`, itself relative to the unenumerated `𝒪`. `Relevant(p)` is **doubly parametrized**, by both `𝒯` and `𝒪` |

## 4. Rule 258.21 ↔ `bandtest.py` correspondence table

`bandtest.py`'s actual mechanism (canonical-construction, re-read in full this pass): a hand-authored
`NEEDS` dict maps each of 18 named operations to a fixed set of K-component labels it "requires... in
order to be well-defined." The removal test computes, for each component, whether it appears in the
`NEEDS` set of any of the 14 forced operations — a pure **static set-membership lookup**, never an
executed, behavioral, two-state divergence test.

| Rule 258.21 | `bandtest.py` |
|---|---|
| Property `p` | A component label (`A,R,S,EL,Dt,PI,T,H`) |
| Mandatory operation `T` | One of the 14 `LOWER` (forced) operation names |
| Context `c` | **Absent** — no context parameter exists anywhere in the script |
| `K_1,K_2` differing only in `p` | **Absent** — no state pair is ever constructed; only set-membership in `NEEDS[o]` is checked |
| Behavioral output | **Absent** — no operation is executed; `NEEDS` is a hand-authored table, not runnable operation logic |
| Equality/equivalence `≢` | **Absent** — no equivalence relation is ever computed |
| Removal operation | Set-theoretic exclusion of a component, then re-checking table membership |
| Failure criterion | `comp∈NEEDS[o]` for some forced `o` (table lookup) — not "`T`'s output differs between two states" |
| Minimality conclusion | Necessity = declared as a listed dependency of some forced operation's *definition*, not = demonstrated behavioral divergence upon removal |

**Explicit relationship classification: `B — methodological analogy`**, not `C`/`D`/`E`. Both share the
intuition "necessity ⟺ removal breaks something," but they are structurally different kinds of test:
`258.21` is a genuine extensional/behavioral criterion requiring two actually-differing states, a
context, and an evaluated inequivalence; `bandtest.py` is a purely intensional/declarative
dependency-table lookup with no instantiated states, context, or equivalence relation. This does not
even rise to "same criterion applied to different universes" (`D`), since the *criteria themselves*
differ in kind. **Per Stop Condition D: recorded as `ANALOGOUS METHODOLOGY`, not `SAME`.**
