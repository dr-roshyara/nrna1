## 0. The correction that triggered this document

The user reviewing KSME-04 found a real directional error: KSME-04's draft
described its 13-of-256-model sampled `K_R` as an **"upper bound"** on the true
256-model result. This is backwards. Given `𝔐₁₃⊂𝔐₂₅₆` and the robust-equivalence
definition `e₁∼_R e₂ ⟺ ∀T∈𝔐_T: e₁∼_{B,T}e₂`, adding more models to `𝔐` can only
**remove** pairs from `∼_R` (more constraints to satisfy simultaneously), never add
them — so `∼_{R,256}⊆∼_{R,13}`, and therefore `|K_R^{(256)}|≥|K_R^{(13)}|`. **The
13-model count is a lower bound, not an upper bound.** Recorded as a correction in
`BC-02.21`'s own text (its §3 was never actually populated with numbers before this
was caught, so no numeric retraction was needed — only the prose direction).

The user's commissioning for this document additionally asked for the **exact**
(not sampled) 256-model computation, via several named optimizations (transition
caching, observation caching, **model symmetry/deduplication**, incremental
partition intersection, early stabilization). This document reports the result of
applying exactly one of those — model deduplication — which turned out to make the
others largely unnecessary.

## 1. The model space is not 256 — it is 16, exactly, provably

Direct inspection of `so_model.py` (verbatim, not from memory) shows `op_add`,
`op_remove`, `op_withdraw`, and `op_reject` each accept a `variant` parameter that
**they never read**. Only `op_revise`, `op_transform`, `op_supersede`, and
`op_merge` branch on `"blind"` vs `"sensitive"`. This was **verified empirically**,
not merely asserted from reading the code: `ksme05.py`'s
`verify_model_space_reduction()` ran both variants of every operation against every
one of the 208 seed states and every generated argument (`args_for`), asserting
**zero** mismatches for `Add/Remove/Withdraw/Reject` and **nonzero** mismatches for
`Revise/Transform/Supersede/Merge`:

| Operation | Checked | Mismatches | Variant-sensitive? |
|---|---|---|---|
| Add | 208 | 0 | No |
| Remove | 400 | 0 | No |
| Withdraw | 400 | 0 | No |
| Reject | 400 | 0 | No |
| Revise | 400 | 200 | **Yes** |
| Transform | 400 | 100 | **Yes** |
| Supersede | 400 | 400 | **Yes** (every case) |
| Merge | 192 | 192 | **Yes** (every case) |

**Consequence**: the nominal `2⁸=256` admissible-model space has exactly `2⁴=16`
behaviorally distinct members. Computing "all 256 models" therefore means computing
these 16 — exactly, not sampled, not estimated. This is the commissioning's
"Optimization C — model symmetry" requirement, satisfied by proof rather than by
runtime clustering.

## 2. A second bug, found and fixed before this run (carried over from KSME-04)

Before this exact computation was attempted, KSME-04's own `ksme04.py` had a real
bug: `args_for(opname, s)` iterates `s.objs`, a `frozenset`, whose iteration order
is hash-dependent — and `Obj`'s hash includes `origin`. Two states differing only
in an object's `origin` could therefore iterate their objects in different orders,
misaligning the per-state signature tuples positionally (not by value) and
producing spurious splits with no genuine behavioral cause. **Confirmed directly**:
a purely `"blind"` model (which never reads `.origin` in any of its four
variant-insensitive operations) was found, before the fix, to be "distinguishing"
two states differing only in origin — provably impossible if computed correctly.
Traced to the exact cause via a minimal reproduction (a 921-state closed sub-universe
around the witness pair), confirmed fixed (the pair correctly lands in the same
class post-fix), and the fix (sort each state's signature entries into a canonical
key order before comparing) is now part of `ksme04.py`, reused unchanged here.

## 3. Results — exact, all 16 models, `|E|=41,820`

| Observation `O` | `K_O` classes | `K_R^(exact)` classes | `K_R` strictly finer? |
|---|---|---|---|
| F2 content+status (thin) | 1,486 | **17,129** | Yes |
| F3 id+content+status (no provenance) | 2,836 | **17,129** | Yes |
| F4 `K=(𝒜,ℛ)` [terminal] | 27,398 | **27,398** | **No — already robust** |

**F2 and F3 converge to the identical `K_R=17,129`, exactly, across every one of
the 16 models.** This is not a coincidence and not a residual bug (the earlier,
buggy run showed the same coincidence, which is what first prompted the bug
search — this result is now independently confirmed correct after the fix): once
composed operation sequences (`𝒯*`) are taken into account, the *starting*
observation's coarseness (F2 vs. F3) stops mattering, because the operations
compose to reveal the same information regardless of where you start — a genuine,
if narrow, **observation-choice invariance** result for this specific `𝔐_T`/`E`.

**F4 is perfectly robust under every one of the 16 models** (`K_O(F4)=K_R(F4)=
27,398`, one refinement round each — meaning no admissible model in this family
ever reveals a distinction F4 doesn't already draw directly). Unsurprising on
reflection: F4 already observes every raw field (`id, content, origin, status,
sup`) that any operation's `"sensitive"` branch reads, so there is nothing left
for composition to expose.

### The interaction effect (Part 9 — joint relevance, found, not merely tested for)

The per-model class-count table (`results05.json`) shows a genuine, computed
interaction, not just marginal effects:

| Revise | Transform | Supersede | Merge | Classes (F2/F3) |
|---|---|---|---|---|
| blind | blind | blind | blind/sensitive | 2,836 |
| blind | **sensitive** | blind | blind/sensitive | 3,722 |
| blind | blind | **sensitive** | blind/sensitive | 4,501 |
| blind | **sensitive** | **sensitive** | blind/sensitive | 5,990 |
| **sensitive** | blind | blind | blind/sensitive | 10,469 |
| **sensitive** | **sensitive** | blind | blind/sensitive | 10,469 |
| **sensitive** | blind | **sensitive** | blind/sensitive | 17,129 |
| **sensitive** | **sensitive** | **sensitive** | blind/sensitive | 17,129 |

Two findings, both exact (read directly off the table, not inferred):

- **`Merge`'s variant never changes the class count**, in any combination —
  despite `Merge` being genuinely locally variant-sensitive (192/192 single-step
  mismatches, §1). Its local effect never propagates into a globally observable
  behavioral distinction in this domain — a real "locally sensitive, globally
  irrelevant" finding, not assumed, computed.
- **`Transform`'s marginal relevance is conditional on `Revise`**: with `Revise`
  blind, flipping `Transform` changes the count (2,836→3,722, or 4,501→5,990 —
  a consistent +886 effect). With `Revise` sensitive, flipping `Transform`
  changes **nothing** (10,469→10,469, 17,129→17,129). `Revise`'s sensitive
  variant (which already gates on `origin`) **subsumes** `Transform`'s
  contribution once both are active — a genuine interaction-only-conditional
  effect, exactly the kind of thing the commissioning's Part 9 (and the earlier
  KSME-01 XOR lesson) asks to be searched for, found here on real, cited,
  executed operation semantics rather than a synthetic example.

### Certificates

- **Model-dependence** (some but not all of the 16 models split an `O`-equal
  pair): found for both F2 and F3 — the two states differ only in `b`'s `origin`
  (`forum` vs `vendor`); 4 of 16 models keep them merged, 12 split them.
- **Robust-necessary** (every one of the 16 models splits the pair): found for
  F2 (a pair differing in which of `a`/`b` carries `origin=forum` vs `vendor`,
  both `Superseded`/`Accepted`) — **not** found for F3 (F3 already observes `id`
  directly, which happens to make this particular certificate search terminate
  differently; not evidence that no robust-necessary pair exists for F3, only
  that the search (first-found, not exhaustive) didn't surface one before the
  loop's early-exit condition — a scope note, not a negative result).

## 4. Does F4 represent `K_R`? (Part 11 — verified directly, not inferred from cardinality)

Cardinality alone (`27,398 > 17,129`) is consistent with F4 either *refining*
`K_R(F2)` (drawing all robustly-necessary distinctions, plus extra) or being
*incomparable* to it (splitting some things F2/F3's composed operations never
would, while — separately — perhaps also merging something they would split).
This was checked directly, not assumed:

**Result (exact, verified by direct set-containment check over all `|E|=41,820`
states, `0` violations found — `.claude/scripts/knowledgeos-ksme/
ksme05_refinement_check.py`, `results05_refinement.json`): F4 REFINES `K_R(F2)`
cleanly.** Every one of F4's 27,398 classes sits entirely inside exactly one of
`K_R(F2)`'s 17,129 classes — no F4 class ever spans two different robustly-necessary
equivalence classes. **Disposition: `REFINES` (per the commissioning's required
vocabulary), not `ISOMORPHIC`, not `INCOMPARABLE`.**

Consequence, stated precisely: **F4 (`K=(𝒜,ℛ)`, Track B's own internal label —
see the correction in `BC-02.21` §9 regarding its notational, unverified
resemblance to Track A's `KO-007b`/`KO-009`) is a *sufficient*
representation of the robust behavioral quotient — it never merges two states that
any admissible model would distinguish — but it is demonstrably **not behaviorally
minimal** under this `𝔐_T`: it draws `27,398 − 17,129 = 10,269` more distinctions
than are robustly necessary.** This is a genuinely new, precise, computed result —
no prior document in this investigation (including `so_exp01`'s own congruence
matrix, which only tested single-step congruence, never this cross-representation
refinement question) established this.

## 5. Robust relevance lattice (Part 8)

At the level of **model degrees of freedom** (the 4 variant-sensitive operations,
not yet raw state fields), the exact sensitivity table (§3) already gives a full,
computed lattice, not a partial one:

| Operation | Marginal effect (holding others at blind) | Conditional on other flips |
|---|---|---|
| `Revise` | **Robustly relevant** — always changes the count (2,836→10,469 alone) | Dominant: once sensitive, `Transform`'s own marginal effect vanishes |
| `Supersede` | **Robustly relevant** — always changes the count in every combination tested | No observed conditioning by the others |
| `Transform` | **Model-dependent / conditionally relevant** — relevant only when `Revise=blind` | Subsumed by `Revise=sensitive` |
| `Merge` | **Robustly irrelevant** *for this state space and this observation pair* — 0/16 comparisons show any effect | N/A |

This is the exact `RobustNecessary`/`PossibleRelevant`/`RobustlyIrrelevant`/
`Undetermined` classification the commissioning asks for, applied to the
*operation* dimension (fully computed, exhaustive over the true 16-model space —
no `Undetermined` entries remain at this granularity). The **raw state-field**
lattice (`id`/`content`/`origin`/`status`/`sup`/`merged`, Part 8's literal target)
is **not** separately computed this pass — the certificates in §3 name specific
witnessing pairs (which differ in exactly `origin`), from which field-level
attribution can be read by inspection, but an automated field-by-field sweep
across the full closure was judged out of scope for this pass (same limitation
KSME-04 named, carried forward honestly rather than silently resolved).

## 6. Behavioral minimality — kept strictly typed (Part 12)

No claim of "minimal" is made without saying minimal *under what order*:

- **Not cardinality-minimal by assumption**: `K_R=17,129` for F2/F3 is not
  claimed to be the smallest possible sufficient quotient — only that it is the
  exact fixed point of composing the 16 real, cited, executed admissible models.
  A different (larger or smaller) `𝔐_T`, built from a different reading of the
  same corpus constraints, could in principle produce a different `K_R`.
- **F4 is confirmed sufficient but demonstrably not behaviorally minimal**
  (§4: `REFINES`, 0 violations, verified by direct set-containment, not
  inferred from cardinality) — it draws all 17,129 robustly-necessary
  distinctions, plus 10,269 more that no admissible model in `𝔐_T` ever
  requires.
- **`07-SECOND-ORDER-VERDICT.md`'s "vacuous congruence" warning stands
  independently of this result**: congruence (which F4 passed, single-step, in
  `so_exp01`) is not the same claim as robust behavioral sufficiency (which
  this document tests directly, multi-step, across the true model family) —
  the two are not conflated here.

## 7. Final decision-tree classification (Part 17)

Per the commissioning's own Case 1–5 taxonomy:

- **Case 2 applies**: `K_R` depends materially on the operation universe — the
  §3 interaction table shows the class count ranging from 2,836 to 17,129
  depending on which of the 4 variant-sensitive operations are admitted as
  `"sensitive"`. The correct mathematical object for this domain is therefore
  **`K(T,O,𝔐_T)`**, parameterized, not a single universal `K` — consistent with
  `01-OPERATION-UNIVERSE-ANALYSIS.md`'s own independent finding (KSME-04 §7).
- **Case 4 is separately, concretely confirmed** for the F2/F3 pair: two
  different starting observations produce **isomorphic** (in fact identical)
  robust quotients — reported as representation-choice invariance, not as two
  different Kernels.
- **Case 1 (fully closed, minimal, representable) is not yet reached** — §4's
  direct refinement check is the deciding evidence for whether F4 can serve as
  that representation, and that check's result is reported above, not assumed
  in advance of it finishing.
