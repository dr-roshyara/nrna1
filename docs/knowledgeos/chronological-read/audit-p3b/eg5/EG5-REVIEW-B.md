## B-01 — MATERIAL — EG-5b's blast radius is universal, not "≥2 register-bearing labels", and it independently blocks BOTH canary batches today

**Severity:** MATERIAL (corrects the severity/scope claim in A's own new finding, which is the thing governance will read to prioritize)

**A's claim (spec top-of-file and §6.3):** *"New finding raised: EG-5b … It blocks every batch with two or more register-bearing labels, not only EMPTY."* The §6.3 narrative frames the defect as a collision problem: independently-numbered `rs_id`/`gap_id` from ≥2 final runs collide once you rewrite them to a shared `run_id`.

**What I verified independently.** I ran two synthetic probes against the *production* verifier via `r7_full_fixture.py` (scripts in this review's scratchpad: `probe_eg5b.py`, `probe_eg5b_2.py`), each touching **exactly one label**, with **zero possibility of a numeric collision**:

1. Set only the SINGLE label's *object* `run_id` to its dispatched run id (`OB9004-R7-L03`, per `U.run_owner`) instead of the batch id (`OB9004-R7`), leaving every other record untouched → `BATCH-FAIL`, `predicates: {"U": "F", ...}`, failure `G-07 relation-8-tuple-vs-triple-reduction: provenance ids`.
2. Set only that same label's *register* records' `rs_id`/`run_id` to the dispatched run id (keeping the numeric suffix as originally assigned — still unique, still one label) → `BATCH-FAIL`, failures `G-07 …: rs_id not <run_id>:<batch_id>:<n>` **and** `G-07 …: provenance ids`, one pair per register record.

Both fail with a **single register-bearing label present and no second label involved at all**. The reason is structural, not a collision artifact: `p3b_s5_verify.py:306-339` fixes one batch-level `run = f"{batch}-R7"` for the whole R7 verify call, and G-07 (`V:511-513` for objects; `V:929-930`/`955-957` for register; `V:988-989`/`990-992` for gap) compares **every** record's `run_id`/`rs_id`/`gap_id` against that single batch-level value — never against the label's own final run. This is unconditional on how many register-bearing labels exist.

**Why A's own probe already proved this, but the framing buries it.** A's §6.3 states: *"Probe (synthetic mutation of FX): setting one SINGLE object's run_id to its dispatched run id turns BATCH-PASS into BATCH-FAIL."* That is exactly my probe 1 — a **single-label** test. A ran the single-label experiment and got the universal result, then wrote it up as if the defect were about ≥2-label collisions. The ≥2-label collision (A's §6.3 bullet 2, `T-21`) is a **second, independent** failure mode that only becomes visible *after* you adopt resolution (a) (force every record's `run_id` to `<B>-R7`) — but the *primary* defect (the dispatched-id vs. batch-id mismatch) already fails universally, for any batch with even one register-bearing label, under the literal, unmodified contract text.

**Contract-text check (task item asked me to check for text that already resolves it).** I grepped the entire addendum (`prompts/20260926_2400_p3b-agent-contract-r7-addendum.md`) for `run_id`, `rs_id`, `gap_id`: **zero matches**. The addendum never states what value a record's `run_id` should carry under R7's per-label dispatch grammar. R3 (rev3) item (3) — *"`<run_id>` is the run id you are dispatched with; every path, reader call and record uses it"* — was written when one run covered a whole R2 batch, so it was harmless there; under R7 the dispatched id is `<B>-R7-L##[U##|S]` (`A:115`), which never equals the batch-level `<B>-R7` that G-07 demands. **No existing contract text resolves this**; the addendum is silent, and R3 item (3), taken literally, is now in direct contradiction with the verifier. This is exactly H-2's territory, but H-2's framing ("Choose (a) an addendum rule… (b) a verifier change") is written as if the ambiguity were narrow; it is total.

**Concrete consequence for the canary.** `audit-p3b/20260928_S5-EXECUTION-PACKAGE-DRAFT.md:61-66` names **both** canary batches: OB0012 (5 SINGLE, 0 EMPTY, 0 DECOMPOSED) and OB0114 (3 SINGLE + 1 DECOMPOSED + 1 EMPTY). OB0012 has **nothing to do with EMPTY** — yet by the mechanism above, any agent that follows R3 item (3) literally on OB0012 would already fail G-07 on every one of its 5 labels. EG-5b is not an EMPTY-adjacent corollary; it is an independent, universal R7-program blocker that happens to also block OB0114's EMPTY object once H-2 is resolved the "obvious" way. Both canary batches are blocked by EG-5b **regardless of whether EG-5/EMPTY is ever resolved**.

**Recommendation.** Re-word the EG-5b top-line finding to: *"Blocks every R7 batch with at least one SINGLE/SYNTHESIS (register-bearing) run under the current, unmodified contract text — this is not limited to multi-label collisions, and it independently blocks both canary batches (OB0012, OB0114)."* This does not change H-2's two resolution options or the recommendation to fold it into the same rebind as EG-5 — it changes the urgency/priority signal sent to the human, since as written the finding reads as a niche multi-label edge case rather than "nothing in R7 can produce a BATCH-PASS today."

**Needs a HUMAN decision:** yes — same H-2 decision A already flags (option (a) addendum rule with label-scoped numbering, or (b) verifier change to accept the label's final run id). My finding does not add a new decision, it corrects the severity text that will drive how urgently governance treats it.

## B-02 — MATERIAL (sharpens H-1) — the forced provenance is not just "not truthful", it violates the contract's own model↔run binding rule

**Severity:** MATERIAL (strengthens, does not overturn, A's own H-1; still needs a human decision — same decision, stronger justification)

A's §5 / H-1 correctly identifies that a deterministic, non-model producer cannot pass G-07 with truthful values, and correctly defers to a human decision rather than picking a resolution silently. I re-read R3 §16 and §18 (`R3:1276-1277`, `R3:1317-1319`) independently and found the case is stronger than A's text states:

> R3:1317-1319: **"AI provenance… on every object record… `model_id` (exact model identifier and version)… as exposed by the runtime… The same contract on a different model is a different experiment, recorded as a different run."**

This sentence does two things A's spec doesn't use: (1) it defines `model_id` as a claim about what **actually generated the record**, not a label of convenience; (2) it explicitly **ties run identity to model identity** — a different producer is supposed to get a different run. The EMPTY object's true producer is a deterministic Python tool invoked by the orchestrator, not any model call — a category the contract text doesn't contemplate at all (it isn't "a different model", it's *no* model). Forcing `model_id: "claude-opus-5-5"` and `proposed_by: "AI-AGENT"` onto it, while keeping `run_id = <B>-R7` (shared with genuinely agent-authored objects in the same assembly), does exactly what R3 §18's own sentence says should never happen silently: it erases the "different experiment ⇒ different run" distinction the contract exists to preserve, and it does so inside the one record type (the EMPTY object) that the contract nowhere anticipates.

A's defense — *"the tool is invoked by the orchestrator session, which runs claude-opus-5-5"* — is explicitly called "weak" by A's own text (`§5`, line 131), and I agree it is weak: the orchestrator session's model is not exercising judgment, taste, or reading on this record; it is running a deterministic function that would produce byte-identical output under any model, or none. That is a materially different claim than "claude-opus-5-5 generated this analysis."

**Recommendation.** Same as A's H-1 default (forced values + explicit `generation_parameters.mode = DETERMINISTIC-NO-MODEL-CALL` + `author_role: ORCHESTRATOR-TOOL`), but the governance act approving it should say explicitly that this is a **documented, deliberate exception** to R3 §18's model↔run binding for this one record shape — not merely a values-forced-by-the-gate footnote. That framing matters if `model_id`/`generation_parameters` are ever used downstream (e.g., stratifying θ_D/θ_A by producer, or an audit that filters "AI-AGENT" records) — see B-03.

**Needs a HUMAN decision:** yes, same as A's H-1 (non-material path: keep forced values with explicit unconstrained fields, recorded as an interpretation of §18; material path: verifier + contract change for a truthful exemption).

## B-03 — MINOR/NOTE (sharpens H-7) — the EMPTY stratum's θ_D is not merely "rule reproducibility", it is designed to be tautologically zero, and Freeze-2 already encodes that expectation without saying so

**Severity:** MINOR (A already raises H-7 and asks for human confirmation against B1 v2 / Freeze 2; I confirm the concern is real and sharper than A's text suggests, using material A said was outside this spec's read set but that the task explicitly authorized me to read)

A's H-7 says: *"θ_D on the EMPTY stratum then measures plan/rule reproducibility, not agent reliability… No wording change to the estimands is proposed."* I read `audit-p3b/20260927_B1-EXPERIMENT-DESIGN-FREEZE-PROPOSAL.md` and `audit-p3b/20260928_FREEZE-2-PROPOSAL.md` (both in my permitted read set) to check this.

- B1 v2 §1 defines θ_D as disagreement against *"an independent same-protocol re-analysis"*, and §7/D1 keeps EMPTY as one of five sampled strata (HUB > EMPTY > MULTIROW > DECOMPOSED > SINGLE precedence).
- Freeze-2 §2's strata table gives EMPTY: `N_h=7, treatment=census, rate=CENSUS, n_h=7, π_h=1, "Exact U_h at d=0 (α/H′=0.05/3)" = 0`.

The `U_h = 0` at `d = 0` is not incidental: for a 100%-sampled (census) stratum, observing zero disagreements *is* the exact stratum value (no sampling uncertainty), so the design is already implicitly built around EMPTY contributing **zero** to the combined exact bound. If the EMPTY object is produced by a deterministic function of the frozen plan/slice (A's whole proposal), then a "same-protocol re-analysis" of an EMPTY label — whether that means running the same deterministic tool twice, or a human/agent independently re-deriving "no required files ⇒ NOT-EVIDENCED-IN-CAPTURE" — is **logically guaranteed** to agree, not empirically found to agree. θ_D on this stratum stops being a measurement of reading/interpretation reliability (as it is for the agent-authored strata) and becomes a check that the deterministic rule was implemented and applied consistently — a software-correctness fact, not a corpus-reading reproducibility fact. A already says this in H-7's first sentence; what I'm adding is that Freeze-2's own numbers show this isn't a hypothetical future concern to "confirm" — the census/exact-bound design for EMPTY is *already built* around an expected-zero outcome, and a reader of a completed audit ("EMPTY: 0/7 disagreements, census") could reasonably (and wrongly) read that as independent corroboration of corpus-reading quality for those 7 labels, when — under A's proposed deterministic producer — it is not.

**Recommendation.** Not a wording change to the estimand (A is right that the definition of θ_D itself need not change), but the **governance act that approves the deterministic-EMPTY-producer design** should explicitly note, alongside Freeze 2's approval, that the EMPTY stratum's θ_D/audit entries measure rule-application determinism rather than reading reliability, so this doesn't get silently reported as equivalent evidence to the MULTIROW census (which *is* genuinely agent-authored and can disagree). This is exactly the confirmation A's H-7 asks for; I'm reporting that I checked the two named documents and the concern is well-founded, not merely a hypothetical to revisit later.

**Needs a HUMAN decision:** yes, but low-urgency — foldable into the same rebind/act as H-1/H-2, since Freeze 2 itself is still only a proposal ("no seed was generated and no sample was drawn").

- **Witness ORCH regex / W8 placement (attack #8).** `ORCH = re.compile(r"^: S5-ORCH (UNITS-VALIDATED|ASSEMBLED|FINAL-VALIDATED) batch=(OB\d{4})(?: label=(...))?;")` (`p3b_s5_r7_witness.py:42`) is applied with `ORCH.match(...)` (`WI:142`), which anchors only at the start; there is no `$` in the pattern, so trailing text after `;` (the actual tool invocation) is accepted and does not break the marker match — confirmed by inspection, matches A's claim. ## Verdict

**SPEC-NEEDS-REVISION.**

The technical construction in §3 (the EMPTY object's field table) and the "cannot manufacture corpus evidence" argument in §4 are sound and I found no false-evidence-creation, no absence/non-observation confusion, and no verifier-bypass path in A's design or in the surrounding verifier code. The revision needed is not to the object construction — it is to **how EG-5b is characterized and prioritized** (B-01), which is a correctness-of-the-finding issue, not a correctness-of-the-design issue: A's own probe already produced the universal (single-label) failure, but the written finding describes only the narrower multi-label collision case, which understates that EG-5b independently blocks both canary batches today, with or without EG-5/EMPTY ever being resolved.

**Minimal set of human decisions required before implementation (unchanged from A, with B-01/B-02/B-03 as amendments to their justification text, not new decisions):**
1. **H-2 / EG-5b** — record-identity resolution (addendum agent rule vs. verifier change). Re-scope the write-up per B-01 before it goes to governance: this blocks the R7 program generally, not just EMPTY-bearing batches.
2. **H-1** — provenance for a non-model producer (forced values + explicit unconstrained fields, recorded as an interpretation of R3 §18; note per B-02 that this is a deliberate exception to §18's model↔run binding, not merely gate-compliance).
3. **H-3** — status constants for EMPTY (`UNTYPED`/`UNDECIDABLE-FROM-CORPUS`/`LAYER-UNRESOLVED`); confirmed the null+SCHEMA-LIMITATION alternative is infeasible.
4. **H-4/H-4b** — in_checklist / hub EMPTY labels: refuse or support; needs the counts-only preflight A already asks for (still missing for the actual canary's own EMPTY label).
5. **H-7** (with B-03) — confirm, as part of the same act, that EMPTY's θ_D/audit entries are understood and documented as rule-determinism evidence, not reading-reliability evidence, before Freeze 2 is finalized.
6. **H-5, H-6, H-9, H-8** — as A states, lower-stakes/default-acceptable choices, foldable into the same rebind.

No change to plans, frame, sample, or estimand formulas is implied by any of the above (agreeing with A's §7/Q14 conclusion, independently re-derived from B1 v2 §7/D1 and Freeze-2 §2).
