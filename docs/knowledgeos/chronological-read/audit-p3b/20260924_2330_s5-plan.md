### A.2 The T4 rule and how the hub list is consumed [FROZEN]

- **Rule** (v1.7 §19.4): a Tier-U/Z discovery label is a hub when its predicted load exceeds 4,081 dispositions. The load is (distinct stage-1 hit keys) × (absence dimensions), computed from `P3B-DISCOVERY-SEARCH.jsonl`. The rule was computed before any S5 result, and it is never recomputed.
- **Consumption:**
  - The batch-slice generator reads `P3B-S5-HUBS.jsonl` and copies each hub's full record line into that hub's slice as `hub_record`, with `hub: true`. Every other label gets `hub: false`.
  - The agent never decides hub status (v1.7 §19.2).
  - The verifier checks that the slice's hub flag equals list membership, and that the list's body hash equals `58aed960…`.

### A.3 Hub labels under treatment (a′) [FROZEN, v1.7 §11.4]

- **Fully processed for hubs:** every per-label step of §9.8 except stage 2. That covers step-1 chronological reading, timeline, births, statuses, layer, dependency edges, stage-1 consumption, and the research checklist where the label is in the checklist.
- **Hub absence dimensions:**
  - Every hit-bearing dimension (its `hits_ref` label carries at least one ledger or raw hit) resolves `ESCALATED`, with reason `LOAD` and the full hub record line.
  - Stage 2, 2A and 2B are not performed. No hit is sampled, and no hit file is read for stage 2.
  - Such a dimension is never FOUND and never GENUINELY-UNDEFINED-AFTER-CENSUS.
  - Gap records on these dimensions use `NOT-FOUND-LOAD-ESCALATED`.
  - Material found by step-1 reading goes into the escalation, plus a P1-GAP candidate.
- **NEGATIVE-CENSUS dimensions of a hub:** ordinary rules apply, including the census–reading disagreement rule. There are none today.
- **Hubs are never treated as "not found".** `ESCALATED (LOAD)` asserts nothing about the hits.

### B.2 Proposed dispatch design

- **Batch unit [PROPOSED]:** a set of labels bounded **by load, not by label count alone**. A batch is valid only if every cap holds:
  - **Σ predicted dispositions ≤ 4,306.** This is the largest batch load S4 actually processed and audited [MEASURED anchor].
  - **Σ predicted stage-2 bytes ≤ 8.63 MB** [MEASURED anchor].
  - **Σ step-1 bytes ≤ 1.80 MB** [MEASURED anchor].
  - **checklist labels ≤ 5** [MEASURED anchor].
  - **total labels ≤ L_max** [PROPOSED; human decision]. Non-checklist labels skip the research checklist, so they are lighter, but by an amount S4 never measured. Options:
    - **L_max = 5:** 382 batches, fully within measured capacity.
    - **L_max = 8:** 239 batches.
    - **L_max = 10:** 191 batches.

    **Recommended: L_max = 10 with a calibration gate** (B.3). No single non-hub label can exceed a cap by itself: the maximum label load is 4,081 dispositions and 8.59 MB, both inside the batch caps. So a heavy non-hub label always sits in a batch whose total stays within audited capacity.
- **Packing [PROPOSED]:** deterministic first-fit decreasing.
  - Order: predicted dispositions descending, then stage-2 bytes descending, then label ascending.
  - Each label goes into the first open batch where every cap still holds.
  - No randomness, so the manifest is reproducible byte-for-byte.
  - Projection at L_max = 10: 191 non-hub batches. The heaviest reaches 4,306 dispositions and 8.63 MB; 49 batches are bound by the disposition cap.
- **Hub batches [PROPOSED]:** the 66 hubs are packed separately, ≤ 5 labels and ≤ 5 checklist labels each, giving 14 batches. So the hub exception is uniform within a batch and simple to verify. They have no stage-2 load.
- **Expected batches:** 191 + 14 = **205** at L_max = 10, or 382 + 14 = **396** at L_max = 5. Batch ids continue the first run's `OB####-R2` numbering from OB0004-R2 [PROPOSED].
- **Budgets per batch** (hard caps; the verifier fails a batch that exceeds them):

  | Budget | Cap | Marking |
  |---|---|---|
  | dispositions | the caps above | [MEASURED anchors] |
  | stage-2 bytes | the caps above | [MEASURED anchors] |
  | step-1 bytes | the caps above | [MEASURED anchors] |
  | reader calls | 2 × the R2.2 per-label maximum × labels, **as an alert, not a failure**. R2.2 showed calls vary with paging, and calls are not a cost driver | [PROPOSED] |
  | research reads | OMQ-16 (§C) | [PROPOSED] |

- **Totals:**

  | Item | Value | Marking |
  |---|---|---|
  | stage-2 reads | 0.43 GB over 13,946 file reads | [MEASURED] |
  | step-1 reads | 0.09 GB | [MEASURED] |
  | dispositions | 283,576 | [MEASURED] |
  | research reads | ≤ 205 × the OMQ-16 cap | [PROPOSED] |

- **Deterministic ordering:** dispatch in manifest order; the manifest is frozen before the first dispatch.
- **Batch manifest:** `_batch_manifest_p3b_r2.jsonl` (§24.1) [FROZEN artifact class]. It has a header per §19.5 and, per batch:
  - batch id, labels, hub flag, checklist flags;
  - predicted dispositions, bytes and file reads;
  - each slice's sha256, and the contract sha256.
- **Batch hashes:** `P3B-BATCH-SNAPSHOT.json` is written once per batch before dispatch, with the slice sha256 and the `02-FILES.jsonl` sha256 (§19.5) [FROZEN].
- **Recovery and restart** [FROZEN rules, §20/§22; operational detail PROPOSED]:
  - A failed batch is kept, marked FAILED, and re-run in a new batch run (`OB####-R2.1`) from the same frozen slice.
  - An interrupted batch is marked INCOMPLETE, its partial output is kept, and it is re-dispatched as a new run.
  - Resumption uses `P3B-STATE.json` and the manifest only, never conversation memory (v3.5 A3).
  - Private scratch per batch; no helper agents (G-LOG-0023 (d)).
- **Audit sampling per batch [PROPOSED]:**
  - The verifier runs on 100% of batches (schema, G-01…G-12, the G-08 join, one disposition per distinct hit key per dimension, the hub checks, F1–F3).
  - A script checks every quote.
  - The §21 independent audit covers **audit groups of 4 consecutive batches**, as in R2.2. In each batch it samples, with a seed derived as `20260926 + batch index`:
    - 1 object record;
    - 4 register records;
    - and, per F3, ≥ 30 Stage-2B occurrences for any label with more than 100.
  - The cross-group checks follow R2.2 item 6 (rule consistency).
- **Acceptance boundary [PROPOSED; human]:** §25 acceptance by the human, per audit group of 4 batches, from the verifier output and the audit report. A batch fails on any §20 gate. An audit PROTOCOL-VIOLATION fails that batch, and it is re-run.

### B.3 Calibration gate (operational, pre-registered) [PROPOSED]

- The first 2 audit groups (8 batches) are dispatched as normal production batches, and their actual bytes, calls and wall time are measured.
- If any batch exceeds 1.25 × a measured anchor, or its audit reports quality loss attributable to batch size, the remaining manifest is regenerated at L_max = 5 **before** further dispatch.
- The regeneration uses the same packing rule and changes no label's treatment.
- The decision uses cost and audit-quality measurements only, never research outcomes.

## C. OMQ-16: research-testing budget

**Measured [MEASURED]:**
- R2.2 produced 87 register records for 20 labels (4.35 per label): 71 OBSERVED, 10 ANALYSED, 6 TEST-DEFINED.
- No record reached TESTED, because the pilot excluded TESTED/STATUS until H-16.
- Step-10 research reads were ≤ 0.08 MB per batch.
- S4 found that hypotheses and structure candidates **do not reproduce across runs** (10 H + 4 SC in R2-001 against 4 H + 2 SC in R2.2, on the same labels).

**Separation.** Research-testing is not part of the mechanical per-label roll-up. It has its own budget and its own reads:
- **In batches:** records up to TEST-DEFINED.
- **In a separate, later S5 test pass:** TESTED and STATUS, run under its own run id, after all batches are accepted and H-16 is decided.

**Proposed rules [PROPOSED unless marked]:**
1. **Allowed research reads (in batches):** whole-file reads through `p3b_read_source.py` at step 10, logged. They are **label-local**: only files cited by the label's slice (rows, stage-1 hit files, `files_touching`). Cross-label reading is not allowed in batches; cross-object reading happens only in S5a/S5b (§9E) and only for a specific candidate.
2. **Cap per batch:** step-10 bytes ≤ 0.9 MB, about 10% of the batch's stage-2 cap and about 11× the largest S4 research-read load. **This cap is a proposal, not a measurement**; the calibration gate (B.3) reports actual use.
3. **Repeated reads:** a re-read of the same file under the same label counts again against the cap. The reader log makes repeats visible, and the verifier reports repeat ratios.
4. **Record caps:**
   - **No quota and no minimum.** An observation may remain an observation (D-38).
   - The audit checks for manufactured hypotheses (§21 item 5).
   - HYPOTHESIS, STRUCTURE-CANDIDATE and THEORY-CANDIDATE must reach TEST-DEFINED with a `test_plan_sha256` [FROZEN §13.9].
5. **Test selection [FROZEN rule, §13.9 RC-9g; share PROPOSED]:**
   - Every CORPUS-scale record is TESTED in S5b.
   - Among non-CORPUS TEST-DEFINED records, a **seeded random share** is TESTED in the S5 test pass.
   - **Proposed share: 20%**, with seed `20260927`. Basis: none measured, because testing cost is unknown. Therefore also proposed: a cost calibration on the first 20 selected tests (bytes, calls, time). The share may be lowered, never raised selectively, **by a governance act made before the remaining tests run and based on cost only** [OMQ until decided].
6. **Formal / mathematical / logical / DDD analysis:**
   - It costs reasoning, not reads.
   - It is budgeted as part of the test pass per selected record.
   - It uses no reads beyond the four disconfirmation searches (§13.10), which are stage-1-style (script) or whole-file reads through the logged reader.
7. **Budget exhaustion:**
   - Remaining candidate reads are recorded as `DEFERRED (BUDGET)` on the record. No further research reads occur in that batch.
   - Records stay at their reached lifecycle stage and carry forward to P4–P7 (§13.9: testing never blocks acceptance).
   - The research register never becomes a second corpus-reading mechanism: every read is label-local, logged and capped.

## F. H-16: N_support

- **Unit (clarified; follows from the frozen text, not newly chosen) [FROZEN]:** N_support is a threshold **per record**, that is, per claim or structure, not per label.
  - At OBJECT scale it counts **independent PRIMARY sources** for the claim.
  - At CORPUS scale it counts **independent occurrences** of the structure class (§9E.3).
  - CROSS-OBJECT findings cannot be SUPPORTED at freeze (L-1).
- **Independence already enforced [FROZEN]:**
  - repeated occurrences within one file count once (R2.2 collapsed 74 repeated in-row occurrences);
  - duplicate files count once (`08-OVERLAP-REGISTER.jsonl`, v3.5 R9);
  - SECONDARY-SYNTHESIS and PROVENANCE-UNRESOLVED files never create an occurrence (§9E.3);
  - occurrences sharing a label or a source are excluded (A.8);
  - SELF-DERIVED, DESCRIPTIVE and control-set findings never count.
- **Dependence the rules do not catch:** copied or restated material inside PRIMARY files of one authoring session, one provenance family or one mtime block. Two PRIMARY files may be one line of thought. The co-change cap (H-18) mitigates this for G-COCHANGE only.
- **Evidence [MEASURED]:** P3a single-pass exact agreement was 20.9%, and S4 R1/R2 agreement was 30–95% by field. Single-run records are therefore not independent observations (§K).
- **Choices:** 1; 2; 3; or 1 at OBJECT scale with 2 at CROSS/CORPUS.
  - **N_support = 1** makes replication unnecessary.
  - **N_support = 2** is the smallest value that requires independent replication.
  - **N_support = 3** is safer against same-session dependence, but will leave more records UNDETERMINED. UNDETERMINED is a legitimate result.
- **Recommendation:** the protocol recommends **2**.
- **Additional proposal [PROPOSED; human]:** for CORPUS records, report alongside N_support the number of occurrences that fall in **distinct mtime blocks** (`02-FILES.jsonl`). This is a **reporting field, not a STATUS condition**, so §13.9a is unchanged.
- **Wording:** "H-16: N_support = 2 (independent PRIMARY sources for OBJECT-scale records; independent occurrences per §9E.3 for CORPUS records); CORPUS records additionally report occurrences in distinct mtime blocks."
- **Interaction with the status vocabulary:** N_support gates `SUPPORTED-IN-CORPUS` (§13.9a) and `RECURRENT` (§13.9b). Below it the result is `UNDETERMINED-FROM-CORPUS` and `PATTERN-OBSERVED`, never REFUTED.

## I. H-18: co-change file-degree cap

- **Co-change:** two or more labels whose S5 timelines have a point at the same PRIMARY source with `change_vs_previous ≠ RESTATES` (A.6) [FROZEN].
- **Dependence risk:** a registry, census or index file lists many labels at once. Co-listing there is an artefact of authoring, not a structural relation, and it creates spurious co-change sets.
- **Degree measured over the discovery population** [MEASURED] (labels whose rows cite the file; 1,975 labels, 1,935 files; no hold-out material):
  - p90 4, p95 6, p99 13, max 35.
  - Files above the cap:

    | Cap | Files above |
    |---|---|
    | 5 | 126 (6.5%) |
    | 8 | 50 (2.6%) |
    | 10 | 29 (1.5%) |
    | 14 | 12 (0.6%) |

  - Top files: S0239 (35), S0237 (28), S2785 (27), S2783 (26), S2782 (25), S2781 (24), S2819 (18), S0234 (17).

- **Effect on recurrence:** it removes registry-driven sets before counting. It may lower G-COCHANGE candidate counts, which could leave cells UNDERPOWERED. That is a legitimate result.

## K. Repeated-run stability

S4 showed that single-run research records do not reproduce. S5 therefore measures stability, and never treats one run's records as independent observations.

- **Rerun population [PROPOSED]:** a seeded, stratified random 5% of non-hub labels (about 96 labels), with seed `20260928`, allocated proportionally over the 24 sample-plan strata.
  - It is drawn from `P3B-SAMPLE-PLAN.jsonl` only, never using hold-out information.
  - It is packed into rerun batches by the same rule (about 10–20 batches).
  - It also includes the 20 R2.2 pilot labels as a **cross-contract** comparison, labelled separately (the S4 contract differs from S5's in F1–F3).
- **Held constant:** v1.7, the S5 contract (same sha), the slices (same sha) and the reader.
- **Regenerated independently:** a fresh agent, a new run id (`OB####-R2S`), private scratch, and no access to the first run's outputs (blind).
- **Frequency:** once, after the primary batches are accepted and before the S5a snapshot.
- **Agreement metrics:**
  - per object field: exact agreement and Cohen's κ (births, type_status, mathematical_status, primary_layer, absence resolutions);
  - per label: research structure classes, as the Jaccard overlap of the pre-registered classes recorded on the label in each run;
  - for S5a: a second blinded analyst on a seeded 20% of analysed sets, with agreement on class disposition.
- **Acceptable disagreement [PROPOSED]:**
  - a field's rerun agreement at or above its S4 R2.2 R1/R2 agreement is **STABLE-AT-BASELINE**;
  - below it, the field is flagged `METHOD-INSTABILITY` and routed to governance.
- **Unstable findings:**
  - A CORPUS record whose participating CROSS-OBJECT findings do not recur in the rerun subset is flagged `UNSTABLE`.
  - This is a **reporting field**. §13.9a/§13.9b are unchanged, and no STATUS is altered.
  - The flag is shown with every level claim.
- **H-19:** the rerun uses discovery labels only, and no hold-out input.
