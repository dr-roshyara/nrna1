**This is exactly the task's question ("which object is the 'S5 outcome' for EP-01 when a correction record exists") and it is still open, not closed.** Two live possibilities, both defensible, not distinguished by anything A cites:
1. ## 1. H-06 tranche binding — the mechanism is sound but the residual is understated

`check_tranche` (§1.2, read in full) is a real improvement over v1: it binds `--reference`/batch/run_id/evidence-sha to a committed artifact, closing the core gap from REVIEW-B v1 finding 5. I checked for the specific bypasses the task named:

- **Modified-and-recommitted file:** caught. If the tranche file is edited and recommitted, check (b) recomputes sha256 against the *current* file and compares it to the *G-LOG text's* recorded hash, so an edit-without-updating-the-G-LOG-line is refused. **But** if an attacker (or a careless automated batch) edits *both* the tranche file *and* the G-LOG-#### section's `H06-TRANCHE ... sha256 ...` line together, in a later commit, check_tranche passes cleanly — nothing detects that the pairing changed after the fact. I checked whether `P3B-GOVERNANCE-LOG.md` has any code-level append-only enforcement comparable to `P3B-STATE.json`'s hash-chain (`verify_chain`/`save()`, ST:~93-115) or AR's write-once report (`p3b_s5_audit_record.py:65-67`, "REFUSED: the audit report exists"). **It has none.** `scripts/p3b_s5_common.py`'s `ALLOWLIST` includes `P3B-GOVERNANCE-LOG.md` as a *readable* file for S5 tooling, but no script anywhere hash-chains or refuses to overwrite it; §24.1 calls it "append-only, human entries," which is stated discipline, not enforced. So `check_tranche`'s trust anchor is weaker than every other trust anchor this design otherwise insists on (state history, audit reports, sample binding all get hash-chains or write-once guards; the governance log itself does not).
  - **A's stated residual** ("binding proves record ↔ state agreement, not human authorship of the G-LOG entry," v2 §1 closing paragraph) is honest as far as it goes but **understates** the gap: it frames the residual purely as an epistemic one (who wrote it), when the concrete, checkable gap is that the binding is a *snapshot* consistency check with no protection against the anchor itself being rewritten later. Recommend disclosing this explicitly and, if the human wants the stronger guarantee the property table (§1, "in the property that matters, it is equivalent to 396 individual acts") actually claims, either (i) hash-chain `P3B-GOVERNANCE-LOG.md` the way `P3B-STATE.json` is hash-chained, or (ii) have `check_tranche` additionally require the tranche file's own commit to be reachable only via a commit that also introduced the matching G-LOG text (a `git log -p` check on that commit), so a later, separate edit to either side is visible.
- **G-LOG section parsing ambiguity:** a real gap the task's own hint anticipates and A's design does not address. `check_tranche` (b) matches `^## (G-LOG-\d{4}) —` "up to the next `## `" — the spec does not say what happens if **two** sections in the file match the same reference (a duplicate heading from a later, separate append). Nothing in the design requires reference-heading uniqueness across the whole file, and the RED test list (T-08) only covers *two `H06-TRANCHE` lines inside one section*, not two sections with the same `G-LOG-####` heading. Recommend adding a uniqueness check (refuse if the reference heading occurs more than once) and a corresponding RED test.
- **Attempt field vs EG-6:** checked whether this is live today. `new_attempt` does not exist in the codebase (confirmed: no occurrence anywhere in `scripts/*.py`), and the existing `new_run` explicitly refuses for `revision == 7` ("a new run of an R7 batch is not defined... needs a human act, G-LOG-0102", ST:~209). So **no R7 batch can be retried at all today** — "the attempt is 1" (v2 §1.2(d)) is not an approximation, it is currently the only possible value, and `check_tranche`'s attempt check is correspondingly vacuous but not wrong. This becomes load-bearing only once EG-6 part (d) actually lands and wires an `attempt` field into `entries`; flag as a forward dependency (check_tranche must be updated then, not left as a hardcoded literal), not a present defect.
- **Outcome mismatch:** no bypass found. Checks (c)/(d)/(f) jointly require the tranche's own internal `reference` field, the batch's single listing, and its listed `outcome` to all agree with the CLI arguments; I could not construct a case where a batch's true outcome and the accepted outcome diverge.
