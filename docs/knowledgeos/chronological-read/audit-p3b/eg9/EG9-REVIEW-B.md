## 2. The core statistical interaction (Q2 of the task) — no bias found, but two things need tightening

**Does §21 act as a content-dependent selection filter that reaches EP-01?** Yes, mechanically: a §21 FAIL is class H (EG6-SPEC-A-v2.md:108, confirmed verbatim: "**H** human/audit-stage | the §21 audit FAIL or an H-06 rejection (after VERIFIED) | **no** automatic re-run (**audit-informed selection**, RR-1). The labels become NOT-ASSESSABLE unless a human act decides otherwise"). The phrase "audit-informed selection" is EG-6's own name for exactly the risk the task asks about — **it is already named as a limitation**, and EG-6 is SPEC-ACCEPTABLE (three review rounds, per EG5 §14). A's spec inherits this disclosure rather than needing to invent it; that is a legitimate answer to "must it be named as a limitation," not an omission.

**Does it bias θ_D/θ_A, or only redefine the population?** I traced this through EP-01's actual design (`audit-p3b/20260926_EP-01-STATISTICAL-SPECIFICATION.md`), not just A's paraphrase:
- The frame N=1,975 is fixed **before S5** and never shrinks (§1: "Labels that never obtain an accepted object... stay in the frame and are classified NOT-ASSESSABLE").
- §7: NOT-ASSESSABLE is "as for AUDIT-FAILED (**worst case** in the primary bound)" — i.e., counted as discordant, which is the conservative direction for an upper-bound estimator. No replacement draw is ever made (confirmed §7: "A replacement draw is never made for either class").
- Since §21 failure is a **batch-level**, content-independent-of-EP-01's-sample event (§21's seed 20261100 is drawn independently of the Freeze-2 seed, and the Freeze-2 sample is drawn and frozen "before any S5 output exists," EP-01 §4/PKG:70/G-LOG-0103) — a §21 FAIL cannot correlate with *which* labels were pre-selected for the EP-01 sample. Whatever correlation exists is only "batches whose content is more likely to contain protocol violations are more likely to also be discordant under EP-01" — and the worst-case rule is exactly the conservative response to that correlation, not a source of bias.
- **Conclusion: it is population redefinition, absorbed by machinery EP-01 already has for other failure classes (A1/A2/X/D), not a new bias.** A's spec is correct on this point, and — importantly — I confirmed EP-01 needs **no design change** to accommodate class H: NOT-ASSESSABLE is generic across all failure causes.

**Two things worth tightening (not blocking):**
1. **Batch-vs-label granularity is understated.** A §21 FAIL removes the *whole batch* (K3: "A batch fails if... G-06 finds a disagreement dispositioned as a protocol violation," K3 §20 table, confirmed at line ~1352-1353), not just the flagged label. A's Materiality section (§3(a)) says this "extends the pre-registered survival limitation (EG5:294-296)" — I checked EG5's named-limitation text (`EG5-V2.8-DECISION-PACKAGE.md:283-286`): "θ_D and θ_A describe the **retry-surviving accepted population**. This is a stated limitation, not an estimator bias." That text is about the A1/A2/X *retry* mechanism, where a label eventually gets a second chance; class H removes an entire batch's sibling labels **with no retry at all**. The pre-registered failure-class table (EG6 line ~108) does list H alongside the retryable classes, so the umbrella disclosure technically covers it — but a batch of up to several labels being pulled from the estimable population in one non-retryable stroke, because of a violation found in one sampled record elsewhere in the batch, is a coarser-grained and more concentrated loss mechanism than what "retry survival" evokes. Recommend the EG-9 proposal text explicitly say so (one sentence) rather than relying on readers to infer it from EG-6's table.
2. **Residual blindness note.** Every label that ever reaches θ_D/θ_A adjudication is, by construction, from a batch that already passed §21 (NOT-ASSESSABLE labels never reach adjudication). That fact is constant across the whole adjudicated population, so it cannot differentially bias θ_D/θ_A — but it does mean the adjudicator's prior is never "genuinely blind to whether *any* audit-stage screening occurred," only blind to *which side is S5* (EP:84's actual blinding claim). This is a pre-existing property of EP-01's design (true whether or not §21 exists, since the verifier's PASS is also always true in the adjudicated set), not something option (a) introduces. Not a finding against A; just worth being explicit that the firewall rule (3) in A's proposal text should be read as "no differential leakage," not "the adjudicator learns nothing about the population's screening history."

## 5. H-06 granularity (Q5 of the task) — the one MATERIAL finding

A's spec (§3, "H-06 granularity") argues the enumerated-tranche form is *not* a standing rule because "AC:4/EP-02" forbid a standing rule, and each `p3b_s5_accept.py` call is "still individually gate-checked" (state = AUDITED, evidence hashes present, not previously decided).

I checked what is *actually* enforced mechanically (`p3b_s5_accept.py:41-58`, read in full) versus what is only a **documentary convention**:

- `record()` requires non-empty `--decision`, `--decided-by` (non-AI pattern), `--reference` **per call**, and refuses if the batch isn't AUDITED with evidenced VERIFIED+AUDITED, and refuses a repeat decision on the same (batch, run_id).
- **Nothing in the tool checks that the `--reference` given actually names a G-LOG entry that lists *this* batch id**, or that the tranche G-LOG entry's stated verify-/audit-report sha256 values match this batch's actual evidence. The "enumerated tranche" (a human-written list of batch ids + hashes, "reviewed at decision time," per A's proposal text item 5) is **not bound to the tool call at all** — it is pure prose discipline.

**Consequence:** an orchestrator (human or AI) that has one tranche `--reference` string can invoke `p3b_s5_accept.py --outcome ACCEPTED` for **any** AUDITED batch under that same reference, whether or not it was actually among the batches the human reviewed and listed in that G-LOG entry, and the tool will not refuse it. At tranche sizes of ~5-80 batches this is a real, exploitable gap between what the governance text says was decided and what the tool set will actually accept as decided. This is not hypothetical misuse-by-malice; it is a **missing safety net** against ordinary operational slippage (copy-paste of the wrong reference, a tranche list edited after the fact, a batch added to "the same group" without updating the G-LOG entry) — precisely the kind of failure mode this project's own engineering discipline (residual-tracking, fail-closed defaults) treats as a defect, not an acceptable risk.

This directly bears on the task's question: **is enumerated-tranche acceptance "genuinely a human act per batch, or automatic acceptance in disguise"?** My answer: **as specified, it is closer to automatic acceptance than A's spec acknowledges**, because nothing mechanically ties the human's per-batch review (evidenced only by prose in a Markdown log) to the per-batch tool invocations that actually flip state to ACCEPTED. The individual gate-checks A cites (state=AUDITED, evidence hashes present, not previously decided) are necessary but do not establish that *this batch* was among the ones a human looked at — they only establish that *some* human decided *a* batch under *some* reference string.

**Recommendation (for H-EG9-3):** either (i) accept this as a documentary-only control and say so explicitly (a defensible but weaker position than A's spec currently implies), or (ii) require the G-LOG tranche entry to be represented as a small hash-bound artifact (a JSON list of batch ids + their verify/audit-report sha256, itself referenced by both the G-LOG entry text and an `--accept-list` argument to a thin wrapper around `p3b_s5_accept.py` that refuses any batch not present in that list, and refuses if a listed batch's live evidence hash differs from the list's). This is a small addition (comparable in scope to the `--sample` binding A already proposes for AR) and it would make "enumerated tranche" mechanically equivalent to "396 individual acts" in the property that matters (every ACCEPTED batch was individually named by the human), while keeping the cost savings of one write-up per tranche. **This needs a human decision** (whether the convenience of unbound tranches is acceptable, given EP-02's "engineering supplies the evidence and a recommendation; the human decides" and AC's own explicit anti-automation stance).

## 6. Runbook DISPATCHED→PROPOSED gap (Q6 of the task) — confirmed, and more severe than A's framing suggests

- I additionally checked `scripts/p3b_s5_r7_orchestrate.py` (which A's read set includes but whose content on this specific point A's spec does not report): it contains **zero references to `p3b_s5_state` or any `transition` call** — `prepare`/`archive`/`freeze-units`/`freeze-final`/`verify` are pure artifact-production subcommands that never touch `P3B-STATE.json`. So the PROPOSED transition is not silently handled by the orchestrator tool either.

**This means the runbook as currently written and tooled cannot literally execute step 9**: with nothing ever moving a batch from DISPATCHED to PROPOSED, the documented `state transition B PROPOSED → VERIFIED` call would itself be refused by the state machine (invalid transition from DISPATCHED). This is a **live, currently-blocking gap for every R7 batch**, not a cosmetic doc nit — it would stop the very first canary batch from ever reaching VERIFIED, regardless of anything to do with EG-9/§21. **I agree with A that it is correctly out of EG-9's scope** (it is orthogonal to the AUDITED question), but I'd flag it more strongly than A's one-line side note: this project's own CLAUDE.md discipline calls for discovered out-of-scope work to become an explicit backlog item, and "PKG §1 needs a `state transition B PROPOSED` step between step 2 and the dispatch sequence (or step 9 needs to add it)" is exactly that kind of item. It should be raised to the human alongside the EG-9 decisions, since it blocks the canary regardless of how H-EG9-1..5 are decided.
