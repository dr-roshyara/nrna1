## 2. Scientific validity (attack 2) — CONFIRMED, no measurement-validity hole beyond what A discloses

- **Hit-file-that-is-also-a-row-source scenario** (the strongest counter-case I could construct): if an S-id is *both* a bundle row source and a stage-1 hit, is it silently droppable under option (a)? No — `bundle` (`rows_verbatim`/`sources_verbatim`) is never under `search_records` or `source_meta`, so it is fully in R(run) under rule (i) regardless of the S-id's hit status; and T(L) (§4) is defined over the *whole* slice minus only `search_records`/`stage2_files`/`source_meta`, so such an S-id is still in T(L) and its `source_meta` entry is still required. I checked this is not accidental: T(L) is built by regex over the full canonical slice with exactly those three keys stripped, which by construction re-admits any S-id that also occurs in `bundle`, `family_md`, `p3a_pairs` or `source_tracks`. No gap.
- **A later/contradicting source visible only in hits**: real, but pre-existing to the *hub protocol itself* (v1.7 §11.4), not created or worsened by option (a). A hub agent is already forbidden from reading or using such a source regardless of whether it's *displayed*, because stage 2 is categorically disabled for hubs. Whether the raw hit list is on-screen changes nothing about what the agent is permitted to conclude from it. Confirmed by cross-reading `hit_bearing()` + the `ESCALATED`/`LOAD` gate: the verifier enforces the *output* is mechanical regardless of input display.
- **REPORT-only coverage leaving a "copy without reading" hole**: A's own characterization ("completeness evidence, not correctness") is accurate but deserves one sharpening for the write-up: because `hub_record` must match the slice's `hub_record` **byte-for-byte** (`hub_rec_eq`, `p3b_s5_verify.py:~783`) and the `DIMENSION` list must match exactly (`set(dims) - set(ab)`, `~:756`), an agent that never displays those lines would have to *reproduce a large opaque JSON blob and an exact dimension-name list from nothing* to pass the verifier undetected — practically this is not "copy without reading," it is closer to "fabricate structurally-correct output without having looked," which the verifier's byte-exact equality checks make very hard to do by accident and easy to catch if this ever becomes a gate. So REPORT-only is an acceptable interim position, but HD-2's own text should say explicitly (it does not currently) that RI-1b's absence is safe *because* of these independent byte-exact structural checks, not merely because "the answer is mechanical."

## 3. R(run)/T(L) well-definedness (attack 3) — ONE MATERIAL FINDING

**MATERIAL — the shipped probe does not implement the rule SPEC-A proposes to adopt.**

- Draft normative text, §5.1 clause (iii), and the formal definition in §4 rule 3, both state: *"p[0..1] = [`search_records`, 0] and p[2] is neither `ledger_hits` nor `raw_hits`"* — i.e. **zero** view lines from inside `ledger_hits`/`raw_hits` are ever required.
- RED test E2 (§5.2) restates this as an acceptance criterion: *"R excludes **every** `search_records[0].raw_hits/ledger_hits` leaf."*
- But `probes/eg3_probe_required_coverage.py::required()` does **not** implement that:
  ```python
  elif len(p) >= 3 and p[2] in ("ledger_hits", "raw_hits"):
      if p[2] not in seen_first:
          seen_first.add(p[2]); req.add(n)
  ```
  This adds the **first leaf line of each non-empty hit map** to the required set — one line for `ledger_hits`, one for `raw_hits`, whenever non-empty. The probe's own docstring documents this as deliberate ("plus the FIRST leaf of each non-empty one"), so it is not a slip of the pen — it is a second, undeclared variant of the rule, tested and reported as if it were the rule in §4/§5.1.
- I re-ran the probe (as shipped, unmodified) to confirm this is live behaviour, not a dead branch:
  ```
  small : REQUIRED lines 211 in 4 ranges -> reads 11
  median: REQUIRED lines 355 in 4 ranges -> reads 16
  large : REQUIRED lines 2159 in 4 ranges -> reads 88
  ```
  These are exactly the "11, 16, 88" figures SPEC-A §5 cites as probe evidence for its cost estimate — i.e. the headline feasibility numbers in the document under review were produced by the **non-conforming** variant of the rule, not by rule 3 as drafted.
- **Materiality of the finding itself**: low magnitude (at most 2 extra lines out of a required set whose production max is 123-127, per `hub_required_counts.json`), and the two extra lines are harmless if displayed (they carry no additional evidentiary content the agent could misuse — a lone hit-map leaf out of context is not attributable to a specific S-id/anchor and the schema forbids any evidentiary use of it regardless). So this is **not** a scientific-validity problem. But it **is** a governance-hygiene problem: a document proposing a byte-exact, test-verified, contract-anchored rule cannot cite a probe that silently tests a different rule, and it cannot ship a RED-test description (E2) that the reference implementation would fail on day one. Left uncorrected, whoever implements §5.9a will face an ambiguous reference: text says "exclude all," probe says "exclude all but the first line."
- **Open question I could not close under the hard constraints**: whether `hub_required_counts.json` (the *production* counts I was given and told not to re-derive) was computed with the probe's "first-leaf-kept" variant or with rule 3 as literally drafted. Given `hub_required_counts.json`'s "narrow"/"citable" max (123/127) sit only slightly above `hub_view_profile.json`'s "without_search_records_and_source_meta" max (108 reads, a quantity that already fully includes `stage2_files` and excludes all of `search_records`), the magnitude is consistent with either variant — it cannot be used to disambiguate. This should be asked of the orchestrator before HD-5/HD-1 are closed.
- **Resolution needed (HUMAN/ENGINEERING DECISION, new)**: pick one of:
  (i) Fix `required()` (and the eventual production implementation) to drop the `seen_first` branch, matching rule 3 exactly as drafted; or
  (ii) Amend §4 rule 3 and §5.1 clause (iii) to explicitly add "*, and the first leaf of `ledger_hits` and of `raw_hits` when non-empty, as a hit-presence indicator*" — if that inclusion is in fact wanted (e.g. so an agent visually confirms a hit map is non-empty without seeing its contents) — and update RED test E2 to match.
  Either is cheap (one line of code or one clause of text plus a re-run of the probe); this should close **before** §5.9a's normative text is finalized for HD-1, not after.

### 3.1 Other counter-cases checked — all benign, none material

- **Empty `ledger_hits`/`raw_hits`** (possible for a hub if all of the label's hits happen to be of one kind): `slice_view`'s `walk()` emits a single `E`-kind leaf line at path `[...,"ledger_hits"]`/`[...,"raw_hits"]` for an empty container, and rule 3 as drafted excludes it too (its `p[2]` is still `"ledger_hits"`/`"raw_hits"`). This is a well-defined, deterministic exclusion and carries zero evidentiary content (an empty container conveys nothing a hub run could act on), so this is a non-issue, not a counter-case that breaks the rule.
- **Hit maps as lists rather than dicts**: cannot occur. Traced construction end-to-end (`p3b_s3_mechanical_prep.py:521-523` → `p3b_s3b_holdout_sample_plan.py:376-377`) — `ledger_hits`/`raw_hits` are always dict comprehensions keyed by S-id; the JSON-path walk in `slice_view` therefore always sees a dict at that node. Not a real counter-case given the producing code, only a hypothetical against a malformed slice, and malformed slices are independently rejected by `slice_view_violations` before any of this applies.
- **A `source_meta` key that is not an S-id**: cannot occur. `source_meta`'s keys are exactly `re.findall(r"\bS\d{4}\b", ...)` matches (`p3b_s5_prepare.py:431-433`), so every key is by construction of the form `S\d{4}`. Not a real counter-case.
- **Nested keys inside a DIMENSION record or elsewhere producing a `p[0]="search_records"`, `p[1]` non-integer, etc.**: `search_records` is always a JSON array (`[LABEL-HITS record] + [DIMENSION records...]`), so `p[1]` is always an integer index; rule 2/3's `p[1] != 0` / `p[1] == 0` dispatch is well-defined over the whole array. No malformed-index case is reachable from `slice_view`'s own walk.

**Conclusion for attack 3**: T(L) itself (§4's S-id regex over the slice with three keys stripped) is well-defined, deterministic and matches its production-code counterpart in spirit; the *only* genuine defect is the probe/rule-text mismatch on hit-map first-leaf inclusion (above), which is real, checked by direct re-execution, and cheap to close.

## 5. HD-3 (T(L) scope: citable vs narrow) — recommendation supported, but on a narrower basis than stated

A's reasoning ("safer for MOVED and family-md citations; small") is correct as far as it goes, but is incomplete as an argument: because R(run) is a **minimum**, not a **maximum** (`§5.1`: *"may display any other line"*), the citable/narrow choice does not create a completeness *risk* either way — an agent may always display more. Its only effect is on **false-positive NOT-COVERED noise** in the RI-1b report: narrow under-covers (a `source_meta[S]` an agent legitimately needed, e.g. for a `family_md`-only MOVED citation, could get flagged NOT-COVERED even though correctly read), while citable over-covers only slightly (extra 4 lines at the max, per `hub_required_counts.json`: 127 vs 123). Recommend the write-up say this explicitly — "safer" should be spelled out as "fewer spurious NOT-COVERED reports," since as currently phrased it could be misread as a correctness/coverage-risk argument, which it is not (report-only has no verdict effect either way).
