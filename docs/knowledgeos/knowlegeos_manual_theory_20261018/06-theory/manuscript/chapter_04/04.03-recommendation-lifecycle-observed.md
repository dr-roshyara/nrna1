## 4.3.1 In plain language

§4.2 described the cycle a recommendation should go through. S0044 records what actually happened when it was first run: ten recommendations issued, then one decision, then an accident (the same decision recorded twice). It refuses to name a domain model until the records demand one.

## 4.3.2 Claims and derivations

**C1. Terms are graded by exercise; promotion needs a recorded performance (Src; restated after review C8).** `[CON-0113 · invalid as stated]` (valid in the restated form)
- Terms are graded "OBSERVED", "OBSERVED as vocabulary, UNEXERCISED as behavior", "HYPOTHESIZED — not introduced" and EMERGING [S0044 L26–31]. Hypothesized terms are already listed in the table; they "enter this table only when engineering performs them" [S0044 L30] refers to their promotion.
- So the rule governs **promotion**, not admission. "Used" is not "performed": IGNORED is part of the vocabulary but has not been performed.
- **Int:** a counterpart of the dimension admission test (§3.2), for vocabulary grades.

**C2. Issued records are immutable; responses are separate records (Src).**
- "A recommendation is immutable once issued; responses live in SEPARATE records" [S0044 L37].
- This is §4.2 C1's discipline in practice: the decision is added beside the recommendation, never written into it.

**C3. Silence as a result (Src).**
- "Rules produce structurally honest silence *(absence of grounds → absence of advice)*" [S0044 L39].
- **Int:** a rule that does not fire has produced information, provided the record distinguishes "did not fire" from "did not run". S0044 does: the silent rules are listed by name [S0044 L18].

**C4. Identity may need three layers (Src, a hypothesis).**
- "identity may need THREE layers: RecommendationDefinition / Instance / Revision", because (rule, subject) cannot answer "did the rule change?" [S0044 L40]. S0044 holds it as "think, never implement, until a real question requires it" [S0044 L40].
- This resembles a type/instance split with versions added. (§6.3's CON-0086, which is INVALID, concerns contexts, so it is a comparison only.) The duplicate decision of §5.5 C5 is the first real question it might answer.

**C5. The impact measure is a change in engineering (Src).**
- "the measure: engineering changed, never recommendations issued" [S0044 L66]; "10 issued is an activity count and counts for nothing" [S0044 L70].
- After the first decision, "the first learning event is **3/5 complete**" (recommendation, decision, rationale; no commit, no outcome) [S0044 L54]. So no assessment exists yet. *This answers §4.2's open question; §4.2 itself is left unchanged until review.*

**C5a. A derived attribute, computed not stored (Src).**
- "recommendations accumulate AGE — and age is already computable from existing timestamps" [S0044 L41]: time-to-decision was 6.5 hours, "computed from EXISTING timestamps, zero new fields" [S0044 L52].
- This is a derived attribute in §3.2's sense: reported, not stored. It is an instance of minimality, since no new primitive is needed.

**C5b. The first decision tests §4.2's stage rule (Src; a finding on §4.2).**
- §4.2 says "the developer decides, always" (S0040). The first recorded decision was made by an AI at the user's direction [S0044 L42] (§5.5 C1). So the only run so far is mixed: the authorizer was a person, the executor and chooser an AI.

**C6. Classification refused for want of evidence (Src).**
- "NONE YET — insufficient evidence, said explicitly." [S0044 L62]. The discriminator is fixed in advance: lifecycle, confidence, versioning and effectiveness emerging mean a domain is forming; mere transformation means it stays a service [S0044 L64].
