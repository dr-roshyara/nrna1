## 6.6.1 In plain language

An AI agent works in a "harness": its own settings, hooks and operating instructions. S0066 says the harness should **point to** the project's knowledge and never **copy** it, because a copy becomes a second truth. Several agents can then run on the same knowledge. The guide also keeps apart:
- the knowledge from the agent's own memory;
- using the knowledge from changing it;
- "authorized", "implemented", "verified" and "completed".

## 6.6.2 Claims and derivations

**C1. Linked, not copied: no second authoritative home (Src; an instance of §1.10 and §0.7).** `[CON-0139 · invalid as stated]` (restricted form below, `[CON-0172 · provisional]`)
- "**Configure the AI agent to navigate and consume KnowledgeOS; do not copy KnowledgeOS into the agent harness.**" [S0066 L5]. A copy "creates a competing source of truth" [S0066 L142], and the principle is named "**Linked, not copied.**" [S0066 L146].
- **A second instance, at the level of models:** the next commission asks to "**relate, do not duplicate**" an existing model [S0070 L35] (ES-005.4).
- **The restricted form (Ded):** a copy is harmful only if it is used as **authoritative**, a second home for the same rule. The book itself admits copies that are not: the working context of §0.7 is assembled and then discarded; a derived representation (§1.14.4) has no standing; a pinned quotation (§1.16.6) says which version it means. So the rule is "no second **authoritative** home; a copy is admissible if it is derived and non-authoritative, pinned, or discarded". In this form it is §1.10's "one authoritative home per rule" plus §1.16.6. **It is probably not a new concept** (review C12, finding 1).
- **Two harms, kept apart.** The restricted form names only the **standing** harm: a copy used as a second authoritative home. A copy can also do a **currency** harm without being used as authoritative: a stale copy misleads its reader, which is §9.5's failure. And copied **scripts** are second implementations of a rule: "That would create multiple implementations of the same engineering rule." [S0066 L509] (on copying a check script into each harness, S0066 L496–508).
- **Ded (§1.10):** a copy used as authoritative is a second home for the same rule. When the original changes by an act, the copy does not, so the two diverge with no act on the copy. An agent reading the copy then applies a superseded rule. That is the failure case of §9.5.
- **But a path pointer is not enough (Ded, §1.16.6):** a pointer to a path is a *live* reference (a link can also be pinned, to a commit or a version). It meets §1.16.6 only with **detection** or **prohibition** of change. And it meets §9.5 only if the current rule actually reaches the acting session. S0066 says the harness holds "a **pointer to the portal**, not a copy of its contents" [S0066 L178]; it does not say how the agent learns that the target changed. *Int:* "linked, not copied" removes the second home, and leaves the distribution problem of §9.5 open.

**C2. One truth, several harnesses (Src; an analogy to K3, untested).**
- "**One project engineering truth. Multiple AI execution harnesses.**" [S0066 L49]. Each harness keeps its own machinery; Claude's and Codex's "must reference the **same engineering truth**" [S0066 L265].
- **Not a case of K3:** the harnesses work in one repository, with "one worktree and one git identity" (§6.5 C8), so git is their single serialization point. They are not independent applications in the sense of the Principal's act (§9.6.6a), and the case cannot bear on K4. S0066 says nothing about evaluating standing either; reading the evaluator CE into it would be the theory confirming itself. *Int:* an analogy for several applications on one kernel, and no more.
- **Protection between applications:** "do not modify the first agent's harness merely to make the second agent work" [S0066 L555]. *Int:* an application must not write into another application's space. This is the visibility and ownership boundary of §1.7 and §6.4, between peers.

**C3. Implementation does not become authority by existing (Src; an instance of P-8, §1.14.4, and A1).**
- The guide's hierarchy runs "KnowledgeOS / Governance → Architecture → DDD principles → Approved ADRs → Approved Design → Implementation → Verification", in order to prevent "an agent from making an implementation decision and then treating that implementation as architectural authority" [S0066 L420–435].
- **Ded (A1):** the existence of an implementation is act-free, so it confers no standing. This is P-8 ("executable … or consumed by AI" confers none) applied to code.
- **A homonym at the top node:** the hierarchy's top is "KnowledgeOS / Governance" [S0066 L420], and the contract says KnowledgeOS and governance "establish engineering authority" [S0066 L286–287]. Under A1 and P-8 a store confers nothing, and the sources' own map puts the authority origin "outside the software" [S0069 L13]. So S0066 uses "authority" for the **canonical home** of knowledge, not for **standing from an act**. The book marks it so; it belongs to the open split of "authority" into its senses (consolidation review, outline).
- **The hierarchy is a source proposal,** an ordering of authorities. Whether such a total order holds in general is the question of Ch. 2 §2.5 and Ch. 3 §3.8 (four separate orders). §2.5 rejects only ranks set by authors; a precedence enacted by the competent authority is a resolution by act. Whether the guide's hierarchy is an author's ranking or an enacted precedence is not shown in S0066. *Hyp:* that a linear order of authorities is sound.

**C4. Authorized, implemented, verified and completed are four states (Src; the family of CON-0092 and CON-0093).**
- "Authorized · Implemented · Verified · Completed. These are separate states." For example "Code exists ≠ Implementation authorized", "Tests pass ≠ Work completed" [S0066 L649–671].
- **Int:** these are four separate questions about one piece of work: an act (authorized), an occurrence (implemented), evidence (verified), and closure, which is again an act; S0067 records "the decision to close is a governance act (`G-1`)" [S0067 L93]. **They are not identical:** "Code exists ≠ Implementation authorized" allows implementation to exist before authorization (review C12). That is descriptive. S0066 also states a **normative** order, from approved design to implementation to verification (S0066 L338–358, L417–433), so the four states are distinct and the source orders them as a norm. They are the same split as running ≠ enforcing and executable ≠ executed (§3.9), on the side of work.

**C5. Agent memory is not the knowledge, and state needs an owner (Src; Hyp).**
- "**Do not treat agent memory as authoritative engineering truth**" [S0066 L853]. For any state artifact, ask "What does it represent? Who owns it? Who reads it? Who may write it? Is it authoritative or derived? Can multiple agents safely modify it?" [S0066 L686–691].
- **Int (F13, the kernel's attribute set):** `[CON-0140 · provisional]` the six questions are a candidate list of attributes every state artifact must carry: subject, owner, readers, writers, standing (authoritative or derived), and concurrency. *Hyp (one source):* that the list is complete. The book's own map already lacks an attribute table (F13); this is input to it.

**C6. Using the knowledge is not changing it (Src).**
- "Using KnowledgeOS ≠ Changing KnowledgeOS" [S0066 L583–585]; "Knowledge changes should be governed separately." [S0066 L598].
- **Int:** reading and writing knowledge are separate capabilities with separate authority, as in S0913's distinct permissions (observe, assert, derive, approve, execute; §8.6). An agent may "identify missing knowledge" without changing it [S0066 L594]. That is the absence lens of §5.4 (Z2) as a permitted act.

**C7. The harness is verified by someone other than its maker (Src; an instance of producer ≠ verifier, §1.14.3).**
- "Do not allow the agent that created its harness to be the only reviewer." [S0066 L740]. The check uses "another agent or human architect" [S0066 L742].
- **Int (§8.6 C1):** "another agent" may share the model, method or context of the first. The guide names process separation only.

**C8. The direction law: applications depend on the knowledge system, never the reverse (Src; Obs).**
- S0066: harness → KnowledgeOS → project engineering truth; "Never reverse this relationship." [S0066 L99]. S0069 measures a platform-level instance: "platform reads/guards app/; product never invokes platform", marked Observed [S0069 L53–54].
- **Int:** a candidate law for deliverable 3 (the kernel/application boundary): the dependency edge runs from application to kernel only. *Open:* its test against §1.14.4's rule on upward edges. *Scope:* S0066 gives the direction as a rule; S0069 gives one measured instance at the platform–product seam.

**C9. Further points from S0066 (Src).**
- **Harness and knowledge, defined by the source and blurred by it:** the agent's execution (how it operates, what it may modify, when it stops) belongs to the harness; architecture, DDD, governance and decisions belong to the knowledge [S0066 L57–83]. Yet the guide writes the authority statement, the process steps and the stop conditions **into** each harness contract [S0066 L281–326]. The line between application and kernel is not sharp inside the source.
- **The stop conditions are the refusal half only:** nine conditions to stop [S0066 L606–616]. An agent that always stops meets them all (the trivial case of §9.1 C2). Only the protocol (identify the conflict, cite evidence, explain the impact, stop, ask for resolution; S0066 L621–629, in meaning) is a must-do.

## 6.6.4 What does not hold

- **CON-0139, "never copies".** INVALID as stated: the book's own working context (§0.7), derived representations (§1.14.4) and pinned quotations (§1.16.6) are admissible copies. Restricted to "no second authoritative home", which is §1.10 + §1.16.6 (review C12, finding 1).
- **C2's reading of the harnesses as a case of K3 and of the evaluator.** They share one worktree and one git identity; it is an analogy (finding 5).
- **"S0066 … carries no date".** It has a file time and a first commit (finding 8).
- **C3's hierarchy as plainly an instance of P-8.** Its top node uses "authority" in another sense (finding 2).
