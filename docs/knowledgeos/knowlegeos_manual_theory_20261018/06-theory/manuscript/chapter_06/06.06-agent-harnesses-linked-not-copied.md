## 6.6.1 In plain language

An AI agent works in a "harness": its own settings, hooks and operating instructions. S0066 says the harness should **point to** the project's knowledge and never **copy** it, because a copy becomes a second truth. Several agents can then run on the same knowledge. The guide also keeps apart:
- the knowledge from the agent's own memory;
- using the knowledge from changing it;
- "authorized", "implemented", "verified" and "completed".

## 6.6.2 Claims and derivations

**C1. Linked, not copied: a harness references the knowledge and never reproduces it (Src; an instance of §1.10 and §0.7).**
- "**Configure the AI agent to navigate and consume KnowledgeOS; do not copy KnowledgeOS into the agent harness.**" [S0066 L5]. A copy "creates a competing source of truth" [S0066 L142], and the principle is named "**Linked, not copied.**" [S0066 L146].
- **A second instance, at the level of models:** the next commission asks to "**relate, do not duplicate**" an existing model [S0070 L35] (ES-005.4).
- **Ded (§1.10):** a copy is a second home for the same rule. When the original changes by an act, the copy does not, so the two diverge with no act on the copy. An agent reading the copy then applies a superseded rule. That is the failure case of §9.5.
- **But a link alone is not enough (Ded, §1.16.6):** a pointer to a live source is a *live* reference. It meets §1.16.6 only with **detection** or **prohibition** of change. And it meets §9.5 only if the current rule actually reaches the acting session. S0066 says the harness holds "a **pointer to the portal**, not a copy of its contents" [S0066 L178]; it does not say how the agent learns that the target changed. *Int:* "linked, not copied" removes the second home, and leaves the distribution problem of §9.5 open.

**C2. One truth, several harnesses: a concrete case of several independent applications (Src; Int).**
- "**One project engineering truth. Multiple AI execution harnesses.**" [S0066 L49]. Each harness keeps its own machinery; Claude's and Codex's "must reference the **same engineering truth**" [S0066 L265].
- **Int (§9.6.6a):** agent harnesses are independent applications of the knowledge system in the sense of the Principal's act of 2026-10-19 (K3). By §9.6, several harnesses agree on what is valid only if they share the evaluation rule over a shared record. That is the evaluator CE of theory turn 2, here in a practical case.
- **Protection between applications:** "do not modify the first agent's harness merely to make the second agent work" [S0066 L555]. *Int:* an application must not write into another application's space. This is the visibility and ownership boundary of §1.7 and §6.4, between peers.

**C3. Implementation does not become authority by existing (Src; an instance of P-8, §1.14.4, and A1).**
- The guide's hierarchy runs "KnowledgeOS / Governance → Architecture → DDD principles → Approved ADRs → Approved Design → Implementation → Verification", in order to prevent "an agent from making an implementation decision and then treating that implementation as architectural authority" [S0066 L420–435].
- **Ded (A1):** the existence of an implementation is act-free, so it confers no standing. This is P-8 ("executable … or consumed by AI" confers none) applied to code.
- **The hierarchy is a source proposal,** an ordering of authorities. Whether such a total order holds in general is the question of Ch. 2 §2.5 (priority numbers are rejected) and Ch. 3 §3.8 (four separate orders). *Hyp:* that a linear order of authorities is sound.

**C4. Authorized, implemented, verified and completed are four states (Src; the family of CON-0092 and CON-0093).**
- "Authorized · Implemented · Verified · Completed. These are separate states." For example "Code exists ≠ Implementation authorized", "Tests pass ≠ Work completed" [S0066 L649–671].
- **Int:** these are four separate questions about one piece of work: an act (authorized), an occurrence (implemented), evidence (verified), and closure, which is again an act. They are the same split as running ≠ enforcing and executable ≠ executed (§3.9), on the side of work.

**C5. Agent memory is not the knowledge, and state needs an owner (Src; Hyp).**
- "**Do not treat agent memory as authoritative engineering truth**" [S0066 L853]. For any state artifact, ask "What does it represent? Who owns it? Who reads it? Who may write it? Is it authoritative or derived? Can multiple agents safely modify it?" [S0066 L686–691].
- **Int (F13, the kernel's attribute set):** the six questions are a candidate list of attributes every state artifact must carry: subject, owner, readers, writers, standing (authoritative or derived), and concurrency. *Hyp (one source):* that the list is complete. The book's own map already lacks an attribute table (F13); this is input to it.

**C6. Using the knowledge is not changing it (Src).**
- "Using KnowledgeOS ≠ Changing KnowledgeOS" [S0066 L583–585]; "Knowledge changes should be governed separately." [S0066 L598].
- **Int:** reading and writing knowledge are separate capabilities with separate authority, as in S0913's distinct permissions (observe, assert, derive, approve, execute; §8.6). An agent may "identify missing knowledge" without changing it [S0066 L594]. That is the absence lens of §5.4 (Z2) as a permitted act.

**C7. The harness is verified by someone other than its maker (Src; an instance of producer ≠ verifier, §1.14.3).**
- "Do not allow the agent that created its harness to be the only reviewer." [S0066 L740]. The check uses "another agent or human architect" [S0066 L742].
- **Int (§8.6 C1):** "another agent" may share the model, method or context of the first. The guide names process separation only.
