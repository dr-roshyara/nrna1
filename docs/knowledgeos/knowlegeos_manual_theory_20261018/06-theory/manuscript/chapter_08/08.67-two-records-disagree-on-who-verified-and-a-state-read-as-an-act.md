## 8.67.1 In plain language

1. **The two records disagree on who did what.**
   - **S0315, the verification report:** gives its own id as one value and names a second process as the producer.
   - **S0316, the registration:** names that second process as the verifier and a third process as the producer.
   - **The identifiers differ in kind:** S0315 uses a full session id, S0316 short labels.
   - **Identity after a resume:** S0316's own id was in doubt after a resume. It settled the question by reading its own transcript, which the book counts as weak evidence, and a resume can carry a session's lineage forward.

   Neither record alone refutes independence, and neither establishes it. Only by combining the two, which contradict each other, do producer and verifier come out as one label. The book's rule that the record can refute independence assumes that the record is truthful, and here that premise visibly fails.
2. **The resolver reported that a human had started a lane whenever the lane's state was anything but "created".** A lane cancelled straight from "created" was reported as started, though no start was ever recorded. That reads an act off a state. The book holds that a state is not an act, and that an act is known only from its recorded entry.
3. **When the resolver answered AMBIGUOUS, it listed 62 candidates as its reason, while only 2 actually matched.** The book counts AMBIGUOUS as a success, but only with its correct reason. A second defect: one advisory field changed depending on how the same lane was asked for, so the same question received two answers.
4. **The verification supplies two premises that §8.66 C5 found unstated, within one harness:** the resolver reads no model setting, and its output is deterministic. That makes the byte-identity across providers a property of the code. The registration says the results "support" the view that the problem was legibility, "not that DeepSeek or Claude inherently cannot resolve". The live ambiguity supports the legibility half. A property that holds by construction cannot support the contrast with the models.
5. **The work item that built the self-governing workflow engine has no record in that engine.** Governance declines to create one, because creating it would decide the open question. It also notes that a wrong key on creation forks the record silently. If that store is the designated record, the work item's activation cannot be shown from it. And a silent fork is two records where there should be one.

On that reading, `d1612e03` is a fourth process and (c) loses support. *(a) has the most support; the window does not decide.* What would decide it is the provenance of S0315's writing act: a record of who wrote it, not an identifier it states (§8.10 C5, CON-0179). **C2. A state read as an act (Src; Ded; Int, agreement).**
- **S0315:**
  - "**Finding V-1 (F14).** `recorded_human_start_act` is **inferred** as `state !== 'CREATED'` (l.360). AST-015 accepts `CANCEL` directly from `CREATED`. … REGISTER S-c → CANCEL S-c (no START ever recorded) → workflow_state = 'CANCELLED' → recorded_human_start_act = true ← FALSE STATEMENT ABOUT THE RECORD" (L148–154);
  - "The registry's own V-3 text asserts truthfulness \"by entailment (CREATED implies no START)\". That entailment holds in the **forward** direction only; the implementation relies on the **reverse** (`not CREATED ⇒ START recorded`), which this probe falsifies." (L156).
- **Ded:** "CREATED ⇒ no START" does not imply "not CREATED ⇒ START". That would be the converse, and one counterexample, the probe, refutes it. *The source's own derivation is correct.*
- **Int:** the field reports an act ("recorded human start act") by reading a state. In the book, a state is not authority (§1.14), and an act is known from its recorded entry (A1; Q2 returns the entries). States are derived from entries (§9.8). Reading entries back from states runs the derivation the wrong way and fails where two entry sequences reach one state. *Agreement*, with a corpus instance of the failure. It "fails safe" (L156) because authorization also requires `ACTIVE`, but the field is still false about the record.
- **Not a new concept.**
