## 8.28.1 In plain language

1. **The kernel owns how things are done, not what they mean.** The estate proposes six tests for whether something belongs in the kernel. Two of them ask whether another domain would need the thing, and nothing in the estate answers that from evidence yet.
2. **Nobody in the estate can prove which AI process did something.** The record holds what a process says about itself. The book's design assumes the kernel can mark entries it accepted, in a way that cannot be forged; the estate has no such mark today.
3. **A design that exists only on paper is not the current system.** Neither is a test that only shows code exists.

## 8.28.2 Claims and derivations

**C1. The kernel owns the mechanism, not the domain meaning; six criteria for kernel membership (Src; evidence for BOOK-OUTLINE §3 and §6.6 C8).** *(No new concept.)*
- "The kernel owns the **mechanism**, not the domain meaning." (S0187 L221, in meaning). Example: authority mechanics belong to the kernel; "which architecture is correct" does not (S0187 L277–283, in meaning).
- Six criteria are given (S0187 L734–756, in meaning):
  1. would PKS need it?
  2. would a future knowledge domain need it?
  3. does it have its own invariant?
  4. does it have a stable lifecycle?
  5. can it exist without engineering-specific concepts?
  6. can EKS depend on it without the kernel depending on EKS?

  The dependency direction is kernel ← EKS, PKS (S0187 L776–792, in meaning).
- **Int.**
  - Criterion 6 is the book's direction law (§6.6 C8).
  - Criteria 3–5 are close to the boundary questions in BOOK-OUTLINE §3 ("necessary? must the kernel provide it? delegable?"). They are not the same questions, and no mapping is claimed.
  - Criteria 1 and 2 are counterfactual. No source in the window tests them against PKS evidence (S0191 L436–444, in meaning; step-1 inventory, S0187 item 3).
- *Revision within the line:* S0187 would grow the kernel "out of the existing EKS" (S0187 L671, in meaning). S0191 replaces this with a convergence study of EKS, PKS and the proposal, saying "we cannot yet conclude that all five belong in the kernel" [S0191 L354] and "we must not prematurely promote any of those into kernel boundaries" [S0191 L657]. The book's kernel is specified, not extracted (§8.26 C6), so neither method is the book's.

**C2. Nothing in the estate attests a process's identity; no gate reads it (Src; a second instance for §1.14.2-1; bearing on §9.17 (c′)).** *(No new concept.)*
- "Nothing in this estate can attest an AI process identity, so this line is a claim by the claimant" (S0190 L25, in meaning). The controls named are falsifiability and a reproducible measurement (S0190 L25, in meaning).
- Because identity "is evidential only and no gate reads it", the engine "would accept a START of `S5` and then report the lane `ACTIVE` and operable — while the evidence in it was false"; "The control here is not mechanical; it is this disclosure." (S0190 L103, in meaning).
- **Int (§1.14.2-1).** This is the S0097 L41 point a second time, in a different process: "no gate reads process identity". It shows, again, that the record can be unsound without challenging ARCH-INV-1.
- **Int (§9.17 (c′), marked for review).** The design sketch assumes that every entry the kernel accepts carries an attestation that cannot be forged. That attestation is of **acceptance by the kernel**, not of **who the caller is**: a different object. Even so, the estate has no attestation of either kind today. The assumption therefore has no instance in the estate; it is a requirement on a kernel that does not exist yet. This is recorded for T9-11 as a premise to be shown, not a defect in the sketch.

- **Int.** This is §8.26 C6's distinction (specified, not built), from the estate's side. It also matches the reporting rule this book now follows, that a finding is not resolved because code or tests pass.
