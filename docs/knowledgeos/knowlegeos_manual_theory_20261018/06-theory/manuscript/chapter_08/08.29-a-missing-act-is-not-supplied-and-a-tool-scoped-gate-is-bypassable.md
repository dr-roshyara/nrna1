## 8.29.1 In plain language

1. **When a required approval is missing, the one who needs it does not write it in.** Two processes were sent work that was registered to a third, and the start had never been recorded. Both stopped. They also did not create the file the work was meant to produce, since its name alone would have claimed the work had been done.
2. **"There is no implementation" was true only of the folders searched.** The code was in a folder that the search did not cover.
3. **A rule that is checked by one tool does not bind a different tool.** A file whose writing needs approval could be written through a shell command that the approval gate does not see (I-28).

## 8.29.2 Claims and derivations

**C1. A missing act is not supplied by the one who needs it; a deliverable whose name asserts an act is not created (Src; evidence for §8.27 C2 and §1.14.2-1).** *(No new concept.)*
- The lane was registered and handed off, but no human act was recorded. "a chat instruction is not a human START" (S0192 L64, in meaning). The commission "is not the `humanAct`": a human delivered it, but "what is missing is the **recorded** act" (S0192 L66, in meaning).
- Each process refused every way of supplying the act itself:
  - appending START as "human";
  - starting itself;
  - re-registering the lane under its own identity, which the mechanism refuses (R8);
  - editing the recorded context.

  "The reviewer must not be its own registrar, nor its own starter." [S0192 L78]
- The deliverable was not written: "a file with that name would assert that an independent review occurred. **The absence is the honest record.**" (S0192 L6, in meaning; S0193 L6).
- S0193 names the cause as mechanical, not a failure of independence: "the commission text is re-delivered to whichever session is live, while the registered lane names one fixed session and the `START` is never recorded" (S0193 L122, in meaning). Its proposed cure is "one recorded `START`, not another reviewer" (S0193 L122, in meaning), next to "I recommend neither as an authority act" (S0193 L120, in meaning). *Qualified (C36 W-02):* "both processes measured clean" rests on zero occurrences of a self-declared identifier the source calls "NOT attestable" (S0193 L20, L33, in meaning): independent on the record as far as a search can show, declared and not attested (CON-0127; §8.27 C3).
- **Int.**
  - This is §8.27 C2 again, seen from the process that would need the act: a recorded START without its human act would be a false record.
  - The file name adds a point. **An artifact's name can itself assert an act** (here, "independent review"), so creating the file would be a claim. The closest home is §8.25 C7 (a status tag is a claim), with §8.26 C3 ("an artifact that is not the act's record") secondary (C36 W-09).
  - The cause S0193 names fits §8.28 C2. Delivery does not read identity, and no gate does either, so the mismatch is caught only by the process's own disclosure.
- *n: one line (S0192, S0193), one chain, one estate.* *Trivial case (C36 appendix):* a gate that refuses everything satisfies every "must-never" rule here while no review is ever done; the required "must-do" is held under CON-0151 / F32 (§8.28 C3).

**C2. An absence claim holds only within its search (Src; an instance for §8.04 C3, CON-0120).** *(No new concept.)*
- S0194 reports: "no PKS implementation is present under `app/`, `resources/`, `tests/`, `routes/`, or `database/`. PKS current state appears **documentation-only**" (S0194 L42, in meaning).
- The baseline then measured an implemented capability layer under `scripts/lib/EngineeringKnowledge/`, with 36 test files (S0196 L68, L136, in meaning). The gate review re-measured it (S0195 L28–31, in meaning).
- **Int (CON-0120).** S0194 stated its search scope, and its claim was true within that scope. Read without the scope ("documentation-only"), it was false. The book's rule says an absence claim needs a statement of what was searched. *Placed (C36 W-07):* the scope is lost inside S0194 itself, from five directories at L42 to "in this repository" at L122 (in meaning). That passage stays hedged and orders "verify independently", and the verification worked (S0196 measured the code). This is §8.04 C3's pattern of a narrow claim generalised. *A second instance:* "PKS evidence never names EKS" (S0196 L742, in meaning) rests on a grep of four artifacts (S0195 L36, in meaning), and is stated without that scope.

**C4. Specified is not realized; internally sound is not shown to work (Src; evidence for §8.26 C6 and §8.28 C6).** *(No new concept.)*
- The PKS's own model records a conformance assessment that is **"specified, not realized"**: "nothing performs it, no role owns it" (S0196 L91, in meaning). Conformance is "strategically Core while operationally Absent" (S0196 L248, in meaning).
- Rule of the baseline: "Documentation describing a desired behaviour is never treated as evidence that it is implemented." [S0196 L46]
- The PKS charter as relayed: "sixteen reviews, five adoptions, and a frozen baseline establish that the methodology is INTERNALLY SOUND. They establish NOTHING about whether it WORKS." [S0196 L523]
- **Int.** This is §8.26 C6's distinction (specified, not built), found in the PKS corpus as well as the EKS one (§8.28 C6). *Whether PKS is a second system is open (T0-03b; restated at C36 W-01).* It is also the distinction this book applies to its own model: model v20 shows the designation rule internally consistent (I-11) under its assumptions, and nothing about any running record (§9.17 (c′)).

**C5. A gate scoped to one tool can be bypassed through another (Src; evidence for §1.5 and §1.9; an analogy to §9.17 R3 (c); header corrected at C37 W-08).** *(No new concept.)*
- The permission adapter maps governance to tool permissions. Its record names two limits: protection is by filename pattern, and "enforcement is **tool-scoped** (a `Bash` heredoc bypasses the `ask` gate — the record's own writing path; deferred)" (S0196 L494, in meaning).
- The same record reports behaviour that held where no gate existed: "tool enforcement says you COULDN'T; behavioral governance says you COULD have, and you didn't." (S0196 L623, in meaning).
- **Int (restated as an analogy, C36 W-04).** The case is a governed *file* written through another tool, past a permission adapter. That is the four-layer chain of §1.5 (policy → capability mapping → runtime adapter → configuration, S0031), with its enforcement mode in §1.9's census, and that is its home. Its relation to §9.17 is an analogy: the book's design does not close such a route; it **detects** a write that bypasses the kernel (fail-closed, the record leaves D), under an attestation **assumed** unforgeable, and the owner check rests on a declared application (§9.17 R3 (c), limit (ii)). A tool-scoped gate checks a route; the book checks the record.
- The behavioural case is evidence that governance can hold without enforcement. It is not evidence that enforcement is unnecessary. §1.9's census separates the two modes.
- *n = 1 record, relayed by S0196 (tier 5 in its own scale).*

**C6. A shared word is not a shared concept; authority, status, maturity and adoption are kept apart (Src; evidence for §5.00, F14, §1.13 and §1.14).** *(No new concept.)*
- "Lexical similarity is evidence for investigation, not evidence of bounded-context equivalence." [S0194 L58]. For each shared term the session records "shared lexical term", "PKS meaning independently established" and "semantic equivalence NOT established" (S0194 L60, in meaning). The baseline keeps PKS–EKS identity UNRESOLVED on that basis (S0196 L742, in meaning, X-01).
- The PKS identity model has three state classes (pre-authority, authoritative, superseded-terminal) and "four orthogonal axes preserved: authority ⊥ status ⊥ maturity ⊥ adoption". "Lifecycle exit from pre-authority: **only via a recorded human decision event.**" (S0196 L252–255, in meaning).
- **Int.**
  - The first point is the book's homonym discipline (F14; §5.00): one word can name two concepts.
  - The second matches §1.14 (state is not authority) and §8.10 (adoption is a recorded act).
  - Whether the four axes are orthogonal is the PKS model's own claim, relayed; no pair is given that shows non-dependence (compare §3.1). *§3.2's test, applied (C36 W-08):* the corpus's own test rejected INTENT-STATUS because its values duplicate status and authority ("Ratified" and "approved" are the same axis, §3.2); by that reading, M4's "adoption" values would fall on M4's own authority and status axes. Under the restated test (CON-0162: some in-scope distinction is inexpressible without the axis), adoption is undecided until a case is shown that needs it (restated at C37 W-09). On the other side, M4's authority ⊥ status agrees with §3.1's reason for marking CON-0003 invalid (standing mixed with lifecycle). No new dimension is proposed.

**C7. A view is never cited as authority; regenerability is held by discipline, not mechanism (Src; evidence for §8.17 and CON-0260).** *(No new concept.)*
- R-3: "nothing may cite a view as authority" (S0196 L490, in meaning). Projections must be regenerable from their sources. The baseline marks this property "enforced by discipline, not mechanism" (S0196 L409, in meaning), and the capability meant to check it (CAP-002) is deferred (S0196 L164, in meaning).
- **Int.** This is §8.17's "a projection, never a source" and CON-0260 in PKS's terms. The second point is the same distinction as C5: a rule stated, not a check run.
