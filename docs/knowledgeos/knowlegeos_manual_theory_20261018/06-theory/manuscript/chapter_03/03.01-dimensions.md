# 3.1 The six dimensions of a knowledge item

## In plain language

The corpus describes every piece of knowledge by six properties, which it calls independent; they are independent only up to a few stated constraints (below). What each property belongs to, the claim or the document that carries it, is an open fork (F37, below). Two documents can say the same thing in different forms; one rule can be approved yet unenforced; a claim can be official yet only a hypothesis. Each of these is a different question, and **mixing them up is the source of repeated mistakes** in the corpus's own history.

## The model (Src)

The corpus's "canonical meta-model" (2026-08-02) states [S0016 L58–63]:

> KnowledgeOS instance = NATURE × REPRESENTATION × GOVERNANCE-STATUS × AUTHORITY-SCOPE × EVIDENCE-STATUS × OPERATIONAL-STATE

| Dimension | Question it answers | Values (as given) | Origin | Concept |
|---|---|---|---|---|
| **nature** | what kind of thing is it? | decision · definition · constraint · description · finding · measurement (· skill) | RQ-002 [S0016 L41; GKC, Ch. 0 §0.3] | `[CON-0001 · validated]` |
| **representation** | how is it encoded? | executable · recorded · conversational · tacit | RQ-002 [S0016 L42; values: GKC L35–38] | `[CON-0002 · provisional]` (the bearer is open: below) |
| **governance status** | where is it in its life? | the 8 executable states draft · discovery · reviewed · approved · baseline · frozen · superseded · archived | RQ-002 + `statuses.yaml` [S0016 L43; S0012 L119] | `[CON-0003 · invalid]` |
| **authority scope** (this book: *canon scope*) | how far does it reach? | context-local · project · platform · constitutional (· runtime) | RQ-002 + placement scopes [S0016 L44; values: GKC L35–38] | `[CON-0004 · provisional]` |
| **evidence status** | how strongly is it held? | observed · inferred · hypothesized | new [S0016 L45] | `[CON-0005 · provisional]` (its necessity argument is uncounted; S0013 holds it as a hypothesis [S0013 L77]) |
| **operational state** | does it bite? | enforced · advisory · unexercised | new [S0016 L46] | `[CON-0006 · invalid]` (partly valid: MM-4 open, whether the value belongs to the artifact or to the rule it carries [S0016 L154]; T3-09) |

**Where the two new dimensions come from.** The corpus admits evidence status because "ten rediscoveries and four falsifications happened because claims were not graded". It admits operational state because it is "what '0 traversals' and my '0 of 11 enforcing' error both measured badly" [S0016 L45–46]. Neither existed as a field anywhere when it was admitted ("NOT a field anywhere"; "never formalized").

**This resolves the lead of Ch. 1 §1.8** ("6 dimensions (2 new, 1 rejected on test)"): four existing dimensions, two new (evidence status, operational state) and one rejected (intent status, §3.2) [S0016 L58]. The identification in Ch. 1 RC-17a, there marked Int, is confirmed at its primary source.

## Independence shown by use (Src → Ded)

The corpus tested the model by classifying six real artifacts without changing it [S0016 L121–135]. It cites two rows as "the orthogonality proof":
- a methodology constitution is **frozen** and **enforced** [S0016 L128];
- a capability is **realized** but only **advisory** [S0016 L127].

**That pair shows nothing (Ded):** the two rows differ on both dimensions, so a function from governance status to operational state (realized → advisory, frozen → enforced) fits them. A pair that does show it is in the same table:
- a verification report, **approved** and **unexercised** [S0016 L129], against `settings.json` `deny`, **approved** and **enforced** [S0016 L131]: one governance status, two operational states, so operational state is not a function of governance status;
- the same report [L129] against `PKS_..._M4`, **accepted-with-refinements** and **unexercised** [L130]: one operational state, two governance statuses, so the converse fails too. *(L130's status is outside the 8 values; review C3 notes. L132, the document itself, gives the same result with "draft".)*

**Ded:** such pairs show the two dimensions are **not functionally dependent**: neither value determines the other. It does not show **full independence** (that every combination occurs), which would need more cases. The corpus calls it "the orthogonality proof"; this book reads it as the weaker result.

**Independent except constraint set S.** Ch. 0 §0.3's constraint set S ties representation, governance status and canon scope together (r = Tacit ⇔ g = ⊥; r = Tacit ⇒ a = ⊥; n = Skill ⇒ r = Tacit). So the six are **independent except for S**, not independent outright.

**"Enforced" has three senses here, and CON-0006 merges what Ch. 2 §2.9 separates.** The table's "enforced" values mean different things: `Round39-MC` is "enforced (void-overriding)" by its **binding force** over lower rules [S0016 L128]; `settings.json` `deny` is enforced as a **runtime block** [L131]; a check that runs and reports, like `design-check.sh` (§2.9), is enforced only as a **lint**. "Unexercised" is a fourth kind of value: it records that a rule has not been used, not how it binds. Mapped onto §2.9's four properties and its exercise history:

| S0016 value (case) | §2.9 property it answers |
|---|---|
| enforced, `Round39-MC` (void-overriding) | **binding strength** (mandatory), with precedence enacted by the competent authority (§2.5); not an enforcement consequence |
| enforced, `settings.json` `deny` | **enforcement consequence**: blocks |
| advisory, CAP-001 | **enforcement consequence**: advises (an executable check that does not block) |
| the intended block ("advisory today; blocking once the gate is trusted") | **hardness** (intended enforcement) |
| unexercised | none of the four: **exercise history** (exercised / unexercised), kept apart from consequence (blocks / advises) |

**Ded:** operational state as one dimension conflates binding strength, enforcement consequence and exercise history. The bridge "how strongly a rule binds is not what enforces it" (Ch. 2 §2.9–2.10) holds between §2.9's properties; it is not shown by CON-0006, which mixes them. *Note:* S0016 L54 maps INTENT's "operational" to `baseline`, while L46 admits OPERATIONAL-STATE as a separate dimension; the two readings of "operational" differ.

## Why governance status is marked invalid here `[CON-0003 · invalid]`

The dimension is well sourced and its values are executable. It fails the **consistency** check:
- the book's Ch. 1 §1.2 shows that GKC's governance status mixes **standing** (canonical, superseded) with **lifecycle** (draft, archived);
- the corpus records that the authoritative lifecycle document draws "idea" and "research" as statuses, while the executable enum defines them as types [S0012 L118–125]. S0012 records this disagreement between a diagram and the enum as "an observation, not a defect claim" [S0012 L125].

As one dimension it is therefore **partly valid** (TODO T3-01). The corpus's own remedy separates provenance from standing in the `authority` field (PM-1, Ch. 1 §1.2), but leaves governance status as stated.

## What carries the dimensions (fork F37; Ded)

The model says what the six questions are; it does not say **what they are asked of**. The candidates do not agree:
- GKC makes the **claim** the atomic unit, located in the space, and a document "a bundle of claims" [GKC L19–20; Ch. 0 §0.3];
- S0016 writes "KnowledgeOS instance =" [S0016 L61], followed by the product of the six dimensions [S0016 L62–63], and classifies **artifacts** in its test [S0016 L121–135];
- one claim can have several carriers at once (Ch. 1 §1.5; §3.4).

Read with one bearer, the knowledge item, the dimensions are ill-typed: if a claim has two carriers, it has two representations, so representation is not a property of the claim. NATURE is a property of what is said, REPRESENTATION of what carries it, and governance status is, at least in part, a document lifecycle (§3.1 above; Ch. 1 §1.2). So CON-0001, CON-0002 and CON-0010 cannot all hold as written.

**Two meanings, kept apart (a definitional fork; neither is chosen here):**
- **(A) One bearer, the instance** `[CON-0184 · provisional]`: the bearer of all six is an **instance**, a pair (claim, carrier). It is well-typed if the values that belong to what is said are equal across all instances of one claim: nature, evidence status, the binding strength part of operational state (below), and, **if F6 splits governance status**, its standing part. Without F6, (A) gives each instance its own governance status, so two instances of one claim could carry different standing; whether that is admissible is not shown. This is S0016's form, with those constraints.
- **(B) A bearer per dimension** `[CON-0185 · provisional]`:

| Dimension | Bearer under (B) | Reason |
|---|---|---|
| nature | the claim | "a rule stays a rule in any encoding" [S0016 L41] |
| evidence status | the claim | how strongly a **claim** is held [S0016 L45] |
| representation | the carrier | one claim, several encodings (§1.5) |
| operational state | **split**, because CON-0006 conflates three properties (above): binding strength → the claim (the rule); enforcement consequence → the realization, the edge from a rule to what enforces it; exercise history → open | MM-4: `Round39-MC` "is enforced because of what it **says**, not how it is stored" [S0016 L154], which is binding strength, a property of the rule |
| governance status | **open** | it mixes standing (of a claim) with lifecycle (of a document) (Ch. 1 §1.2; CON-0003) |
| authority scope (canon scope) | **open** | it can be read as the reach of a claim or of a document's placement (Ch. 2 §2.8 scope senses) |

**The six-artifact test, re-run under (B)** [S0016 L121–135]. Each row is split into its claim and its carrier(s); nothing in the source is changed.
- *CAP-001 README:* the representation is given as "prose + code", a compound value. Under (B) it is one claim (a capability spec) with **two carriers**, a prose file and code, each with one representation. "Advisory" is an enforcement consequence and belongs to the realization by code.
- *`Round39-MC`:* "prose" is its carrier; "enforced" here is binding strength (void-overriding, mapping above), a property of its rules, not of the prose (MM-4). Under one bearer, the same item is both "prose" and "enforced"; under (B) the two values have different bearers.
- *`settings.json` `deny`:* the carrier and the enforcer are the same file. (A) and (B) agree here.
- *The verification report, `PKS_..._M4`, this document:* one carrier each; (A) and (B) agree.
- **Result, under (B):** all six artifacts classify without a compound value **on the four dimensions that have a bearer** (nature, evidence status, representation, operational state as split). Governance status and canon scope have no bearer under (B), so their values are not tested. The governance status values outside the 8 ("realized", "accepted-with-refinements"; review C3 notes) stay as recorded.
- **Under (A):** the same two compound cases also disappear: CAP-001 becomes two instances (spec, prose file) and (spec, code), and `Round39-MC`'s "enforced" is constrained to be equal across its instances. **So the re-run does not tell (A) from (B).** It shows only that one bearer for all six, without either split, is ill-typed. It tests well-typedness only, not independence or sufficiency.
- **What would decide F37 (Ded).** On the four dimensions with a bearer, (A) and (B) translate into each other: an instance's claim values are its claim's, its carrier values are its carrier's. They differ in two places. (i) Governance status and canon scope: (B) needs F6 (standing vs lifecycle) and the scope senses to give them bearers; (A) gives them the instance at once, without saying whether standing may differ between instances. (ii) **A claim with no carrier at all:** under (A) it has no instance and so no nature or evidence status; under (B) it keeps them. So F37 is decided by two questions: how F6 splits governance status, and whether the kernel must hold claims that no carrier carries (compare E4, Ch. 2 §2.8.8, where knowledge has no carrier in the examined class). If it must, (A) is incomplete without a null carrier.

**What depends on it:** F13 (the kernel's attribute set needs a bearer for each attribute); §3.4 (knowledge ≠ carrier is the claim/carrier split of (B)); §3.8 (relations between items need typed ends). Also dependent: Ch. 0 §0.3 and Ch. 1 §1.2 (the standing/lifecycle split, F6). The Principal decided that the bearer stays a fork (DB-5, 2026-10-20).

- **The test needed values outside the declared sets** (F-10): "accepted-with-refinements" [S0016 L130] is not one of the 8 statuses [S0020 L27]; SCOPE "product" [S0016 L129–130] is missing from CON-0004's value list.
