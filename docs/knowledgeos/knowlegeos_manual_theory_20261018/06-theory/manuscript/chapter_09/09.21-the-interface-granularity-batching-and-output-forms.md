## 9.21.1 In plain language

1. **The grain of a mechanism is not fixed by the book's behaviour.** Since the Principal cut O1 per act kind (U6), "one mechanism per input kind" and "one mechanism per act kind" are the same pool, for O1's kinds. But a single mechanism that handles several kinds case by case produces exactly the same steps, replies and answers, and so do guards counted separately. Only the count of a "minimal" kernel tells these apart. G is therefore fixed only up to such regroupings, and fixing it further is a question for the Principal.
2. **Composites and batching.** If the kernel's origin rule holds (a step adds only what its input carried), no step adds several acts from one input. That rule's kernel status is not yet decided, and the argument covers acts only. Evidence entries, which are not acts, and held acts are outside it. Batching, if allowed, changes no answer only if a batch is checked entry by entry, in order. A batch checked all at once, or all-or-nothing, behaves differently.
3. **The outputs.**
   - Q2 returns whole entries; its own text says so. Which entries count as "about k" is not fixed. The book elsewhere computes Q1 from Q2's entries, which needs grants and roots too.
   - Q1's "acts the answer rests on" is the support that the marks already use, a set. Q3's "with the grant" is the set of bases that hold, and roots can be among them. Q4's evidence entries raise the same question.
   - Each of these may be given as identities or as whole entries.
4. **What decides minimality.** The authentication status of entries in any answer's support is already shown through the marks. What no output shows, under identity outputs, is who recorded an act that is not about an item. How far that reaches depends on how the book's entry identity is read (B-07), an open repair.
5. **The Principal's decision:** which entries Req's core outputs must return whole.

## 9.21.3 Step 2: the objects

**(1) G-kind and G-act coincide on O1's kinds (Ded); G is not fixed by behaviour (Ded)** *(restated at review: A-11, B F10, F11, C-04, C-09)*.

| Step | Claim | Justification |

| 2 | Req's input kinds for O1 are O1's act kinds | U6 (a) (§9.19.9) |
| 3 | on O1's kinds, G-kind is G-act | 1, 2; §9.19.4 L161 |

*Scope:* the act kinds §9.10 L105 lists for O1. Two things are not stated in the book. First, the mapping of D's other kinds to O1–O4: annulment, ending, consumption, transfer, removal and designation; removal is both an act kind and an O3 input (C-09, A-11). Second, O2's cut (one kind or three). O3's "marked absence" has no admitted kind (B F11). O1's five kinds outside D have no clauses (T9-21).

**G is not fixed by behaviour (Ded; C at step 1, A and B probes).**
- In C6 a step is (s, x, m(s, x)). Guards, P_S, P_T, P_R, Req_O, observers and replies are all conditions on steps, runs, states and replies, not on which mechanism made a step (§9.1 L94, L100–107, L116, L120).
- Two pools with the same step relation therefore satisfy every condition of the type alike, except minimality.
- So a **case-split appender** that handles several kinds by input kind is behaviourally inert: one mechanism, m = m_i on disjoint X_i. It is **not** a composite, since it is no "sequence … in one step" (§9.19.4 L162, L173).
- Added to a per-kind pool it gives further minimal kernels. A scratch model (B, step 1) has two: {a_all} and {a_1, a_2, a_3}. This is form only.
- The same holds for **guards** counted as components. On the same guards in force, the same steps and replies result (§9.1 C6 result 8), though H-down and H-mono may fail (T6). *Scope (C-08):* this holds for the kernel's own steps; a separate guard in C6 can also constrain application mechanisms on the line (§9.19.4 L156).
- **Narrowed:** G is fixed by the book only up to case-split regrouping and guard placement. What separates the options is only how minimality counts, which bears on existence and uniqueness of the minimal kernel (T6; T9-04), not on any answer. **A decision**, needed only if mechanism minimality is to be stated (§9.21.5, question G).

**(2) Composites that append several acts: excluded, given the origin rule (Ded, on a stated premise; acts only)** *(restated at review: A-05, B F1, F2, F4, C-06, C-07, A-12)*.

| 1 | each input carries an act, or none | §9.1 L93 |
| 2 | each step consumes one input | §9.1 L94; §9.19.4 L159 |

| 4 | so it breaks step 0's invariant | 0, 3 |

*Not excluded:* a removal act together with its tombstone, which is one act (§9.13.2). *Not covered:*
- **W's evidence entries,** "not an act in A1's sense" (§9.10 L115). An input with act(x) = none carrying several evidence entries is not excluded (DC-3 met for W's kinds).
- **Held acts.** Law 18 → (c) reading (i) is decided (§9.11 L54, L96). If applying a held act is an O1 kind, the step that brings its object into existence carries two acts. Held acts are not a kind of D (§9.16 L192); with T9-21.
- **Law 12 and §1.16 L171.** An approval recorded in the same atomic change as its effect is two acts. Under law 12's refinement reading (§9.11 L48) that implementation step maps to two type steps; stated as a refinement premise (A-12).

**(3) Batching: excluded for acts on (2)'s premise; its observability depends on how a batch is guarded (narrowed)** *(restated at review: A-04, B F3, C-05, C-06)*.
- **Excluded for act entries,** by (2) step 0 with step 1: the same point §9.19.4 L164 makes. Batching of **non-act** (W) entries stays undecided.
- **If a batch is guarded entry by entry, in order** (premise; the book has no batch semantics):
  1. the append guard is checked at each new entry against the record before it (§9.13 L63, L73);
  2. every prefix of a record in D is evaluable (§9.13 L69);
  3. Q1–Q4 at a cut read a prefix (§9.10 Q1, Q2; H2);
  4. so the batch reaches the same records as single appends, and every core observer gives the same answer at every cut.
- **If a batch is guarded against the record before the batch** (snapshot), two uses of one single-use grant both pass (accepted only if T at append, §9.13 L45; single use prevented, §9.16 R3a). So does a designation that omits a maximal entry added in the same batch (§9.17). Records unreachable by single appends become reachable (**DC-4 met**).
- **If a batch is all-or-nothing,** guard verdicts and replies differ from single appends (§9.1 C6 result 8). Reachable records are a subset (DC-4 met on verdicts and replies).
- **Narrowed:** (i) no batching; (ii) sequential per-entry batching, which is unobservable by Req's observers and the reachable records; (iii) snapshot or all-or-nothing batching, which is observable. For act entries, (2)'s premise gives (i).

**What separates identities from whole entries (Ded; restated, A-06, B F6, C-03).** An entry's identity is given at §9.16 L93 in two clauses: "the fields CE* reads", and "kind and D's required fields other than the recorder and the status". Its B-07 note records that the two sets differ. Whatever the reading, a whole entry adds:
- (i) the **recorder** and **authentication status**;
- (ii) **content beyond the required fields**;
- (iii) **generic clauses outside the identity**: store, attestation, integrity result, `removed_by`.

**Under the "fields CE* reads" reading** it also adds (iv): **required fields no clause reads** (recording time, reason, delegation parent, I14, revocation scope, the act times of roots; §9.20.3 row 3). The literal "required fields" reading puts recording time into the identity, which conflicts with K2, since independent recorders must compute one identity (C-03). **The reading is an open repair (B-07), not settled here.**

**The merge (R2) does not make the whole-entry form well defined (Ded; restated, A-07, B F5).** R2's merge fixes the recorder (the set), the status (the weakest) and the tombstone, and requires agreement on the fields CE* reads (§9.16 L94–98). It fixes nothing for (ii), (iii) or (iv). Copies with one identity in two applications' records may differ there; the store differs by construction. So a whole-entry output of a merged record needs a merge rule for those fields. The draft's "a function of the copies" holds for (i) only.

*Restated at review (A-02, A-03, A-08, B F6, F7, F13, C-01, C-03). The quotient compares records by the **join** of everything every core output conveys (values, marks, act lists, entries), not output by output (C, rigour note).*

| the **recorder** of an entry not about an item (grant, root, annulment, ending, consumption, transfer, removal, designation) | **only** if some output returns it whole: Q1, Q3 or Q4 in whole-entry form, or Q2's scope (S-c)/(S-b) | (i) above; no clause reads the recorder outside the signed-as-other mark (§9.20.5) |

| content beyond the required fields | of entries some output returns whole: yes; else no | (ii) |

- **So the record is a minimal state for Req's core only if** every entry is returned whole by some output, which (S-b) gives. Short of that, the coarsest output-respecting quotient identifies records that differ only in the recorder (and content and generic clauses) of entries no output returns whole. D requires those fields by decision (the Principal's v6 decision on recorder and status), not by Req.
- *Scope:* stated over the join of Q1–Q4's outputs, with the readings above; restated from §9.20.5's models and the reviewers' probes, not a new model (B F13).

## 9.21.5 T9-22, the questions, and the consequences

**T9-22 is reduced to one question on the outputs, with one precondition and one separate question on G.**
- **Precondition, not a new choice:** the reading of entry identity (§9.16 L93, B-07), an open repair for §9.16 R2's restatement. It decides only the M6 row.
- **Question O (the outputs):**
  > *Which entries must Req's core outputs return whole?* (a) Only entries about an item, through Q2 (S-a), with Q1, Q3 and Q4 returning identities. The record is then not a minimal state, and the recorder of other entries, and of entries no output returns, is required by D's decision only. (b) Also every entry that Q1's support, Q3's set of bases and Q4's reasons name, through whole-entry forms or Q2 (S-c). Separated then for every returned entry; entries no output returns stay unseparated. (c) Every entry: Q2 as "the record itself, cut at s" (S-b), as §9.10 L186 and L194 already use it. The record is then minimal over the tested fields. **No recommendation:** the evidence fixes what follows from each option, not the choice.
- **Question G (granularity), needed only if mechanism minimality is stated:**
  > *Is mechanism minimality counted over a stated partition of the inputs into mechanism domains (and with guards inside or as components), or modulo equality of step relations (then G drops out)?*
- **T9-03 (consequence, not settled).** For act entries of D's kinds and on (2)'s premise, there are no composites, so §9.19.4's one direction applies: mechanism-minimal kernels consist of underivable mechanisms. The notions can still come apart through case-split regrouping, which §9.19.4 L173's "derivable" does not capture, and through guards as components. Primitive minimality needs a notion of derivability that covers case splits (A, B, C).
- **T9-04 (consequence, not settled).** T5's route (adding a composite) is closed for act entries on (2)'s premise. The remaining routes:
  - case-split appenders (inert in behaviour);
  - alternative appenders of one kind (ALT);
  - guards as components (T6);
  - snapshot or all-or-nothing batching, and W batching;
  - held acts.
  
  With disjoint per-kind domains, one appender per admitted kind, guards fixed and none of these routes, T10's condition holds and the minimal kernel is unique **within that pool**. Whether KnowledgeOS's pool is such a pool is not fixed.
- **Not changed:** U3 stays decided (b) for everything not derived here. No primitive is fixed, and no minimal kernel of KnowledgeOS is stated. RESEARCH-PURPOSE.md is not edited, and T9-21 is not started.
