## 9.6.1 In plain language

The question is where the record of authority belongs: in the kernel, or in one application context. The answer depends on three separate questions:
1. Does the kernel need such a record at all?
2. If it does, must the kernel build it itself?
3. Could an ordinary application context build it without breaking the kernel's rules?

The analyses below find:
- the machinery under test is **two capabilities**, not one;
- the first is needed only if the kernel must answer questions about standing;
- whether the kernel must build it depends on one assumption the Principal has to choose;
- an application context can build it, provided it keeps a short contract, and there is only **one** recorder for any given set of acts.

## 9.6.2 The capability under test, and the invariants it is tested against

**Definitions.**
- **The machinery (Src):** BC-7's record of work items, session assignments, transitions and grants, with its fold and its read-only queries (§6.5.2; S0067 L33, L73–77).
- **It is two capabilities (Ded, from the sources' own invariant I-4):** the record holds two parts "that never merge", `transitions[]` (lifecycle) and `grants[]` (authority) [S0071 L130]. The refinement measures each invariant against the part it governs, and finds the earlier confusion of the two to be "itself the conflation I-4 forbids" [S0078 L214]. So:
  - **CR-a, recording acts of authority:** registering a reference to an external human act, with its scope, status and time; refusing a registration without such a reference; answering whether a registration exists;
  - **CR-w, orchestrating governed work:** lanes, roles as values, handoffs, mutation ownership, START as the conjunction of a recorded handoff and a recorded human act.

  `[CON-0135 · provisional]`
- **Excluded from both (Src):** evaluating authority. BC-7 "can refuse a *malformed* act. It can never refuse an *unauthorized* one" [S0071 L293]. That is ARCH-INV-1 (§1.14.2).

**The kernel invariants used below (from the book; their status is given):**

| Name | Statement | Home · status |
|---|---|---|
| A1 | only an act confers standing | §1.6 · axiom |
| ARCH-INV-1 | the mechanism records authority and never grants it | §1.14.2 · Src (an ARB proposal) |
| RA | a record of an act is not the act; verification can show only that a record of sufficient integrity exists | §1.12 · Ded |
| I-1 (book) | knowledge never silently disappears | §0.5 · stated |
| U | a uniqueness needs a serialization point, or only detection is possible | §1.16.7 · Ded |
| PV | producer ≠ verifier | §1.14.3 · law of the corpus |

**The form of the test (§9.1):** Kernel(M) = P ∧ Req, where P is preservation with refusal and Req is the set of required capabilities. **Req for KnowledgeOS is not defined (T9-01).** So every result below is **conditional on a stated member of Req**, and the condition is named.

## 9.6.3 Analysis 1: is the capability necessary?

**Definition.** A capability c is **necessary for a requirement r** if no set of preserving mechanisms without c reaches r. It is **necessary** if it is necessary for some r ∈ Req.

**Assumptions, explicit.**
- (N1) A1 holds: standing changes only by acts.
- (N2) Acts happen outside the software; the kernel sees only records (RA, §1.12).
- (N3) **The candidate requirement R_s:** the kernel can answer "does item k have standing in scope x at time t?". This is the verifiability half of §1.12, and the "current authority is derived" of §1.14.1.

**Derivation, step by step.**
1. By N1, the answer to R_s depends on which acts occurred, with their scope and time.
2. By N2, the kernel can know of an act only through a record of it.
3. So any mechanism set that reaches R_s contains a mechanism that registers acts and answers whether a registration exists. That is CR-a.
4. **Therefore CR-a is necessary for R_s** (Ded, given N1–N3).
5. **CR-w is not reached by this argument.** Nothing in R_s needs lanes, handoffs or mutation ownership. CR-w would be necessary only for a requirement about how governed **work** proceeds, for example R_pv: role separation recordable and checkable, "making role separation recordable and checkable" being BC-7's contribution to I-8 [S0067 L68] (the sources' own reading of I-8). R_pv is a requirement of an engineering process, not, as far as shown, of a knowledge kernel.

**Trivial cases and boundary cases.**
- **Req = ∅:** nothing is necessary (§9.1 C3).
- **R_s ∉ Req:** a kernel that only tracks evidence, and never answers standing questions, does not need CR-a. Whether such a kernel would still be KnowledgeOS is a question about the purpose (RESEARCH-PURPOSE: standing is part of the knowledge model, §0.3), not about this derivation.
- **Necessity is of the capability, not of this mechanism.** Any representation with the required integrity would do: the JSON record, a ledger or a database.
- **R_pv ∈ Req:** then CR-w becomes necessary too, and the test must be repeated for it.

**What a reviewer would need to challenge it.**
- **A counterexample:** a mechanism set reaching R_s without any registration of acts, for example standing derived from content alone. That would contradict N1.
- **Or an argument** that N3 is not a requirement of the kernel.
- **Or a requirement** of the knowledge kernel that needs CR-w.

## 9.6.4 Analysis 2: must the kernel provide it?

**Definition.** The kernel **must** provide a capability c if:
- c is necessary (Analysis 1);
- **and** leaving it to an application context would leave some kernel invariant unprotected, or would make a kernel-level answer depend on which application is asked.

**Assumptions, explicit.**
- (K1) **Standing of a shared item is one fact per (item, scope, time).** Two contexts asking about the same item and scope get the same answer. *This is a modelling choice.* The book validated "one authoritative home per rule **per context**" (consolidation C1–C6; Ch. 1 §1.10), which allows standing to differ by context, but not the **occurrence** of an act. K1 is therefore stated for occurrence: an act occurred or did not, whoever asks.
- (K2) **Kernel closure (KC), optional:** every kernel invariant must be checkable with kernel-provided capabilities alone. `[CON-0136 · provisional]`

**Derivation, step by step.**
1. By K1, two records of the same act must agree on its occurrence and time. Where several writers could register the same act, agreement needs one serialization point, or else disagreement can only be detected (U, §1.16.7).
2. **A single serialization point does not have to be the kernel.** One context that serves all others gives one point too. The sources draw exactly this: BC-7 as an "OPEN HOST SERVICE" whose "downstream sessions are CONFORMIST" [S0069 L33–35; L63]. So step 1 does **not** force kernel placement.
3. **Under KC, it does.** If the kernel must check A1 and ARCH-INV-1 by its own means, it needs CR-a inside (Analysis 1, step 3). **Without KC,** the kernel can delegate CR-a and keep only the **contract** of the record.
4. **Therefore: "must the kernel provide CR-a?" is decided by KC, not by the evidence.** KC is a stipulation (§1.16.8: declared as such, accepted by adoption). The Principal decides it.

**Trivial cases and boundary cases.**
- **A middle option: the kernel owns the contract, an application owns the store.** The sources already treat the record schema as a "PUBLISHED LANGUAGE seam" at the writing side [S0069 L20–22; L62]. In the book's terms (§1.11, §6.1, CON-0072), this is the method-and-binding split: the kernel defines what a valid registration is, and an application binds it.
- **"Cross-cutting" does not decide it.** A mechanism that every context uses can still be delegable (§6.5 C0, premise stated at the consolidation). The ARB's "plane" ruling (§1.14.3) and ADR-AIP-03's context (S0065 L28) differ in classification. On this analysis they need not differ in substance: a plane can be one shared supporting context.
- **The later reconstruction keeps BC-7 a context and calls something else a control plane:** "C-5 Separation attestation … cross-context control-plane assurance capability … NOT a bounded context" [S0234 L126]. So the plane notion moved, in the corpus, from the record to attestation.

**What a reviewer would need to challenge it.**
- **An invariant that delegation breaks** even under a kernel-owned contract (then "must" holds without KC).
- **Or a proof that KC follows** from the other kernel invariants (then it is not a free choice).
- **Or a case** where one shared context cannot serve as the serialization point.

## 9.6.5 Analysis 3: can an application context provide it without violating the invariants?

**Definition.** Delegation of c to an application context is **safe** if, for every kernel invariant c bears on, the context **preserves** it (§6.5 C2: enforced on behalf of an owner elsewhere), and a breach would be detectable by the kernel.

**Assumptions, explicit.**
- (D1) BC-7 is an application context. It is accepted as a Supporting Subdomain, and "all seven: SUPPORTING" [S0069 L52; S0065 L28].
- (D2) The evidence is BC-7 **as built and measured on 2026-08-17**. Each measurement is a dated snapshot.

**Derivation: one invariant at a time, against the evidence.**

| Invariant | Preserved by BC-7? | Evidence | Intrinsic to being an application? |
|---|---|---|---|
| ARCH-INV-1 (records, never grants) | **yes** | a grant refuses to exist without `humanActRef` [S0067 L51]; "can never refuse an *unauthorized* one" [S0071 L293] | — |
| I-5 (only Governance writes authority) | **yes, totally on the authority part** | grant refuses any writer role but governance; 47/47 grants by governance [S0078 L206]. The two `architecture` recorders were HANDOFFs, by the required actor, which "confers nothing" [S0078 L201–204] | — |
| append-only history (I-1 in the mechanism) | **yes, in the mechanism** | `seq` contiguous in every record, 0 removal operations [S0072 L53] | — |
| I-1 at the store (nothing silently disappears) | **no, as built** | "Authority state has no provenance — all workflow records gitignored, zero history" [S0062 L113] | **no:** a tracked, durable store fixes it, and the move was decided, not executed (S0234 finding 4, in meaning) |
| fold fixity (derived state changes only with the log) | **no, as built** | "Interpretation authority is environment-swappable" [S0062 L112] | **no:** fix the interpreter |
| recorder attestation (who recorded) | **no** | producer identity is outside what BC-7 can attest; "So no bounded context in the accepted model owns" the ability to produce a lifecycle fact [S0078 L222] | **no, and not fixable by kernel placement either:** in a single-operator estate no one can attest it (S0164 L2420–2424, §8.6 C3) |
| PV checkable | partly: role separation is recorded, not decided | I-8 "PRESERVES only" [S0067 L68] | — |

**Result (Ded, given D1–D2):**
- **No invariant in this list requires kernel placement.** The three failures as built are a store without history, a swappable interpreter and an unattestable recorder. Each is either fixable inside an application context or unfixable anywhere.
- **So delegation is possible in principle**, provided the application keeps a contract. `[CON-0137 · provisional]`:
  1. registration only with a reference to an external act, and no evaluation of authority;
  2. one writer class for the authority part;
  3. append-only, on a durable store with history;
  4. a fixed fold;
  5. references never dereferenced (T-2).
- **The limit: at most one recorder per act-space (Ded, from U and K1).** If two application contexts both register the same acts, for two products, say, agreement on occurrence needs a shared serialization point. Without one, disagreement can only be detected (§1.16.7). **Delegation to one shared context is safe; delegation to several is not**, unless a kernel-level rule assigns each act-space exactly one recorder. That rule is a **kernel law even if the recording is delegated**.

**Trivial cases and boundary cases.**
- **One product, one context:** the limit is trivially met.
- **A refuse-everything recorder** preserves every invariant above and reaches no R_s. That is §9.1's trivial case, excluded by Req.
- **Snapshot dependence:** the counts (47 grants, 126 transitions) moved during the day (S0078 N-2). The result uses no rate.

**What a reviewer would need to challenge it.**
- **An invariant missing from the table** that an application context cannot preserve.
- **Or evidence** that one of the three failures is intrinsic to delegation.
- **Or a design** in which several recorders agree without a shared serialization point.
