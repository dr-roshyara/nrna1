## Summary (10 lines)
1. §9.21 is mostly honest and modest. Items (1) and (4) and the shape of the question hold.
2. Its largest weakness: (2) and (3) are labelled "Ded from C6's input-origin condition as written". But L93 only says an input carries one act. What forbids a mechanism from appending several entries from one input is the **origin transition invariant** (§9.1 L96), which is an example of I_T, and whose kernel status is not decided (F36 per-law list). The derivation uses an unstated premise, so DC-1 is met for (2) and (3) as labelled.
3. "Unobservable batching" assumes batches are guarded entry by entry. That is an assumption, not a derivation.
4. The R2 check is wrong in its reason. The merge rule fixes only recorder, status, tombstone and the CE*-read fields. Fields outside both identity and CE*'s reads (recording time, reason, delegation parent, coverage, content) have no merge rule, so a merged whole entry is not shown order-independent.
5. The minimality table overstates two rows: the "no core output returns it" row (which ignores Q3's grant output) and the identity-versus-entry difference "exactly" (which depends on a reading of L93).
6. Q3's "the grant" is not a function of the call when several grants cover it. §9.21 does not see this.
7. The pool-shape question (a case-split appender, an alternative route to uniqueness) is not stated for G. G is never given a class (derived, narrowed or a decision).
8. "T9-22 reduced to one decision" depends on Q2's scope being derived. That derivation rests on an interpretation plus registration being outside D, so it is narrowed at best.
9. Limits: no primitive is fixed and no open fork is used as decided, except the registration status noted at F6.
10. §9.21.7 and the proposed TODO rows are not yet written or applied. That is expected for a draft.

"One appended entry per step" is assumed or follows from the origin invariant. The unobservability argument holds under entry-by-entry guarding, for prefix cuts, and for removals of an act plus its named tombstone (F3). The single-use guard reads CE* on the record before the entry (§9.13 L37); under a batch it would also read earlier entries of the same batch, which is the F3 premise.
- **(4).** Right for answers; incomplete for existence and uniqueness; leaving it to T9-03 is within the limits, if T9-04 is also named (F14).
