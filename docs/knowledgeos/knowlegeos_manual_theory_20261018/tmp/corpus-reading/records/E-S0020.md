## 0. In business language

The repository's knowledge schemas were **parsed**, not skimmed, to classify what ontology exists. Result: **three ontology layers, not four.**

| Layer | State | What it is |
|---|---|---|
| **L-A documentation ontology** | **exists, executable, enforced** | 31 document types, 8 statuses, 5 authority levels, 9 audiences (including `ai`), 11 typed edges, 18 lint rules, a generated graph |
| **L-B platform ontology** | **does not exist** | its seed is the domain list D-1…D-7 (governance, method, runtime, capability, evidence, PKS) |
| **L-C product ontology** | **partly exists** | the product's 12 bounded contexts plus four unindexed catalogues |

A proposed fourth "engineering knowledge" layer is **declined**: the documentation ontology already covers engineering-knowledge kinds at document granularity.

**Three proofs** that platform concepts must not be forced into the document schemas:
1. **a key collision.** The product contexts already contain a `governance` key (the election product's authority models); adding "Engineering Governance" would collide in an enforced list;
2. **missing verbs.** The edge vocabulary has no `governs`, `produces`, `consumes` or `observes`;
3. **a subject mismatch.** Every schema field is a property of a document; "Engineering Method" has no reviewer or review date.

So L-B would **own and classify** L-A; L-A never contains L-B.

**A key reframing:** the graph covers only ~13% of documents because its scope is **declared** (`docs/knowledge/**` only). That is a scope decision someone made, so extending it is a **governance act, not a bug fix**.

**PKS as a projection:**
- supported in principle: the vocabulary already has `derived`, `derived_from`, and operating projections; the rule DP-2: "every projection regenerates from its sources and is cited as authority by nothing";
- blocked in practice: there is nothing to project from inside the declared scope;
- later annotated: falsified for existing artifacts, which are authored and accepted.

## 11. [I] Interpretation (kept apart)

- **[I-1] Declared scope as a governance object.** A boundary that someone declared is a **decision**, so changing it is an **act** that needs authority. This is the book's scope concept (Ch. 2 §2.8) applied to the knowledge platform itself: "the graph covers 13%" is not a defect claim but the result of a scope act.
- **[I-2] The key collision** is a concrete, mechanical instance of the identifier-namespace problem (Ch. 1 §1.10, T1-35): one short key (`governance`) cannot name both a product context and a platform domain inside one enforced enum.
- **[I-3]** "L-B would own and classify L-A" sets a **direction of governance between ontologies**: the platform's model governs the documentation model, never the reverse. It parallels "knowledge feeds authority, never holds it".
