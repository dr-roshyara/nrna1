## 0. In business language

The document answers: **how do the platform's concepts relate to each other, and which of those relations may never change?**

- **The chain from purpose to artifact.** A reviewer proposed Mission → Strategy → Principles → Capability. The author admits Strategy (charter documents) and Principle (six registers of numbered principles), and **discovers** a further layer, the **design policy** (`DP-n`): every capability in the Capability Catalog is bound to one design policy. The reviewer's other idea, that an **engineering domain** owns capabilities, is **rejected**: nothing in the repository binds a capability to a domain.
- **Thirteen concepts, each with a kind and an owner** (vision, mission, strategy, principle, design policy, capability, knowledge, artifact, knowledge space, PKS, product, runtime adapter, projection). The runtime adapter has **no owner found**.
- **A knowledge space is a declared scope**, not a folder: a set of artifacts with a declared boundary, an owner and a constitution.
- **Four relations** (contains, references, generates, depends on), filled in for every concept.
- **Eleven invariants vs eight implementation choices.** An invariant "may never be changed by a project"; a choice may be changed without breaking the model (folders, Markdown, YAML, the graph's scope, the runtime tool, identifier formats …). The author calls this the durable output: an adopter may change every choice and none of the invariants.
- **A success test:** eleven existing things are placed without a new top-level concept; the test surfaces a candidate twelfth invariant (a capability may read across a space boundary but never own what it reads).
- **Open:** adopt `DP-n` as a named layer (RO-1); are spaces nested or adjacent (RO-2); repair or withdraw the breached I-7 (RO-3); does the runtime adapter need an owner (RO-4).

## 5. Arguments

- **Admission by evidence:** a layer is admitted when an artifact class exists (Strategy: 12+ charters; Principle: six identifier series; DP: the catalog binding) and rejected when no binding artifact exists (domain ownership). This is the commission's rule (Q4) applied.
- **Invariant vs choice:** what a project may change without breaking the model is a choice; what it may never change is an invariant. The author's claim that this makes the model "a platform rather than a repository layout" (L130) rests on the choices being separable.
- **Success test:** if any existing thing needed a new top-level concept, the model would be incomplete (L134); none did (L150).
