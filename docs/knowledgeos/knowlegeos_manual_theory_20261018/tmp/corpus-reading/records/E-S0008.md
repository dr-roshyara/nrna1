## 0. In business language

The corpus's **meaning ledger**. Its premise: rediscovery happens "because meaning is lost, not files". So every major engineering term should have one meaning, one responsibility, one owner and one place.

**Seventeen concepts are examined.**

Kept as canonical (12):
- KnowledgeOS (the reusable platform; the name itself is a placeholder);
- the Product Knowledge Space (one product's knowledge and bindings; never reusable method);
- Engineering Knowledge; Engineering Capability (one design policy; the script is only its realization); Engineering Method; Engineering Governance;
- the Runtime Adapter; the Documentation Ontology (the executable ontology of *artifacts*); the Knowledge Graph (only a derived projection);
- three concepts the corpus "forces in": **Knowledge Space** (a declared boundary, an owner and a constitution; spaces nest), **Design Policy (DP-n)** (the named policy a capability executes, the anchor between principle and capability) and **Execution Asset (AST)** (prompts, instructions, hooks registered as runtime assets).

The rest:
- **rejected and merged:** Engineering Runtime (into Runtime Adapter); Engineering Ontology (into Documentation Ontology);
- **split:** Engineering Evidence, into a platform Evidence Protocol and product Evidence Records;
- **kept as candidates:** Platform Ontology (does not exist yet); Product Ontology (partial); Engineering Kernel (each part portable, the set failed).

**The "Prompt" question (raised in S0002) is answered:** a prompt is an Execution Asset with a runtime moment. What is missing is one *link* (capability ↔ asset), not a new layer.

**The proposed concept chain is corrected:**
- "KnowledgeOS creates PKS" is a hypothesis (n = 0);
- "PKS contains engineering knowledge" is **wrong**, since a PKS must not hold reusable method;
- "capabilities executed through runtime" hides that **41 enforced controls are runtime-side while every capability is advisory**.

**Eight named meaning conflicts remain open (SC-1…SC-8).** One is that "authority" holds provenance and standing in one field.

## 11. [I] Interpretation (kept apart)

- **[I-1]** The corrected chain separates **four strands** that earlier chains fused:
  - normative: mission → principle → design policy → capability;
  - representational: knowledge → artifact → space → projection;
  - executional: capability → script / execution asset → adapter;
  - evidential: work → records → protocol → platform.

  This matches the book's distinction between knowledge (which does not execute), carriers and execution (Ch. 1 §1.1, §1.5, §1.9).
- **[I-2]** P10 (enforcement is runtime-side; capabilities are advisory) is a concrete instance of Ch. 2 §2.10: the rules with meaning and the rules with enforcement are different sets.
