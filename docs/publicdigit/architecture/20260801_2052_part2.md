# Part 2 — Programme Architecture & Design Principles

---

# 2.1 Architectural Vision

The programme adopts a layered architecture consisting of three complementary domains:

```
                         KnowledgeOS
      (Reusable Engineering Platform & Methodology)
                           ▲
                           │
         Engineering Standards • Governance • Tooling
                           │
                           │
                           ▼
                    Product Knowledge System
                 (Operational Evidence Repository)
                           ▲
                           │
          Engineering Observations • Lessons Learned
                           │
                           ▼
                      PublicDigit Platform
             (Business Product & Operational System)
```

Each domain has a distinct responsibility and evolves at a different rate.

PublicDigit evolves through product requirements.

PKS evolves through engineering observations.

KnowledgeOS evolves only through validated operational evidence extracted from PKS.

This separation prevents engineering methodology from becoming coupled to a single product while ensuring that abstractions remain grounded in real engineering work.

---

# 2.2 Architectural Layers

The programme distinguishes between three architectural layers.

## Business Layer — PublicDigit

Responsible for solving business problems.

Examples include:

- Election Management
- Governance
- Evidence Management
- Audit
- Voting
- Contestation
- Adjudication

Business behaviour belongs exclusively to this layer.

---

## Knowledge Layer — PKS

Responsible for preserving engineering knowledge.

This includes:

- implementation observations,
- architectural discoveries,
- verification reports,
- engineering lessons,
- repository observations,
- operational evidence,
- documentation integrity findings,
- reusable implementation experience.

PKS records reality.

It does not prescribe engineering methodology.

---

## Engineering Layer — KnowledgeOS

Responsible for reusable engineering capability.

KnowledgeOS contains:

- engineering standards,
- architectural governance,
- review methodology,
- documentation governance,
- repository standards,
- reusable engineering tooling,
- AI engineering workflows,
- architectural patterns,
- engineering verification methods.

KnowledgeOS prescribes engineering methodology.

It does not contain business functionality.

---

# 2.3 Evolution Model

The programme intentionally avoids designing a complete engineering platform before operational evidence exists.

Instead, architecture evolves through repeated engineering cycles.

```
Business Need
      │
      ▼
PublicDigit Implementation
      │
      ▼
Operational Observation
      │
      ▼
PKS Recording
      │
      ▼
Pattern Recognition
      │
      ▼
KnowledgeOS Extraction
      │
      ▼
Future Engineering Improvement
```

Every reusable capability follows this lifecycle.

Capabilities are never generalized solely because they appear elegant.

Operational evidence is the promotion criterion.

---

# 2.4 Domain-Driven Design

Domain-Driven Design (DDD) is the primary architectural methodology.

The programme applies both strategic and tactical DDD.

---

## Strategic Design

Strategic DDD establishes:

- bounded contexts,
- ubiquitous language,
- context ownership,
- explicit authority,
- clear architectural boundaries.

Cross-context communication is explicit.

Business capabilities remain owned by their respective bounded contexts.

---

## Tactical Design

The programme employs tactical DDD patterns including:

- Aggregates
- Value Objects
- Domain Services
- Application Services
- Domain Events
- Repository interfaces
- Factory methods
- Explicit ports

Infrastructure concerns remain outside the domain model.

---

# 2.5 Architectural Dependency Principles

Dependencies are governed by explicit architectural rules.

The programme distinguishes between:

Business Capability

↓

Architectural Interface

↓

Current Implementation

Engineering decisions are expressed first in terms of business capabilities rather than implementation classes.

Example:

```
Evidence Preservation Window Resolution

        implemented today by

ResolvesEvidencePreservationWindow
```

This preserves architectural stability while allowing implementation evolution.

---

# 2.6 Evolutionary Architecture

The programme deliberately follows evolutionary architecture.

The architecture is considered:

- stable in principle,
- evolutionary in implementation.

New abstractions require operational justification.

Existing abstractions are refined only when supported by evidence.

Architectural redesign is considered exceptional rather than routine.

---

# 2.7 Repository Architecture

The repository itself is considered an architectural asset.

Repository organization follows explicit architectural rules rather than historical convention.

Major architectural areas include:

```
engineering/
```

Engineering methodology, governance, architecture standards, ADRs, verification.

```
docs/publicdigit/
```

Product documentation.

```
docs/knowledgeos/
```

Engineering platform documentation.

```
docs/pks/
```

Operational evidence and engineering observations.

```
.claude/
```

AI runtime state.

Session memory.

Planning.

Automation.

Runtime configuration.

The repository distinguishes runtime artifacts from persistent architectural knowledge.

---

# 2.8 Documentation Architecture

Documentation is governed by explicit architectural rules.

The programme established the following invariant:

> **Classification precedes placement. Placement is derived exclusively from classification. Placement shall never be used as evidence of classification.**

This principle governs all documentation organization.

Documentation placement is therefore deterministic rather than subjective.

The repository implements this using:

- documentation classification,
- declarative placement registry,
- resolver,
- verification tooling.

---

# 2.9 Documentation Evolution

Documentation evolves through two distinct stages.

## Classification

Every document receives explicit metadata describing:

- scope,
- steward,
- maturity,
- domain.

Classification establishes document identity.

---

## Placement

Placement is computed from classification.

The placement mechanism does not infer document identity.

It simply realizes the architectural rules.

This allows documentation organization to evolve without changing architectural semantics.

---

# 2.10 Repository Governance

Repository evolution follows explicit governance.

Deterministic repository transformations may be automated.

Examples include:

- documentation placement,
- repository migration,
- documentation validation,
- link repair,
- documentation integrity verification.

Repository changes that affect architectural meaning remain governance decisions.

Automation never decides semantics.

---

# 2.11 Operational Evidence Feedback Loop

Operational evidence is treated as a first-class architectural asset.

Every significant engineering activity may produce:

- implementation observations,
- architectural observations,
- governance observations,
- documentation observations,
- engineering patterns.

These observations are evaluated for:

1. Local implementation improvement.
2. PKS operational recording.
3. KnowledgeOS extraction.
4. Engineering Standard candidates.
5. Future architectural evolution.

Not every observation becomes reusable methodology.

Repeated operational evidence is required before promotion.

---

# 2.12 Long-Term Architectural Direction

The programme deliberately grows in the following order:

```
PublicDigit
      │
      ▼
Operational Evidence
      │
      ▼
PKS
      │
      ▼
KnowledgeOS
      │
      ▼
Future Products
```

The long-term vision is a mature engineering platform whose methodology has been validated through repeated real-world implementation rather than speculative architectural design.

KnowledgeOS therefore remains an evolving engineering platform, continuously refined through operational experience rather than predefined completeness.
