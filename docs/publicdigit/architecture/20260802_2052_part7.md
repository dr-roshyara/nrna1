# Part 7 — Engineering Methodology, Development Workflow & Quality Standards

---

# 7.1 Purpose

This section defines **how engineering is performed** within the programme.

It captures the engineering methodology that has evolved through operational experience and governance decisions.

Unlike the previous sections, which describe architecture, this section defines the engineering discipline used to evolve that architecture safely.

The objective is not merely to produce working software, but to produce software whose implementation, verification, documentation, and governance remain consistent over the lifetime of the programme.

---

# 7.2 Engineering Philosophy

Engineering follows several foundational principles.

## Architecture Drives Implementation

Implementation follows approved architecture.

Engineering shall not redesign architecture during implementation.

If implementation exposes architectural uncertainty, engineering pauses and returns the question to governance.

---

## Engineering Is Evidence-Driven

Engineering decisions shall be supported by evidence appropriate to their scope.

Evidence may include:

- implementation observations,
- verification results,
- operational experience,
- repository analysis,
- architectural reviews,
- accepted ADRs,
- engineering standards.

Engineering avoids speculative implementation.

---

## Incremental Evolution

Engineering progresses through small, verifiable increments.

Large architectural rewrites are avoided unless explicitly authorized.

Every increment should be:

- understandable,
- reviewable,
- reversible,
- independently verifiable.

---

# 7.3 Engineering Lifecycle

Every engineering activity follows a consistent lifecycle.

```

↓
```

Each phase has a distinct purpose and shall not implicitly perform another phase's responsibilities.

---

# 7.4 Work Package Model

Engineering work is organized into Work Packages (WP).

Each Work Package defines:

- objective,
- architectural scope,
- implementation boundary,
- acceptance criteria,
- verification requirements,
- governance authority.

Large objectives are divided into slices.

Each slice represents a small architectural increment.

---

# 7.5 Slice Development Model

Each implementation slice follows strict TDD.

```
Authorization

↓

RED

↓

GREEN

↓

VERIFY

↓

ACCEPT
```

### RED

Engineering writes the tests first.

Tests fail for the expected reason.

RED establishes that the requirement has been expressed correctly.

---

### GREEN

Engineering implements only enough behaviour to satisfy the approved scope.

Scope expansion is prohibited.

---

### VERIFY

Engineering demonstrates:

- tests pass,
- architectural boundaries remain intact,
- repository remains healthy,
- merge gates pass.

---

### ACCEPT

Acceptance is performed by governance.

Engineering never accepts its own work.

---

# 7.6 Test Strategy

Testing is considered part of the architecture.

The programme distinguishes multiple levels of testing.

---

## Unit Tests

Verify:

- entities,
- value objects,
- domain behaviour,
- invariants.

---

## Integration Tests

Verify:

- ports,
- adapters,
- application services,
- repository integration.

---

## Architectural Tests

Verify:

- dependency rules,
- layering,
- bounded-context integrity,
- architectural constraints.

---

## Verification Tests

Verify:

- repository integrity,
- documentation integrity,
- engineering standards,
- governance constraints.

---

## Merge Gate

The merge gate represents the final engineering verification.

Engineering work is considered complete only after all required gates succeed.

---

# 7.7 Domain-Driven Development Rules

Engineering follows tactical DDD.

Key expectations include:

- rich domain model,
- explicit business language,
- immutable value objects,
- protected invariants,
- infrastructure independence,
- capability-oriented design.

The domain model remains the centre of the architecture.

---

# 7.8 Coding Standards

Implementation follows consistent engineering standards.

General expectations include:

- expressive naming,
- small methods,
- single responsibility,
- explicit dependencies,
- constructor injection,
- immutable value objects where appropriate,
- behaviour-oriented design,
- minimal infrastructure leakage.

Code should communicate business intent before implementation detail.

---

# 7.9 Architectural Boundaries

Engineering shall preserve architectural boundaries.

Specifically:

- business rules remain inside the domain,
- orchestration belongs to application services,
- persistence belongs to repositories,
- infrastructure implements ports,
- frameworks remain outside the domain.

Boundary violations require governance review.

---

# 7.10 Documentation Standards

Documentation is produced continuously during engineering.

Documentation includes:

- ADRs,
- Engineering Standards,
- developer guides,
- verification reports,
- PKS observations,
- operational evidence,
- repository documentation.

Documentation is maintained alongside implementation rather than after implementation.

---

# 7.11 Documentation Governance

Every documentation artifact should possess:

- ownership,
- classification,
- lifecycle,
- steward,
- maturity,
- placement.

Documentation follows the approved documentation architecture.

Engineering does not invent new documentation structures without governance approval.

---

# 7.12 Repository Discipline

Repository health is continuously maintained.

Engineering verifies:

- broken links,
- document placement,
- migration integrity,
- documentation references,
- repository validation,
- engineering scripts.

Repository quality is considered part of software quality.

---

# 7.13 AI-Assisted Engineering

AI is an engineering collaborator.

Different AI systems may perform complementary roles.

Typical responsibilities include:

## Architecture AI

- architectural review,
- governance support,
- DDD coaching,
- architectural challenge,
- KnowledgeOS evolution,
- risk analysis.

---

## Engineering AI

- implementation,
- refactoring,
- testing,
- repository changes,
- migrations,
- documentation updates.

Responsibilities remain distinct even when performed by the same AI system.

---

# 7.14 Review Model

Every significant engineering change should undergo structured review.

Typical review dimensions include:

- architectural correctness,
- DDD correctness,
- repository integrity,
- documentation completeness,
- governance consistency,
- operational impact.

Reviews should focus on architectural quality rather than stylistic preference.

---

# 7.15 Operational Evidence

Engineering concludes by recording operational evidence where appropriate.

Examples include:

- implementation observations,
- engineering friction,
- architectural discoveries,
- tooling improvements,
- documentation improvements,
- reusable patterns.

Not every engineering activity requires operational evidence.

Evidence is recorded when future engineering can benefit from the experience.

---

# 7.16 KnowledgeOS Extraction

Operational evidence may eventually become reusable methodology.

Promotion follows this progression:

```
Implementation

↓

Observation

↓

Repeated Observation

↓

PKS

↓

Candidate Pattern

↓

Engineering Standard

↓

KnowledgeOS Capability
```

Promotion requires repeated operational validation.

Engineering does not generalize isolated observations.

---

# 7.17 Quality Attributes

Engineering continuously protects the following quality attributes:

- correctness,
- maintainability,
- traceability,
- auditability,
- determinism,
- consistency,
- repository integrity,
- architectural stability,
- documentation quality,
- operational reproducibility.

Quality is considered multidimensional rather than limited to functional correctness.

---

# 7.18 Engineering Principles

The programme consistently applies the following engineering principles:

- Architecture drives implementation.
- Engineering follows explicit authorization.
- TDD is the preferred implementation workflow.
- Every slice has explicit scope and boundaries.
- Verification precedes acceptance.
- Acceptance precedes closure.
- Repository quality is software quality.
- Documentation evolves alongside implementation.
- Operational evidence is preserved.
- AI augments engineering but does not replace governance.
- Reusable methodology emerges from repeated operational evidence.
- Long-term architectural integrity is preferred over short-term implementation convenience.

These principles collectively define the engineering methodology used throughout the programme and serve as the operational foundation for future development.
