# Part 6 — Repository Architecture, Documentation Structure & Engineering Platform

---

# 6.1 Purpose

The repository is considered an architectural asset rather than a passive source-code container.

Repository organization is intentionally governed because repository structure influences:

- engineering workflow,
- documentation discoverability,
- architectural consistency,
- AI-assisted engineering,
- operational evidence collection,
- KnowledgeOS evolution.

Repository organization is therefore part of the architecture itself.

---

# 6.2 Architectural Repository Model

The repository is organized into four primary architectural areas.

```
Repository
│
├── PublicDigit
│
├── Engineering Platform
│
├── Product Knowledge System
│
└── AI Runtime
```

Each area has explicit ownership and responsibility.

---

# 6.3 PublicDigit Area

The PublicDigit area contains the production system.

Typical contents include:

- application source code,
- domain model,
- infrastructure,
- APIs,
- database migrations,
- frontend,
- tests,
- product documentation.

This area exists to deliver business functionality.

It does not contain reusable engineering methodology.

---

# 6.4 Engineering Area

The `engineering/` directory is the canonical home for engineering governance.

Its responsibilities include:

- architecture,
- ADRs,
- engineering standards,
- governance,
- methodology,
- verification,
- architecture reviews,
- engineering reports,
- decision records.

This area represents the evolving engineering platform.

It is intentionally independent of any single product implementation.

---

# 6.5 Documentation Area

The documentation system follows the approved documentation-root model.

The canonical documentation roots are:

```
docs/

├── publicdigit/

├── knowledgeos/

└── pks/
```

These roots separate three distinct domains.

---

## PublicDigit Documentation

Contains documentation specific to the product.

Examples include:

- architecture,
- APIs,
- developer guides,
- user documentation,
- product ADRs,
- product knowledge.

---

## KnowledgeOS Documentation

Contains reusable engineering knowledge.

Examples include:

- governance,
- methodology,
- engineering standards,
- reusable patterns,
- engineering ADRs,
- engineering verification.

---

## PKS Documentation

Contains operational engineering evidence.

Examples include:

- implementation observations,
- operational evidence,
- lessons learned,
- engineering discoveries,
- repository observations,
- verification findings.

---

# 6.6 Documentation Classification

Every documentation artifact possesses an architectural identity.

Classification includes:

- Scope
- Steward
- Domain
- Maturity
- Classification

Classification establishes document identity.

Classification is independent of repository location.

---

# 6.7 Documentation Placement

Placement is deterministic.

Placement is computed from classification.

The governing invariant is:

> Classification precedes placement.
>
> Placement is derived exclusively from classification.
>
> Placement shall never be used as evidence of classification.

Repository organization therefore reflects architectural decisions rather than historical convention.

---

# 6.8 Documentation Lifecycle

Documentation follows an explicit lifecycle.

```
Create

↓

Classify

↓

Place

↓

Review

↓

Approve

↓

Maintain

↓

Archive
```

Movement within the repository changes placement only.

It never changes architectural meaning.

---

# 6.9 Documentation Domains

Three documentation domains currently exist.

---

## PublicDigit

Business documentation.

Audience:

- developers,
- operators,
- architects,
- users.

---

## KnowledgeOS

Engineering documentation.

Audience:

- architects,
- reviewers,
- engineering leads,
- AI engineering assistants.

---

## PKS

Operational engineering knowledge.

Audience:

- engineering,
- architecture,
- KnowledgeOS evolution,
- future product teams.

---

# 6.10 Legacy Documentation

The repository intentionally distinguishes between active documentation and historical material.

Legacy documentation remains preserved.

Examples include:

- legacy architecture folders,
- legacy developer guides,
- historical engineering documents.

Legacy material may be reorganized through governed repository evolution.

Historical preservation remains important for traceability.

---

# 6.11 AI Runtime Area

The `.claude/` directory is considered a runtime environment.

It contains:

- session context,
- planning,
- AI automation,
- hooks,
- runtime scripts,
- temporary engineering state.

It is intentionally separated from persistent architectural knowledge.

Persistent engineering knowledge belongs in the repository.

Runtime context belongs in `.claude/`.

---

# 6.12 Runtime vs Persistent Knowledge

The programme distinguishes two categories of knowledge.

## Runtime Knowledge

Characteristics:

- temporary,
- session-specific,
- mutable,
- execution-oriented.

Examples:

- session memory,
- current plans,
- temporary notes.

---

## Persistent Knowledge

Characteristics:

- version controlled,
- reusable,
- architectural,
- historically traceable.

Examples:

- ADRs,
- Engineering Standards,
- PKS observations,
- architecture documents,
- governance reports.

Persistent knowledge survives AI sessions.

---

# 6.13 Repository Governance

Repository evolution is governed.

Repository changes fall into two categories.

---

## Deterministic Changes

Examples include:

- documentation placement,
- migration,
- link repair,
- documentation validation,
- folder normalization.

These may be automated when supported by sufficient evidence.

---

## Semantic Changes

Examples include:

- ownership,
- classification,
- stewardship,
- architectural boundaries,
- engineering standards.

These remain governance decisions.

Automation never changes architectural meaning.

---

# 6.14 Repository Migration

Repository evolution preserves history.

Repository migrations are:

- explicit,
- documented,
- repeatable,
- evidence-based.

Migration history is considered engineering knowledge.

Repository evolution therefore becomes auditable.

---

# 6.15 Documentation Integrity

Documentation integrity is treated as a repository quality attribute.

Integrity includes:

- valid placement,
- valid classification,
- valid references,
- valid ownership,
- consistent navigation,
- architectural consistency.

Integrity verification is performed independently of document content.

---

# 6.16 Repository Validation

Repository validation operates at multiple levels.

Examples include:

- documentation validation,
- link integrity,
- placement verification,
- repository structure,
- engineering standards,
- architectural verification.

Validation confirms repository correctness.

Validation does not redefine architecture.

---

# 6.17 AI-Assisted Engineering

AI is considered an engineering participant.

AI responsibilities include:

- implementation,
- review,
- verification,
- documentation,
- architecture analysis,
- engineering recommendations.

AI does not exercise governance authority.

AI recommendations require appropriate architectural approval.

---

# 6.18 Engineering Automation

Automation is encouraged wherever engineering work is deterministic.

Examples include:

- documentation placement,
- migration,
- link repair,
- repository validation,
- engineering verification,
- documentation generation support.

Automation executes engineering policy.

It does not establish policy.

---

# 6.19 Repository Evolution

Repository organization is expected to evolve.

However, repository evolution follows these principles:

- preserve architectural meaning,
- preserve document identity,
- preserve traceability,
- preserve operational evidence,
- preserve governance history.

Repository evolution shall improve engineering without rewriting architectural history.

---

# 6.20 Repository Architecture Principles

The repository is governed by the following architectural principles:

- Repository organization is architecture.
- Runtime state is separate from persistent knowledge.
- Documentation is a first-class architectural asset.
- Classification determines placement.
- Repository migrations are explicit.
- Repository evolution preserves history.
- Deterministic repository operations may be automated.
- Semantic repository decisions remain governance responsibilities.
- Engineering methodology belongs to KnowledgeOS.
- Operational evidence belongs to PKS.
- Business documentation belongs to PublicDigit.
- The repository exists to support long-term engineering sustainability rather than short-term convenience.
