## 3. New defects found during principal review

### 3.1 Historical freshness test is incorrect

The test RM-15 expects an observation to be fresh when evaluated at a time before the observation was made.&#x20;

Eingefügter Text.txt



The freshness calculation uses:

\\[ \operatorname{age}=t-\operatorname{observationTime} \\]

If \\(t\\) is earlier than the observation time, this produces a negative age. A negative age must not automatically imply freshness.

For example, suppose a membership suspension is recorded on 10 June, but we reconstruct an authorization decision made on 5 June. The 10 June observation cannot be used as information available on 5 June.

Required correction: Distinguish freshness from temporal admissibility.

- Temporal admissibility asks whether the observation was available under the query's knowledge cutoff.
- Freshness asks whether an admissible observation was recent enough for the decision.
- Historical domain validity asks whether the fact applied at the relevant valid time.

A future observation may provide evidence about what actually happened earlier, but it must not be represented as information the system already knew.

### 3.2 The fallback test cases contain a contradiction

The reference-model tests say:

- `Unknown + NoRecord` for a sensitive action → `Indeterminate`.
- `Unknown + ExplicitAbsence` → `UseAuthoritativeFact(false)`.

But the model defines `observedValue` as `KnownTrue | KnownFalse | Unknown`. If the value is `Unknown`, the system cannot simultaneously treat it as an established `KnownFalse` without a defined absence-resolution rule.&#x20;

Eingefügter Text.txt



Required correction: Make the distinction explicit:

- A verified negative fact is `KnownFalse`.
- A confirmed absence can be mapped to a negative business conclusion only when the applicable domain rule says that absence has that meaning.
- An unexplained absence or failed retrieval must not be silently interpreted as false.

The reference model should return a reasoned result, not manufacture certainty from missing information.

### 3.3 Complete replacement revisions are not fully implemented

The document chooses complete replacement revisions rather than patches, but the correction model still permits field-oriented correction types such as `toState` and `effectiveAt`.&#x20;

Eingefügter Text.txt



Those representations are ambiguous unless the specification explicitly says how the unchanged fields are preserved.

For example, a second correction that replaces only the state must not accidentally restore the original, incorrect effective date.

Required correction: Either:

- Store a complete corrected transition snapshot in every correction revision; or
- Keep patch semantics and define a deterministic patch-folding algorithm.

I recommend complete replacement snapshots for the reference model because they are easier to inspect and verify. Each effective revision should contain all required transition fields.

### 3.4 Correction lineage must be resolved at the transaction-time cutoff

The proposed lineage graph creates edges from `supersedesCorrectionId`, but the pseudocode does not adequately handle a correction whose predecessor is missing from the corrections selected at transaction time \\(k\\).&#x20;

Eingefügter Text.txt



The implementation must not attempt to traverse an invalid reference or silently discard it.

Required correction: Validate that every correction reference resolves within the appropriate subject and permitted knowledge scope. If a valid lineage cannot be reconstructed at \\(k\\), return an explicit inconsistency or incomplete-history result according to the approved contract.

### 3.5 Initial-state lookup must respect the same historical cutoff

The document requires initial-state records to be versioned and only those declared by \\(k\\) to be visible in historical reconstruction. However, its `stateAt` pseudocode calls `initialState(subjectId)` without passing \\(k\\).&#x20;

Eingefügter Text.txt



That creates a risk that a later initial-state declaration contaminates an earlier historical query.

Required correction: Resolve the initial state using the same transaction-time cutoff as the transitions and corrections. Also distinguish a subject that was not yet created from a subject whose history is missing or unreconstructable.

### 3.6 Rule-status terminology is inconsistent

The document uses one vocabulary in its earlier rule-status specification and a different vocabulary in its current evidence-matrix tasks. In particular, `Unsupported` and `Contested` are not interchangeable.&#x20;

Eingefügter Text.txt



I recommend maintaining two independent dimensions:

| Dimension       | Suggested values                                             |
| --------------- | ------------------------------------------------------------ |
| Evidence status | Not assessed, supported, contradicted, insufficient evidence |
| Decision status | Proposed, approved, rejected, superseded                     |

A rule can have supporting evidence but remain unapproved. An approved rule can later be challenged by new evidence. This model avoids treating research findings and governance decisions as the same thing.

Principal-review conclusion: These are specification-level defects. They should be corrected before the reference-model tests are considered authoritative.

# Principal Review and Next-Step Execution: v0.4.5 Corrected Formal Semantics and Reference Model v0.1

## 1. Principal Reviewer Assessment

### 1.1 What This Review Contributes

The v0.4.4 review is the most disciplined artifact in the corpus. It does not accept the specification as complete. It identifies **six new defects**, all of which are genuine logical errors, not stylistic preferences. These defects must be corrected before the reference model is built, because a reference model built on defective semantics would simply reproduce the defects.

The six findings:

1. **Historical freshness test is incorrect.** Test RM-15 expects an observation to be "fresh" when evaluated at a time before the observation was made. The freshness formula `age = t - observationTime` produces a negative age, which is not the same as freshness. The model must separate **temporal admissibility** (was this observation available at the query's knowledge cutoff?) from **freshness** (is it recent enough?) and **historical domain validity** (did the fact apply at the valid time?).

2. **Fallback test cases contain a contradiction.** The tests treat `Unknown + ExplicitAbsence` as returning `UseAuthoritativeFact(false)`, but the model defines `observedValue ∈ {KnownTrue, KnownFalse, Unknown}`. If the value is `Unknown`, the system cannot treat it as `KnownFalse` without a defined absence-resolution rule.

3. **Complete replacement revisions are not fully implemented.** The correction model still permits field-oriented correction types (`toState`, `effectiveAt`), which are ambiguous unless unchanged fields are explicitly preserved. A correction that replaces only the state must not restore the original, incorrect effective date.

4. **Correction lineage must be resolved at the transaction-time cutoff.** The lineage graph creates edges from `supersedesCorrectionId` but does not handle the case where a correction's predecessor is missing at transaction time `k`. The implementation must not traverse invalid references or silently discard them.

5. **Initial-state lookup must respect the same historical cutoff.** The `stateAt` pseudocode calls `initialState(subjectId)` without passing `k`, which risks contaminating an earlier historical query with a later initial-state declaration.

6. **Rule-status terminology is inconsistent.** Earlier the specification used one vocabulary; now it uses another. `Unsupported` and `Contested` are not interchangeable. Evidence status and decision status must be two independent dimensions.

All six findings are **accepted**. They become the basis of v0.4.5.

### 1.2 Where I Strengthen the Review

The review is precise, but I identify five areas where it must be extended.

**Weakness 1 — The temporal admissibility / freshness / domain validity distinction is stated but not formalized.** The review correctly separates the three concepts but does not specify the formal model, the query contracts, or how they interact.

**Weakness 2 — The absence-resolution rule is required but not specified.** The review correctly requires a defined absence-resolution rule but does not specify:
- The formal mapping from `absenceReason` to a business conclusion.
- The distinction between "verified negative" and "unknown."
- How absence interacts with temporal admissibility.

**Weakness 3 — The correction lineage contract needs formal revision.** The review correctly requires complete replacement snapshots but does not specify:

- How lineage resolves when predecessors are missing at `k`.

**Weakness 4 — The initial-state cutoff contract needs formalization.** The review correctly requires `initialState(subjectId, k)` but does not specify:

**Weakness 5 — The two-dimension rule-status model needs operational details.** The review proposes Evidence status and Decision status as independent dimensions but does not specify:

## 2. Next-Step Deliverable: v0.4.5 Corrected Formal Semantics

### 2.1 Correction 1 — Temporal Admissibility vs. Freshness vs. Domain Validity

**Principle:** Three independent temporal concepts must be distinguished.

| Concept | Question | Determined By |
|---|---|---|
| Temporal admissibility | Was this observation available at the query's knowledge cutoff? | `observationTime ≤ k` |
| Freshness | Is the observation recent enough, relative to the evaluation time? | `t - observationTime ≤ freshness policy` |
| Historical domain validity | Did the fact apply at the valid time in the domain? | `validFrom ≤ v < validTo` |

**Formal semantics:**

```
isAdmissible(observation, k):
  return observation.observationTime ≤ k

isFresh(observation, t):
  if t < observation.observationTime:
    return NotYetObserved   // not a valid freshness state
  age = t - observation.observationTime
  if age ≤ observation.freshnessPolicy.normalFreshness:
    return Fresh
  if age ≤ observation.freshnessPolicy.maxStaleness:
    return Stale
  return Expired

isValidAt(observation, v):
  return observation.validFrom ≤ v < observation.validTo
```

**Query contract:**

```
evaluateFact(observation, v, k, t):
  if not isAdmissible(observation, k):
    return NotYetKnown

  if not isValidAt(observation, v):
    return NotValidAtTime

  freshness = isFresh(observation, t)
  if freshness == NotYetObserved:
    return NotYetObserved  // t is before the observation

  return { value: observation.observedValue, freshness: freshness }
```

**Key correction:** A future observation (`observationTime > t`) is **not fresh**. It is `NotYetObserved` — the system did not know it at the evaluation time.

**Required tests:**

| Test | Scenario | Expected |
|---|---|---|
| TA-T1 | Observation at t=5, evaluation t=3 | NotYetObserved |
| TA-T2 | Observation at t=3, evaluation t=5, fresh | Fresh |
| TA-T3 | Observation at t=3, evaluation t=5, stale | Stale |
| TA-T4 | Observation at t=3, k=2 | NotYetKnown |
| TA-T5 | Observation valid at v=2, query v=5 | NotValidAtTime |
| TA-T6 | Observation valid at v=2, query v=2, fresh, k=5 | Valid, Fresh |

### 2.2 Correction 2 — Absence Resolution (Explicit Mapping)

**Absence-resolution model:**

```
AbsenceResolution {
  absenceReason: NoRecord | NotApplicable | ExplicitAbsence | Unretrievable
  businessConclusion: KnownTrue | KnownFalse | Indeterminate
  ruleAuthority: string           // the domain rule that establishes this mapping
  requiresHumanReview: boolean
}
```

**Default mappings (subject to domain override):**

| `absenceReason` | Business conclusion | Rationale | Human review |
|---|---|---|---|
| ExplicitAbsence | KnownFalse | Business explicitly recorded absence | No |
| NotApplicable | KnownFalse | Fact type does not apply | No |
| NoRecord (sensitive action) | Indeterminate | Absence is ambiguous | Yes |
| NoRecord (non-sensitive action) | KnownFalse | Default for non-sensitive | No |
| Unretrievable | Indeterminate | Operational failure | Yes |

**Domain override rule:**

```
resolveAbsence(absenceReason, action, domainPolicy):

  override = domainPolicy.absenceOverrides[absenceReason]

    return override

  return default
```

### 2.3 Correction 3 — Complete Replacement Snapshots (Formal)

**Principle:** Every correction revision contains the complete corrected transition. No field-oriented patches.

**Revised correction model:**

```
TransitionRecord {
  id
  subjectId
  fromState
  toState
  effectiveAt
  recordedAt
  authority
  reason
  version
}

CorrectionRecord {
  id
  subjectId
  targetTransitionId
  replacementSnapshot: {            // complete revised transition
    fromState
    toState
    effectiveAt
    authority
    reason
  }
  recordedAt
  authority
  reason
  supersedesCorrectionId (nullable)
}
```

**Key rules:**

| Rule | Statement |
|---|---|
| CR-1 | Every correction contains a complete snapshot |
| CR-2 | Applying a correction replaces the transition entirely (for interpretation purposes) |
| CR-3 | The original transition record is immutable |
| CR-4 | The replacement snapshot must be self-consistent (valid state machine transition, `effectiveAt ≤ recordedAt`) |
| CR-5 | Correction chains form a single valid lineage |

**Effective revision resolution:**

```
resolveRevision(transitionId, corrections, k):
  chain = { c ∈ corrections
            | c.targetTransitionId = transitionId
            ∧ c.recordedAt ≤ k }
  if chain = ∅: return originalTransition(transitionId)

  # Validate lineage before traversal
  lineageValidation = validateLineage(chain, k)
  if lineageValidation.status == invalid:
    return InconsistentLineage(reason=lineageValidation.reason)

  # Single root, single terminal
  root = lineageValidation.root
  terminal = lineageValidation.terminal
  return terminal.replacementSnapshot
```

**Lineage validation (before traversal):**

```
validateLineage(chain, k):
  # Check 1: Every supersedesCorrectionId resolves within the chain
  for c in chain:
    if c.supersedesCorrectionId ≠ null:
      if c.supersedesCorrectionId ∉ { c'.id | c' ∈ chain }:
        return { status: invalid, reason: "missing predecessor" }

  # Check 2: Single root
  roots = { c ∈ chain | c.supersedesCorrectionId = null }
  if |roots| ≠ 1:
    return { status: invalid, reason: "multiple roots" }

  # Check 3: Acyclic
  if hasCycle(chain):
    return { status: invalid, reason: "cycle" }

  # Check 4: Single terminal
  terminals = { c ∈ chain | no successor in chain }
  if |terminals| ≠ 1:
    return { status: invalid, reason: "multiple terminals" }

  return { status: valid, root: roots[0], terminal: terminals[0] }
```

**Required tests:**

| Test | Scenario | Expected |
|---|---|---|
| CR-T1 | Single correction, all fields | Replacement applied |
| CR-T2 | Correction chain, terminal wins | Terminal replacement |
| CR-T3 | Missing predecessor | InconsistentLineage |
| CR-T4 | Multiple roots | InconsistentLineage |
| CR-T5 | Cycle | InconsistentLineage |
| CR-T6 | Multiple terminals | InconsistentLineage |

### 2.4 Correction 4 — Correction Lineage at Transaction Time Cutoff

**Principle:** Lineage must be resolved using only records known at `k`. Missing predecessors at `k` produce `IncompleteHistory`, not silent traversal failure.

**Formal algorithm:**

```
resolveEffectiveHistory(subjectId, k):
  # Step 1: Select records known at k
  transitions = { t | t.subjectId = subjectId ∧ t.recordedAt ≤ k }
  corrections = { c | c.subjectId = subjectId ∧ c.recordedAt ≤ k }
  retractions = { r | r.subjectId = subjectId ∧ r.recordedAt ≤ k }

  # Step 2: Resolve effective revision for each transition
  effective = {}
  for t in transitions:
    resolution = resolveRevision(t.id, corrections, k)
    if resolution is InconsistentLineage:
      effective[t.id] = { status: inconsistent, reason: resolution.reason }
    else:
      effective[t.id] = { status: ok, transition: resolution }

  # Step 3: Apply retractions
  for r in retractions:
    if r.targetTransitionId ∈ effective:
      effective[r.targetTransitionId] = { status: retracted }

  # Step 4: Return effective history
  return effective
```

**Result model:**

```
EffectiveHistory {
  transitions: Map<TransitionId, EffectiveEntry>
  inconsistencies: [InconsistencyRecord]
  retracted: Set<TransitionId>
}

EffectiveEntry {
  status: ok | inconsistent | retracted
  transition: TransitionRecord (if ok)
  reason: string (if inconsistent)
}
```

**Required tests:**

| Test | Scenario | Expected |
|---|---|---|
| CL-T1 | Correction known at k, predecessor known | Valid resolution |
| CL-T2 | Correction known at k, predecessor not known at k | IncompleteHistory for that transition |
| CL-T3 | Retraction known at k, transition known | Retracted |
| CL-T4 | Multiple transitions with corrections | All resolved independently |

### 2.5 Correction 5 — Initial-State Lookup at Transaction Time Cutoff

**Principle:** Initial state must be resolved using `declaredAt ≤ k`. Later declarations must not contaminate earlier queries.

**Formal algorithm:**

```
resolveInitialState(subjectId, k):
  records = { r | r.subjectId = subjectId ∧ r.declaredAt ≤ k }
  if records = ∅:
    return { status: unknown }
  latest = max(records, by=(declaredAt, version))
  return { status: ok, initialState: latest.initialState }
```

**Integration with state query:**

```
stateAt(subjectId, v, k):
  # Step 1: Resolve initial state at k
  initial = resolveInitialState(subjectId, k)
  if initial.status == unknown:
    return { state: Unknown, reason: "no initial state at k" }

  # Step 2: Resolve effective history at k
  history = resolveEffectiveHistory(subjectId, k)

  # Step 3: Filter to prefix (valid time ≤ v)
  prefix = { e ∈ history.transitions
             | e.status = ok
             ∧ e.transition.effectiveAt ≤ v }

  suffix = { e ∈ history.transitions
             | e.status = ok
             ∧ e.transition.effectiveAt > v }

  # Step 4: Validate prefix independently
  prefixValidation = validateSequence(
    sort(values(prefix), by=(effectiveAt, version)),
    initial.initialState
  )

  # Step 5: Report suffix inconsistencies separately
  laterInconsistencies = collectInconsistencies(suffix)

  # Step 6: Return result
  if prefixValidation.status == invalid:
    return { state: Inconsistent, reason: prefixValidation.reason, scope: "prefix" }

  if prefixValidation.finalState == NotCreated and no transitions:
    return { state: NotCreated }

  return {
    state: prefixValidation.finalState,
    validAt: v,
    knownAt: k,
    laterInconsistencies: laterInconsistencies
  }
```

**Distinct result cases:**

| Case | Condition | Result |
|---|---|---|
| NotCreated | No initial state, no transitions, or explicit `NotCreated` | `NotCreated` |
| Unknown | No initial state known at k, but transitions exist | `Unknown` |
| IncompleteHistory | Some transitions have unresolved revisions | `IncompleteHistory` |
| Valid | Prefix validates | The prefix's final state |
| Inconsistent | Prefix fails validation | `Inconsistent` |

**Required tests:**

| Test | Scenario | Expected |
|---|---|---|
| IS-T1 | No initial state at k | Unknown |
| IS-T2 | Initial state declared at k | Use it |
| IS-T3 | Initial state declared after k | Not visible at k |
| IS-T4 | Prefix valid, suffix inconsistent | Prefix state + suffix inconsistencies |
| IS-T5 | Prefix inconsistent | Inconsistent |

### 2.6 Correction 6 — Two-Dimension Rule Status

**Principle:** Evidence status and decision status are independent dimensions.

**Evidence status:**

| Value | Meaning |
|---|---|
| NotAssessed | No evidence collected yet |
| Supported | Source evidence supports the rule |
| Contradicted | Source evidence contradicts the rule |
| InsufficientEvidence | Evidence is inconclusive |

**Decision status:**

| Value | Meaning |
|---|---|
| Proposed | Rule is a candidate |
| Approved | Decision authority has accepted the rule |
| Rejected | Decision authority has rejected the rule |
| Superseded | Rule has been replaced by a newer version |

**Rule record:**

```
RuleRecord {
  ruleId
  version
  proposition
  scope
  domain
  evidenceStatus: EvidenceStatus
  evidenceRefs: [SourceCitation]
  decisionStatus: DecisionStatus
  decisionAuthority: string (if Approved or Rejected)
  decisionDate: timestamp
  counterexamples: [CounterexampleRecord]
  effectiveFrom: timestamp
  reviewTrigger: [Condition]
  dependencies: [RuleId]
}
```

**Transition rules:**

| Transition | Condition | Authority |
|---|---|---|
| NotAssessed → Supported | Source found and supports | Research team |
| NotAssessed → Contradicted | Source found and contradicts | Research team |
| NotAssessed → InsufficientEvidence | Sources inconclusive | Research team |
| Supported → Contradicted | Counterexample found | Research team |
| Proposed → Approved | Decision recorded | ARB |
| Proposed → Rejected | Decision recorded | ARB |
| Approved → Superseded | New version approved | ARB |

**Required tests:**

| Test | Scenario | Expected |
|---|---|---|
| RS-T1 | Rule with source support, no decision | Evidence: Supported, Decision: Proposed |
| RS-T2 | Rule with ARB approval, later contradicted | Evidence: Contradicted, Decision: Approved (flagged) |
| RS-T3 | Rule superseded by new version | Evidence: (inherited), Decision: Superseded |

### 2.7 Reference Model v0.1 Specification

The reference model implements the v0.4.5 semantics independently. It does not use production code, schemas, or infrastructure.

**Minimum operations:**

| Operation | Behavior |
|---|---|
| `isAdmissible(obs, k)` | `obs.observationTime ≤ k` |
| `isFresh(obs, t)` | Compare `t - obs.observationTime` to freshness policy; return `NotYetObserved` if `t < obs.observationTime` |
| `isValidAt(obs, v)` | `obs.validFrom ≤ v < obs.validTo` |
| `resolveAbsence(obs, action, policy)` | Map `absenceReason` to business conclusion |
| `fallbackDecision(obs, action, t, policy)` | Total function with reason codes |
| `resolveRevision(transitionId, corrections, k)` | Complete replacement snapshot with lineage validation |
| `resolveEffectiveHistory(subjectId, k)` | Effective entries with inconsistencies marked |
| `resolveInitialState(subjectId, k)` | Use `declaredAt ≤ k` cutoff |
| `validateSequence(transitions, initialState)` | Transition legality + continuity |
| `stateAt(subjectId, v, k)` | Prefix-isolated bitemporal query |
| `reconstructDecision(decisionId, k)` | Recompute decision using records known at k, evaluated at original `t` |

**Verification gates:**

| Gate | Requirement |
|---|---|
| Gate A | Hand-verified test cases (RM-01 to RM-16, corrected) pass |
| Gate B | Property-based tests for determinism, correction preservation, retraction, prefix isolation, ordering validity, fallback behavior, three-clock independence |
| Gate C | Adversarial counterexamples: invalid lineages, missing initial states, future observations, inconsistent transitions |
| Gate D | Discrepancy resolution: all disagreements between spec, reference model, and production investigated and documented |
