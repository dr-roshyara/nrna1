Membership: decision paper for Q1, Q2, Q3, Q6 and G-5

  This is Session 1's recommendation, not an approval. I made no repository changes. Every key claim below was re-checked against the sources this session; the evidence is in the appendix.

  1. Executive summary

  Recommended path, in order:

  1. Q3 first: keep the Principal Reviewer's original recommendation in an official, traceable place.
  2. Q2: close the "lost test outputs" gap honestly. The 10 October outputs are gone, their fingerprints stay as history, and the 16 October run (A1) is the evidence for today's code.
  3. Q1: formally accept the C-1 correction rules with listed residual risks. One of those risks becomes a precondition for building the correction commands. This differs from your starting hypothesis (defer). My check found the V-2 gap is not reachable through any code path today, and the contract itself defers that area to a later slice. Deferral is still a valid choice if you want zero known gaps at acceptance; §2 explains both.
  4. Q6: commission a dedicated Membership test database, with its own restricted account and proof of identity. Then the ARB re-checks the security gate.
  5. G-5: name one engineer for a read-only, findings-only health check of the wider Membership test suite.

  Nothing here authorises implementation.

  2. Business decision paper

  Q1: Accept the C-1 correction rules (PBDIGIT-268)?

  The issue in business terms. C-1 is the engine rule set that lets the organisation set aside a wrong membership decision (Annul) or mark a record as never true (Void). It is built and tested, and the reviewer has recommended acceptance with known limitations. After that recommendation, one gap was found (V-2): the engine checks that the decision being set aside was a proper decision, but it doesn't check that the setting-aside itself is recorded as a proper decision.

  Recommendation: accept with explicit residual risks. Attach one condition: V-2 must be fixed before any correction command or database loader can create Annul records.

  Why:
  - The gap cannot be reached today. The only code in the application that can create non-decision records is the database loader, and an automated architecture test enforces that. There is also no correction command and no database storage for Annul yet.
  - The contract itself defers this area. It says the authority and "reason" parts of an Annul record stay open until the correction-command slice. It also says application and persistence criteria belong to that later slice, not to C-1.
  - No C-1 acceptance criterion is failed. Every K-criterion is met on current evidence.

  So this is a recorded residual risk with a hard precondition, not a contract breach that blocks acceptance.

  Counterargument. The contract's description of the resulting Annul record does say it carries a decision provenance. A strict reading treats any departure as non-compliance. If you want no known deviation at acceptance, choose defer: authorise the small fix (MEM-K1) first and accept afterwards. That costs one small slice and its review.

  Q2: The lost test outputs (gap G-6)

  The issue in business terms. The 10 October test outputs behind C-1 were kept in a temporary folder and are gone; only their fingerprints (hashes) remain. On 16 October a new run on the committed code (A1) passed and was saved properly.

  Recommendation: close G-6 by recording three facts:
  1. the original outputs are unrecoverable;
  2. their fingerprints stay as the historical reference, which is one of the two options the source itself offered;
  3. A1 is the evidence for the current code.

  Do not describe A1 as reproducing the lost outputs. It ran on later code, a different framework version and a stricter run mode.

  Why: this is honest, and it lets the Q1 decision rest on evidence that exists and has been checked.

  Q3: Keep the reviewer's original recommendation on record

  The issue in business terms. The reviewer's C-1 recommendation sits in a personal working file that the repository doesn't track, and the official record cites it under the wrong name. If the file is lost, the basis of the decision is lost.

  Recommendation: store it in the official reviews area under its correct name and correct the citation. First, three checks must pass:
  - privacy and content: my quick scan found no emails, credentials or personal paths, but a person must confirm. Pasted-text artefacts (&#x20;, a reference to an attachment that isn't included) should be either noted or cleaned;
  - document placement: the placement script must be run by an authorised session;
  - labelling: a banner stating "reviewer recommendation, not an acceptance".

  Alternative: annotate the record with the real filename and a fingerprint, without storing the file. This is weaker, because the file can still disappear.

  Closes when: the citation points to a tracked file.

  Decides: PO. The documentation change itself is carried out by an authorised session.

  Q6: A safe test database for Membership

  The issue in business terms. Membership's database layer and the security investigation (PBDIGIT-266) can only be tested on a database that is provably separate from shared and production data. None exists for Membership. The database approved for the voter-slug and IP-limit work does not cover Membership.

  Recommendation: a dedicated nrna_test_membership:
  - with its own restricted account that cannot reach the shared nrna_test;
  - with a permanent identity label on the database;
  - with a safety check before connecting that reuses the existing test-safety rules (PBDIGIT-283), rather than building a second guard.

  Approval sequence, from the existing plan:
  1. Name who sends the request to Infrastructure, and to whom (D-2).
  2. Infrastructure creates the database and account and removes the shared-database access (I-1).
  3. Infrastructure supplies the provisioning evidence: identity label, database ID, account name, proof of no shared access, server details.
  4. The Principal Reviewer reviews that evidence.
  5. The Human PO/ARB accepts it.
  6. The ARB re-checks the security gate (ARB-SEC-01). It failed on 2026-10-09 only because no such database existed.
  7. Database test runs are then authorised separately (P2-6).

  Counterargument. Reusing the existing isolated database would be faster. But it needs its own written approval, and it mixes two workstreams' data and timing.
