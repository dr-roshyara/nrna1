# PBDIGIT-223 — The vote's `vote_hash` is computable from voter-side data and configuration (A5)

**Type:** Defect — **constitutional (ballot secrecy)** · **Severity:** Critical · **Epic:** `PBDIGIT-EPIC-05` Voting · **Created:** 2026-10-05
**Found by:** Phase 1 characterization (roadmap `docs/plans/20261005-0647-…-roadmap-plan.md`) · evidence report `docs/publicdigit/reviews/2026-10-05-phase1-characterization-evidence-report.md`

| **Business intention (PO-stated, 2026-10-05)** | The hash was meant to support **administrator-assisted dispute resolution**: if a voter disputes the recorded result, an authorised administrator could verify that voter's ballot. Recorded as a **legitimate requirement candidate**, not as a mistake. |
| **Capability (what it provides, who holds it)** | Whoever has read access to `codes` + `votes` **and** the application configuration (`app.vote_salt`) — DB administrators, operators, holders of backups — can derive voter → ballot by recomputation. **No feature exposes it** (FACT: no code reads `vote_hash` for a lookup; only `VerifyArchitecture` checks the column), so the capability is **latent**, not a governed dispute function (no access control, no four-eyes, no audit of its use). |
| **Constitutional conflict** | Under **strong ballot secrecy** ("even the administrator cannot determine a voter's ballot") the mechanism violates non-derivability. Under **administrator-mediated dispute resolution** it would be an *accepted* capability — but then the platform offers *conditionally* anonymous voting, which must be stated explicitly and governed (and it creates a coercion surface: "even the administrator cannot know" is no longer true). |
| **Defect** | `VoteController::save_vote()` sets `vote_hash = sha256(code.id ‖ election.id ‖ code.code_to_open_voting_form ‖ castAt->timestamp ‖ config('app.vote_salt'))`. All inputs are kept on the voter side (the voter's code row; the plain-text code value, never cleared after voting; the completion second `codes.code_to_save_vote_used_at`) or in configuration. |
| **Evidence (FACT, synthetic data)** | `tests/Feature/Characterization/Phase1/BallotAnonymityCharacterizationTest::test_k1_known_gap_…` — three synthetic voters; for each code the recomputed hash matches **exactly one** vote, with **Δ = 0 s** (no search window needed); three voters → three distinct ballots (complete mapping). Source: `VoteController.php:2720-2730`. |
| **Affected boundary** | cast transaction (ballot storage) ↔ voter-side `codes` |
| **Constitutional impact** | Breaks "participation knowledge without ballot knowledge": the application/operator can derive voter → ballot deterministically. |
| **Historical data** | Every vote cast so far whose code row (id, code value, completion time) and the salt still exist is linkable — including backups. |
| **Questions for the Phase 2.0 ADR** | **Q1** Do we require strong ballot secrecy against election administrators? (yes → this mechanism must eventually disappear) · **Q2** Do we require administrator-assisted individual dispute resolution? (yes → state explicitly that ballot anonymity is not administrator-resistant, and govern the capability) · **Q3** Can dispute resolution be achieved **without** identifying the individual ballot — e.g. voter-held evidence (a receipt proving the participation / inclusion was recorded) — so that no administrator lookup exists? Today's voter-held path (receipt + view-my-vote, PBDIGIT-228) is a primitive form of Q3 with its own coercion problem. |
| **Severity** | **Critical under strong secrecy (Model B)**; under Model A an ungoverned latent capability — still to be fixed (governance, access, audit). Severity is final only after the ADR. |
| **Proposed phase** | Phase 2.0 decision → Phase 2.1 implementation of whatever the ADR decides (remove, redesign, or deliberately retain under a different trust model) · **ADR required** (also: receipt/view-my-vote semantics, historical remediation). |
| **Not in scope here** | no design chosen and no policy decided; the "random receipt secret" is a candidate only. |
