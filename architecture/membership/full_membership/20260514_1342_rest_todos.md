# The architectural gap now

Right now the domain can answer:

```php id="gxqvsv"
Can this member vote?
```

But governance systems actually need:

```text
Who is eligible to vote in this committee?
Who currently has governance rights?
Who may participate in constitutional decisions?
Which committees currently have valid members?
```

Those are:

* query concerns
* projection concerns
* read-model concerns

NOT aggregate concerns.

## Coordinate:

## Produce:

Governance-safe read DTOs.

NOT aggregates.

---

# Example target API

```php id="hho4g6"
interface EligibleCommitteeQueryService
{
    /**
     * @return EligibleVoterView[]
     */
    public function eligibleVotersForCommittee(
        CommitteeId $committeeId
    ): array;
}
```

---

# Important DDD principle

This service belongs in:

* Application layer
  or
* Read Model / Query layer

NOT inside aggregate.

---

# What the service should NOT do

Avoid:

* domain mutations
* lifecycle transitions
* policy duplication
* authorization decisions inline

It should orchestrate only.

---

# Recommended architecture

```text
Committee
    ↓

    ↓
MembershipLineage
    ↓

    ↓
```
